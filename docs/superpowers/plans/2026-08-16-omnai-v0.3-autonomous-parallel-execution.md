# OmnAI v0.3 Autonomous Parallel Execution Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver one resumable `omnai run` loop that autonomously synthesizes a shared contract and source-traceable test plan, runs isolated coding Agents concurrently in different repositories, independently reviews and verifies their work, creates Core-owned commits, proves the exact commits together in an isolated multi-project environment, preserves partial success, and recovers without unnecessary human decisions.

**Architecture:** Add a focused `src/execution/` subsystem above the existing repository-local Change state and personal Workset state. Zod YAML/JSON/JSONL records remain durable truth, XState v5 owns only legal in-process transitions through a registered per-aggregate reducer registry, a file-backed `LocalExecutionBackend` supplies locking/event/retry/settled-dispatch primitives, and ACP v1 supplies one Agent session per Run through the official TypeScript SDK. A read-only Project Test Planner proposes source-traceable project `TestCase`s and safe command definitions; Core validates and persists them, then compiles one immutable `VerificationPlan` after integration profiles have been discovered or bootstrapped. Core verifies a test-only RED tree, a full GREEN `verifiedTree`, and the metadata-only delta to the official `commitTree`, then runs the exact official commit/tree tuple through a profile-selected `compose | commands | external` integration environment before a `CommitSet` may leave `VERIFYING`. Contract coordination, deterministic scheduling, Claims, review, verification, Git integration, environment lifecycle/recovery, and CommitSets remain Core policy and are exposed only after the four ordered slices pass.

**Tech Stack:** Node.js 20+, TypeScript 5.9+, Commander, Zod 4, YAML 2, XState 5.19+, `@agentclientprotocol/sdk` 1.x (stable ACP v1 entry point), native Git CLI, Node `fs/path/crypto/child_process/stream`, and the existing `node:test` harness.

## Global Constraints

- This is one coherent feature implemented as four ordered acceptance slices: C1 lifecycle/Agent substrate, C2 contract coordination, C3 parallel project execution, and C4 hardening/release certification.
- Project truth stays in each Workset requirement worktree under `.omnai/changes/CHG-*`; Workset execution records reference `project/change/revision/task` and never copy full child Change state.
- Workset execution truth is created lazily under `~/.omnai/worksets/WKS-*/execution/`; existing v0.2 Worksets remain valid without migration.
- There is no server, database, daemon, Redis queue, Kubernetes workflow engine, or built-in model API in v0.3.
- XState defines legal transitions only. Versioned Zod records and append-only hash-linked events are the durable authority; raw XState actor snapshots are never persisted as domain truth.
- ACP v1 is the primary Agent protocol. Use the official fluent `client()` API, not deprecated `ClientSideConnection` or `AgentSideConnection` classes, and do not import the draft ACP v2 entry point.
- Every AI invocation is exactly one Run bound to at most one Agent session. Sessions are never shared or silently repurposed between Run kinds.
- Only `PROJECT_WRITER` and `RECOVERY_WRITER` may hold a Writer Claim or edit a project worktree. Coordination and review Runs use disposable read-only source snapshots plus a separate writable output inbox.
- ACP permission prompts are not containment. Autonomous writers require a profile with proven workspace-root enforcement; Core still validates source hashes and Git diffs.
- Repository A implementation completion never gates Repository B implementation start. Shared `ContractSnapshot` references coordinate projects; cross-project `dependsOn` references are rejected.
- At most one writer may exist for a repository. A Claim remains held through review and integration and is reclaimed only after liveness is proven.
- Workers never create official commits. Core preserves unexpected commits under quarantine refs, independently verifies accepted work, and creates standardized commits.
- Successful unrelated work survives failures. CommitSets are coordination records, never cross-repository atomic transactions.
- A READY ContractSnapshot is immutable and content-addressed. A changed source creates a new snapshot and targeted compatibility/revalidation work; active packets never change.
- A task may participate in multiple logical `contract:<key>` scopes. Core requires exactly one current READY snapshot per applicable key, freezes the sorted key/ref set, and never chooses one key while silently dropping another.
- Every behavior-changing task and every required ContractSnapshot business scenario is covered by an immutable, source-hash-bound `TestCase` or an explicit policy-approved `NOT_APPLICABLE` decision. A Wave cannot dispatch without one current `VerificationPlan: READY`.
- `TestCase.scopedTasks` is the sole task-coverage direction. Tasks do not author reverse TestCase links. An authoritative `TestCaseRef` always contains a source scope plus content hash; a bare `TC-*` string is display-only and cannot identify a case across projects.
- Wave members and Run Packets freeze the VerificationPlan ID/hash plus their relevant case and command refs. A generic command PASS without case mapping cannot satisfy required coverage.
- Project-local and provider/consumer contract checks gate each official project commit. Required multi-project integration/E2E checks gate only the coordinated result, so they never serialize provider and consumer implementation.
- An authoritative integration Run is bound to the exact VerificationPlan, keyed ContractSnapshot bindings, IntegrationEnvironmentProfile ID/hash, CommitSet scope hash, and sorted project `{ commit, commitTree, verifiedTree, metadataDeltaHash }` tuple. Mutable branches, floating tags, and unattested shared URLs cannot satisfy the gate.
- Integration environments support exactly `compose`, project/Workset `commands`, and enterprise `external` adapters. Core owns the fixed `setup -> build -> start -> health -> seed -> test -> collect -> teardown` lifecycle, isolation/lease proof, evidence collection, and recovery; it is not a deployment or release orchestrator.
- Environment profiles persist secret reference names only. Resolved values are memory-only, recursively redacted, excluded from hashes/events/reports, and missing authority yields `BLOCKED`/`EXTERNAL_ACTION_REQUIRED`.
- Profile discovery happens before VerificationPlan compilation. User-owned source profiles live under the Workset outside `execution/`; Core may deterministically bootstrap one from unambiguous project-owned Compose/command configuration and persists only an immutable normalized copy under execution truth.
- Authoritative command execution requires a proven sandbox, exact process-tree ownership, read-only commit snapshots, a bounded writable run root, and race-free port assignment. An unisolated command or mutable/shared environment may run only as diagnostic evidence.
- `CommitSet: COMPLETE` is a strict lock-protected transition from `VERIFYING`; it requires exact-tuple project, contract, and integration evidence plus proven collection and teardown. Test, infrastructure, stale-input, or cleanup failure preserves all official commits without claiming full-flow success.
- A CommitSet completion event is accepted only by the registered CommitSet aggregate reducer with a current `completionProofHash`. Raw backend transitions, migrations, compatibility shortcuts, public APIs, CLIs, and Skills cannot emit or synthesize `COMPLETE`.
- Core automatically authorizes only packet-bounded safe actions. Out-of-policy actions are denied; resolved secret values are memory-only and redacted from records and diagnostics.
- Human attention is limited to unresolved business choice, missing external authority/authentication, or safety that cannot be proven from available evidence.
- All new behavior uses RED -> GREEN -> REFACTOR, real Git repositories where Git semantics matter, deterministic Fake ACP Agents in ordinary CI, and frequent focused commits.
- The public `omnai run` command, `omnai-run` Host Skill, and v0.3.0 version bump land only after C1-C4 acceptance tests are green.

## Scope and slice gates

This remains one plan rather than four independent plans because each slice consumes the exact durable contracts of the preceding slice: C2 creates coordination Runs through C1, C3 consumes READY snapshots from C2, and C4 certifies the complete C1-C3 loop. Splitting those into separate specifications would duplicate and risk drifting Run, event, Agent-session, and recovery semantics.

Each slice ends with a full-suite gate:

1. **C1:** versioned lifecycle/event recovery plus Fake ACP conformance works for read-only Runs and no Agent prompt can be duplicated on restart.
2. **C2:** Planner/Critic/Resolver Runs produce source-traceable READY snapshots,
   profiles are discovered/bootstrapped, and Project Test Planner Runs plus Core
   validation produce one READY VerificationPlan or one precise blocker; no project
   implementation Writer starts here.
3. **C3:** isolated writers in different repositories run concurrently, each receives a separate Reviewer Run, Core creates commits, a real integration environment proves the exact commit tuple, and partial CommitSets recover selectively.
4. **C4:** project and environment fault injection, packaged install, a real-service golden three-repository scenario, documentation migration, and authenticated Codex certification gates are in place before the command is declared ready.

## Adversarial test gate

Adversarial assurance is orthogonal to the six existing `TestCase.level` values;
it does not introduce another level, Agent kind, writer, aggregate, ledger,
scheduler, event log, or execution engine. For every behavior-changing Task 5-22:

- add at least one positive behavior test and one table-driven `[adversarial]`
  mutation group;
- name in each group the real production boundary, exact mutation, independently
  observable safety property, and stable failure code or outcome;
- run `npm run test:adversarial`; no task, acceptance slice, or final certification
  may be declared green while that command is red or while it discovers zero tagged
  tests;
- keep the pure policy/compiler functions as the sole implementation of coverage
  rules; orchestration loads exact authority by ref and invokes those functions
  without reimplementing policy, hashing, closure traversal, or evidence acceptance;
  and
- use fakes only at Agent, process, filesystem adapter, Git adapter, Compose,
  network, or external-service boundaries. Tests exercise real schemas, compilers,
  gates, and Core call sites on either side of those fakes.

The mandatory attack matrix is:

| Task(s) | Mandatory adversarial focus |
| --- | --- |
| 5 | packet hash, command definition, permission, secret, path, snapshot drift |
| 6 | malformed ACP events, capability lies, cancellation, replay, unexpected exit |
| 7 | malicious Fake Agent, immutable handoff, restart, duplicate dispatch |
| 8-9 | source/contract forgery, unsafe validator, role confusion, poisoning, stale compatibility |
| 9B | process/Compose escape, secret leak, digest drift, resource ownership |
| 9A | policy/ref authority, v2 persistence, coverage, exemption, invalidation |
| 10-11 | incomplete dependency graph, stale evidence, cross-project implementation dependency |
| 12-17 | Wave/Claim race, member drift, impersonation, Git/path escape, evidence forgery, recovery |
| 18-22 | diagnostics, fault/resource injection, package integrity, adapter and release attacks |

The Planner proposes source-traceable cases, the Writer implements them, an
independent Reviewer reviews the result, and Core alone loads policy authority,
compiles and persists current cases/plans, admits work, accepts evidence, and
changes lifecycle state. Preserve Task order exactly: 5 -> 6 -> 7; 8 -> 9/9B ->
9A -> 10 -> 11; and 12 -> 13 -> 14 -> 15 -> 15A -> 16 -> 17. F4 remains blocked
until C1-C3 pass, and the public `omnai run` command remains blocked through Task
22.

```ts
export function sha256(value: string | Uint8Array): ContentHash {
  return `sha256:${createHash('sha256').update(value).digest('hex')}`;

function sortValue(value: unknown): unknown {
```

```ts
export function transitionLifecycle(machine: AnyStateMachine, current: string, event: { type: string }): string {
  const [initial] = initialTransition(machine);

}
```

```ts
for (let attempt = 1; attempt <= 3; attempt += 1) {
  let candidate = await runPlanner(newPlannerRun(attempt, priorFindings));
  const settled = await backend.runBounded(participants, criticCapacity, (participant) => runCritic(newCriticRun(candidate, participant)));
  const findings = requireFulfilledCriticsOrRetry(settled, participants);
  const classified = classifyFindings(findings);
  if (classified.unresolvedDecisions.length > 0) return needsDecision(onePreciseAttention(classified.unresolvedDecisions));

    continue;
  }
  return validateAndPersist(candidate, findings);
}
```

```ts
function contractRefsForCandidate(task: Task, snapshots: ContractSnapshotManifest[], scopes: ContractCoordinationScope[], scopedTask: ScopedTaskRef): ContractRef[] {
  if (task.contractRefs.length > 0) return requireExactReadyRefs(task.contractRefs, snapshots);
  const requiredScopes = scopes.filter((scope) => scopeAppliesTo(scope, scopedTask));
  if (requiredScopes.length === 0) return [];
  const applicable = snapshots
    .filter((snapshot) => snapshot.status === 'READY' && requiredScopes.some((scope) => snapshotSatisfiesScope(snapshot, scope)))
    .map(toContractRef)
    .sort(compareContractRef);
  if (applicable.length === 0) throw eligibility('CONTRACT_NOT_READY', scopedTask);
  if (hasDuplicateOrIncompatibleSnapshotForSameKey(applicable, snapshots)) throw eligibility('CONTRACT_SCOPE_AMBIGUOUS', scopedTask);
  return applicable;
}
```

`scopeAppliesTo()` matches every normalized `contract:<key>` entry from the task's
`consumes`/`produces` against frozen scope participants;
`snapshotSatisfiesScope()` then checks the manifest key, scope hash, participants,
and source traceability for the candidate project/Change/task files. A task outside
every shared-contract scope legally gets `[]`; a task inside any pending/blocked key
gets `CONTRACT_NOT_READY:<key>`, never an accidental bypass. Explicit task pins must
cover every applicable key exactly once and remain current. An unpinned task gets
exactly one READY snapshot for each applicable key, sorted by key; multiple different
keys are normal, while multiple candidates for the same key are ambiguous. All refs
are frozen into the `ReadySetItem`, Wave member, Run Packet, VerificationPlan, and
CommitSet scope. This allows snapshots allocated after task creation to coordinate
work without rewriting task metadata.

Use this explicit control flow:

```ts
export async function runWorksetExecution(options: RunExecutionOptions, services = productionExecutionServices()): Promise<ExecutionOutcome> {
  const context = await services.resolveContext(options);
  await services.ensureExecutionLayout(context);
  await services.recoverInterruptedExecution(context);
  const agentPool = await services.prepareAgentPool(context, options);

  for (;;) {
    if (options.signal?.aborted) return services.stopSafely(context);
    const contracts = await services.ensureReadyContracts(context, agentPool);
    const verificationPlan = await services.ensureReadyVerificationPlan(context, contracts);
    const readySet = await services.collectReadySet(context, {
      ...options,
      agentPool,
      verificationPlan,
      readyContractRefsByProject: contracts.readyRefsByProject,
      blockedProjects: contracts.blockingProjects,
    });
    if (readySet.items.length === 0) return services.finishOrExplainNoWork(context, contracts, readySet);
    const wave = await services.planWave(context, readySet, options);
    await services.startWave(context, wave.id);
    const settled = await services.backend.runBounded(wave.members, wave.members.length, (member) => services.executeWriterAndReview(context, member, options));
    const results = services.classifySettledWriterResults(wave, settled);
    await services.integrateReviewedResults(context, wave, results);
    await services.reconcileWaveAndCommitSet(context, wave.id);
    await services.verifyReadyCommitSetsInIntegrationEnvironments(context);
  }
}
```

`prepareAgentPool()` probes configured profiles and invokes Task 7's input-hash-bound conformance automatically for available/authenticated candidates whose evidence is missing or stale. It records unavailable/login/conformance failures as profile-specific exclusions, so one bad Agent does not block another eligible Agent; it never installs or authenticates external software.

`ensureReadyContracts()` calls `discoverContractCoordinationScopes()`, reuses exact current READY snapshots, and runs independent stale/missing scopes through C2 with bounded concurrency. It returns `{ readyRefsByProject, blockingProjects, attentionIds, externalActions }`. `NEEDS_DECISION` and external-authority results block only the projects named by their source/participant scope; all other projects still enter the Ready Set and integrate normally. Existing unresolved attention is reused by identity hash, so the loop cannot create duplicate questions. `finishOrExplainNoWork()` returns the highest-priority persisted outcome only after no unaffected ready work remains, distinguishing COMPLETE, PARTIAL with exhausted recovery, unresolved attention, external authority, and truly no applicable tasks. Bound iterations follow the finite task set and retry budgets; no busy polling loop is permitted.
