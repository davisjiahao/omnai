# OmnAI v0.2 B2b Internal Protocol Resources Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Separate OmnAI's four Host-discoverable Entry Skills from a packaged, non-discoverable protocol system that Core loads, validates, routes, audits, and exposes read-only through the CLI, including a common plain-language accessibility floor, an explicit Show-me interaction, and OmnAI's own local Visual Companion.

**Architecture:** Add a closed protocol catalog and loader under `src/protocols/`, move judgment-oriented capability guidance from embedded TypeScript and large Entry Skills into `resources/protocols/`, and keep schemas, transitions, output contracts, closures, readiness, and evidence rules in deterministic Core code. Every bundle receives a small product-level accessibility baseline from `common.authoritative-work`; richer explanation, comparison, and visualization guidance lives in `interaction.show-me`. A process-scoped loopback runtime under `src/visual/` renders validated declarative documents as OmnAI's built-in Visual Companion; it never executes Agent-provided HTML or JavaScript and has no workflow-write API. Repository runs consume the same canonical protocol resources as Workset interactions, while `omnai workset next --json` returns ordered protocol IDs and `omnai protocol show` renders the approved bundle for Codex, Claude Code, or OpenCode.

**Tech Stack:** Node.js 20+, TypeScript 5.9, Commander 14, Zod 4, YAML 2, SHA-256 and random tokens via `node:crypto`, Node `fs/path/url/os/child_process/http`, browser-native HTML/CSS/JavaScript, existing OmnAI Git/Workset APIs, `node:test`, GitHub Actions Node 20/22 matrix.

## Global Constraints

- The public Host Skill surface is exactly `omnai`, `omnai-grill`, `omnai-brainstorm`, and `omnai-reconcile`.
- `omnai-run`, Wave planning, writer claims, Run packets, and parallel execution remain unavailable until Milestone C.
- `skills/` is Host-discoverable package content; `resources/protocols/` is packaged internal content and is never copied into Host Skill directories.
- Codex, Claude Code, and OpenCode share one canonical Skill and protocol source; no Host-specific workflow forks.
- OmnAI Core never calls an LLM and never uses conversation memory as workflow state.
- Core selects legal actions and all workflow/state-bearing protocol IDs; Hosts must not recreate the Workset routing table. On explicit Show-me intent, the Host may prepend only the fixed `interaction.show-me` presentation overlay.
- Mechanical contracts remain in TypeScript/Zod: schemas, output paths, transitions, readiness, closures, evidence, guards, and approvals.
- Judgment guidance lives in versioned Markdown Protocol Resources.
- `common.authoritative-work` contains only the product-level plain-language floor; configurable tone, length, depth, and visual frequency remain future user-level preferences.
- `interaction.show-me` is explicit and read-only. It is not a fifth Entry Skill, `Capability`, Workset action, readiness key, or persisted `InteractionMode` value.
- Necessary canonical terminology, evidence, exact constraints, edge cases, and unknowns remain intact when wording is simplified.
- Visuals are used only when they reduce understanding cost; decorative visuals and mandatory images are excluded.
- Protocol loading is read-only and must complete before any repository run directory, prompt, manifest, progress event, or readiness mutation is written.
- Missing, invalid, unknown, or unmapped protocols are hard failures; there is no generic prompt or chat-memory fallback.
- Protocol hashes cover exact complete file bytes, including frontmatter; prompt hashes cover exact rendered prompt bytes.
- `omnai protocol show` is read-only and does not initialize repositories or create/advance Workset or Project Change state.
- `omnai init` initializes only repository-local `.omnai` state and has no `--host` behavior.
- No compatibility layer is retained for unreleased repository-local Host installation, `.codex/skills`, `.opencode/skills`, `ProjectConfig.installedHosts`, or fine-grained Host Skills.
- No persistent or remote Web control plane, database, daemon, background scheduler, protocol marketplace, remote protocol download, or general-purpose prompt template language is introduced. The only Web surface is an explicitly authorized, process-scoped server bound to `127.0.0.1` for the built-in Visual Companion.
- Production changes follow RED -> GREEN -> REFACTOR with a focused commit after every task.

```ts
import { homedir } from 'node:os';
import { resolve } from 'node:path';

import {
  USER_HOSTS,
  installUserHostSkills,
  listUserHostSkillStatuses,
  type UserHost,
} from './user-host-skills.js';

export function isUserLevelCommand(value: string | undefined): boolean {
  return value === 'context' || value === 'host';
}

function parseHostSelection(value: string | undefined): UserHost[] {
  if (!value || value === 'all') return [...USER_HOSTS];
  if (!(USER_HOSTS as readonly string[]).includes(value)) {
    throw new Error(`Unsupported Host '${value}'. Expected claude, codex, opencode, or all.`);
  }
  return [value as UserHost];
}

function resolveUserHome(env: NodeJS.ProcessEnv = process.env): string {
  return resolve(env.HOME ?? env.USERPROFILE ?? homedir());
}
```
