# OmnAI v0.2 Milestone B1 — Selective Re-entry and Interaction Routing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a running multi-project Workset record a mid-flight requirement/fact change, deterministically route it back to Research, Grill, Brainstorm, Experiment, Plan, or Work, insert newly affected projects as read-only candidates first, and expose the resulting next action to Codex/Claude Code/OpenCode without adding an LLM to OmnAI Core.

**Architecture:** Add immutable/history-friendly Workset Re-entry records under `~/.omnai/worksets/<id>/reentries/`. A pure routing table maps a structured change kind to an existing OmnAI capability plus an interaction mode (`none`, `grill`, or `brainstorm`). A new Workset router composes membership state and pending Re-entry state with strict precedence: newly discovered candidate research first, then unresolved read-only impact decisions, then pending Re-entry interaction, then ordinary active-project work.

**Tech Stack:** Node.js 20+, TypeScript, Commander, Zod, YAML, existing personal Workset APIs, existing repository-local workflow/readiness/reconcile APIs, native `node:test` harness.

## Global Constraints

- OmnAI Core does not call an LLM and does not classify free-form natural language.
- The Agent host translates user language into a structured `ReentryKind`; the CLI validates and persists it.
- Grill and Brainstorm are interaction modes inside existing capabilities, not mandatory global stages.
- A Workset Re-entry record is coordination history, not a replacement for project-local `.omnai` Revision/Baseline truth.
- Milestone B1 does not mutate project Change Revision/Baseline state; project-level reconcile propagation belongs to B2.
- Newly affected repositories must enter `CANDIDATE -> RESEARCH_ONLY` before writable activation.
- If a Re-entry names a new candidate project, candidate/read-only research takes precedence over the pending Grill/Brainstorm route.
- `OBSERVED_ONLY` means research disproved the need for a code change; the Re-entry may continue for other affected projects.
- `ACTIVE -> INACTIVE` semantics from Milestone A remain unchanged.
- No Web UI, database, daemon, server, background scheduler, or built-in LLM API.
- Implement every executable behavior test-first with RED -> GREEN -> REFACTOR.

## Plan Self-Review

- **Spec coverage:** user-visible mid-flight requirement changes, re-Grill/re-Brainstorm routing, candidate project discovery, research-first precedence, persistence/recovery, explainable next action, and CLI contracts all map to explicit tasks.
- **Scope:** project-level `reconcileChange()` propagation, cross-project Revision dependencies, writer claims/Waves, and user-level host skill installation are explicitly outside B1 and reserved for B2/C.
- **Type consistency:** Re-entry IDs use `WRE-\d{4}`; Workset IDs remain `WKS-\d{4}`; the eight `ReentryKind` values are identical across schema, route table, CLI validation, tests, and docs.
- **Safety:** candidate injection validates before mutation; no candidate operation creates a Worktree; resolved records are retained; existing Milestone A Worktrees are never moved/deleted/reset.
- **Testing:** each executable unit has an explicit RED/GREEN cycle and the final gate reruns the complete release-oriented suite.
