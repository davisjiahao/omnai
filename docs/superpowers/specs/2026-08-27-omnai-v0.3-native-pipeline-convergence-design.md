## 1. 结论

后续开发以 `948d927` 的 native/final-v0.3 模型为唯一架构基线，不合并或逐提交移植 `full-pipeline-fusion` 的旧模型实现。旧分支中已经验证的恢复权限能力只作为需求证据，其不变量改写到 native 的 `ChangeAuthorityContext`、`AuthorityEnvelope`、持久 owner、`MachineAuthoritySeal` 与有序 audit outbox 中。

本次收敛遵循四条硬边界：

1. 不恢复 v0.2 或中间 v0.3 的兼容 reader、writer、CLI 或持久 Schema。
2. 不把旧 `RecoveryAuthorityPlan` 实现机械搬入 native，避免形成第二套事务与权限模型。
3. 不修改、清理、暂存或覆盖三个旧工作区；所有新工作只发生在本分支。
4. 先用可执行诊断归属门管理 `888 diagnostics / 76 files` 的迁移债务，再按 Plans02–09 顺序恢复全仓绿色；`micro-change` 必须最后实施。

## 4. RecoveryAuthority 不变量的 native 映射

| 旧规格不变量 | final-v0.3 的唯一承载 | 关闭计划 |
|---|---|---|
| owner 只能来自已认证冻结 transaction | `AuthorityEnvelope`、owner kind、operation request/digest 与冻结 payload | Plan03、Plan04 |
| 同一锁内一次读取当前机器状态 | `ChangeAuthorityContext` 固定 inventory 与 observed-I/O，写前封印 | Plan02、Plan04 |
| 当前状态只能是唯一操作序列的精确前缀 | 通用持久 owner 的 PENDING/COMPLETED 状态机与 frozen target publication | Plan03、Plan04 |
| 先按稳定 owner 范围选候选，再验证 correlation 等正文 | 全局 authority chain、owner inventory、request/payload binding；不以待验证 audit 字段缩小集合 | Plan03、Plan04、Plan08 |
| prepare-before-write | `normalize → provider → native gate → lock → context → owner branch → frozen PENDING → target` | Plan02–Plan06 |
| commit 不二读、不重新编译、不调用业务 callback | 只消费 frozen payload，随后用 `MachineAuthoritySeal` 验证真实目标 | Plan02–Plan06 |
| PENDING 与 COMPLETED 使用同一候选、顺序和边界规则 | 共享 owner recovery、全局 chain inventory 与 exact ordered audit outbox | Plan04、Plan08 |
| ordinary、Decision、Flow 的 source/target/completed 规则一致 | 三类 public mutation 收口到同一 Core writer fence 和 owner family | Plan04 |
| ordinary 与 Scenario 只有一个终态算法 | `ordinaryTerminalTarget`；Scenario 只包装并绑定 nested digest | Plan08 |
| completed/global lineage 不忽略 orphan、fork、错序或额外事件 | 全链认证、outbox full-list equality、Plan09 对抗与发布再认证 | Plan08、Plan09 |

final-v0.3 不保留旧 `UNOWNED_INTERNAL` 持久写入模式。无 owner 的逻辑只能是无副作用的纯编译器或只读投影；任何 durable mutation 必须映射到 writer census 中唯一、可恢复的 owner。

实现内部可以使用一次性的 prepared recovery value，但它不得成为第二个持久 Schema、第二条 chain、公共 API 或绕过 `ChangeAuthorityContext`/`AuthorityEnvelope` 的路径。

## 5. 诊断迁移基线

在干净的本分支、Node `v24.19.0`、npm `11.9.0` 上已复现：

- TypeScript diagnostics：`888`
- 受影响文件：`76`
- `TS2339`：`538`
- `TS2345`：`171`
- `TS2322`：`124`
- `npm test`：在 TypeScript build 阶段退出 `2`，尚未执行测试

这不是可发布的绿色基线，而是 Plan01 收紧模型后留给 Plans02–09 的显式迁移债务。诊断门必须满足：

1. 每个当前 diagnostic path 有且仅有一个未来 owner。
2. 未归属路径立即失败。
3. `completed-through` 及更早 owner 的残留立即失败。
4. `src/execution/**` 只能由 Plan07 原样退出 native 编译/包/runtime 图，禁止修改来消除诊断。
5. Plan07 起 `typecheck`、`build`、`npm test` 必须恢复全绿；Plan09 完成时 diagnostics/files 必须为 `0/0`。
6. 每次计划退出都生成 fresh ledger，不把 RED 叙述为 GREEN。
7. Plans02–09 的 17 个 exact `Files` 重叠保留在计划依据中；transition manifest 必须用 `overlapOwners` 逐项指定最早必须清零诊断的阶段，禁止加载器按文件顺序静默选 owner。后续计划再次修改同一路径不构成诊断债务移交。
8. owner 到期后，即使诊断已经清零，非 `CLOSED` 条目仍阻止 transition；`CLOSED` 只能通过 manifest 的 `closed` 清单表达，且任何仍携带诊断的 `CLOSED` 条目失败关闭。
9. 任何包含 `error TS<n>:` 但不能解析为仓库相对文件 headline 的 TypeScript 输出都失败关闭，不能因同一输出中另有可解析诊断而被忽略。
10. manifest、计划 `Files` token 与 baseline key 必须是 canonical 仓库相对路径；计划文档在 `realpath` 后仍须位于当前收敛工作区，禁止通过绝对路径、遍历或 symlink 从旧工作区读取 owner 依据。

## 6. 开发顺序

1. 收敛规格、计划与 transition ownership gate。
2. Plan02：Authority Context、Git Provider、SourceRef。
3. Plan03：Project Genesis、全局 AuthorityEnvelope chain。
4. Plan04：Core writer 收口，并吸收 native RecoveryAuthority 不变量。
5. Plan05：Stage、Run、Task、Issue、Evidence 与 verification lifecycle。
6. Plan06：Workspace、Workset、WOP 与原生 Worktree publication。
7. Plan07：Host、CLI、package surface，原样退休旧 Execution，恢复全仓绿色。
8. Plan08：exact ordered audit outbox、ordinary/Scenario 唯一终态与恢复闭环。
9. Plan09：清理、对抗、打包、双门发布再认证和最终评审。
10. 在 Plan09 全绿后 Reconcile 并实施 `micro-change`。

Plan04 与 Plan06 只有在 Plan03 完成后才允许分开推进；共享 Schema、catalog、compiler 和 authority primitive 仍是单 writer。当前执行环境按串行顺序实施，避免共享工作区冲突。
