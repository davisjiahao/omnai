# OmnAI v0.2 B2b Internal Protocol Resources Design

## 1. Status and decision

This document records the approved **Option A** architecture for OmnAI v0.2 B2b:

```text
four Host-discoverable Entry Skills
                +
non-discoverable packaged Protocol Resources
                +
deterministic OmnAI Core routing and state
```

It is a design amendment to `docs/design/omnai-v0.2-b2b-user-host-skills.md`.

The decision is intentionally a clean pre-release break. OmnAI has not published a stable release, so this design does not preserve the earlier fine-grained Host Skill surface or embedded prompt layout for compatibility.

## 2. Problem

B2b has already reduced the public Host surface to four Skills:

```text
omnai
omnai-grill
omnai-brainstorm
omnai-reconcile
```

The repository workflow still contains many fine-grained capabilities such as `research`, `model`, `spec`, `design`, `plan`, `debug`, `work`, `review`, and `verify`. Those capabilities need detailed execution guidance, but exposing every capability as a Host Skill creates three problems:

1. users must understand the internal state machine and choose among many commands;
2. Host auto-discovery can invoke a downstream Skill directly and bypass Workset, Re-entry, readiness, and evidence guards;
3. maintaining the same workflow across Codex, Claude Code, and OpenCode becomes a large prompt-forking problem.

Moving all detailed guidance into the four Entry Skills is also wrong. It would make the default router large, repeatedly load unrelated instructions, and couple changes to independent capabilities.

The approved architecture separates **discovery**, **judgment guidance**, and **mechanical enforcement**.

## 3. Goals

B2b Protocol Resources must:

- keep `skills/` limited to exactly four Host-discoverable Entry Skills;
- keep one canonical workflow definition shared by Codex, Claude Code, and OpenCode;
- preserve detailed, independently maintainable guidance for every repository capability;
- provide detailed Workset protocols for candidate research, impact decisions, Project Change binding, and Re-entry handling;
- provide a product-level plain-language accessibility floor through `common.authoritative-work`;
- provide an explicit, read-only Show-me interaction for explanations, comparisons, and useful visual representations;
- let OmnAI Core select protocol IDs deterministically;
- let the Agent Host perform language understanding and artifact authoring without letting chat become workflow state;
- reuse the same repository protocol source when Core generates a bounded capability prompt;
- package protocols with the npm artifact but never copy them into Host Skill directories;
- record the exact protocol versions and hashes used by prepared repository runs;
- fail safely when a protocol is missing, invalid, or unmapped.

## 4. Non-goals

This design does not add:

- a Web UI, server, database, daemon, or background scheduler;
- an embedded LLM API or Core-side natural-language classifier;
- `omnai-run`, Wave planning, writer claims, Run packets, or parallel execution;
- separate Claude, Codex, and OpenCode workflow prompts;
- a protocol marketplace or remote protocol download system;
- user-edited protocol forks as a supported customization model;
- configurable or persistent personal preferences for tone, response length, explanation depth, or visual frequency;
- a blanket ban on technical terminology;
- a diagram or generated image in every response;
- a new Workset `InteractionMode` value for Show-me;
- automatic migration for unreleased fine-grained Skill installations;
- a general-purpose prompt templating language.

Project-specific policies remain repository truth under `.omnai/project/` and related artifacts. Personal interaction preferences belong in a future user-level preference layer, not in canonical protocol files.

The product-level accessibility floor is not a personal preference. It standardizes only four minimum behaviors: state practical meaning first, prefer ordinary language when it is equally precise, define unavoidable specialized terms on first use while retaining their canonical names, and never weaken evidence or exact constraints merely to simplify wording.

## 5. Definitions

### 5.1 Entry Skill

A Host-discoverable `SKILL.md` installed into the native user directory of Codex, Claude Code, or OpenCode.

Entry Skills answer:

- when should this entry be invoked;
- how does it obtain OmnAI context;
- which deterministic Core command is authoritative;
- which safety boundaries must never be bypassed.

Entry Skills do not contain the complete method for every engineering capability.

### 5.2 Protocol Resource

A packaged Markdown document containing judgment-oriented execution guidance for one repository capability, Workset action, or interaction mode.

Protocol Resources are not copied into Host Skill directories and are not discoverable as slash commands or autonomous Skills.

### 5.3 Mechanical contract

A rule that Core can enforce deterministically, such as schemas, allowed transitions, output paths, exact closures, readiness state, evidence requirements, or approval gates.

Mechanical contracts stay in TypeScript and schemas. They are not delegated to Markdown instructions.

### 5.4 Protocol bundle

An ordered, validated set of Protocol Resources rendered for one action. The common authoritative-work protocol is automatically prepended, requested protocols retain their declared order, and duplicate IDs are removed deterministically.

### 5.5 Show-me interaction

An on-demand presentation protocol loaded when the user explicitly asks for an explanation, comparison, visualization, “show me”, or says that the current explanation is unclear.

Show-me changes only how already-authorized information is presented. It is not a repository capability, Workset action, Re-entry interaction state, readiness transition, or canonical artifact.

## 7. Protocol identity and metadata

Every Protocol Resource starts with validated YAML frontmatter.

Repository example:

```yaml
---
schemaVersion: 1
id: repository.design
version: 1
kind: repository-capability
capability: design
---
```

Workset example:

```yaml
---
schemaVersion: 1
id: workset.reentry-replan
version: 1
kind: workset-action
actions:
  - replan-reentry
---
```

Interaction example:

```yaml
---
schemaVersion: 1
id: interaction.grill
version: 1
kind: interaction
interaction: grill
---
```

The explicit explanation interaction uses:

```yaml
---
schemaVersion: 1
id: interaction.show-me
version: 1
kind: interaction
interaction: show-me
---
```

The `show-me` metadata value is independent from the Workset domain type `InteractionMode`. That type remains exactly `none | grill | brainstorm`; Show-me is never persisted as Re-entry state.

The ID-to-path convention is fixed:

```text
repository.design          -> resources/protocols/repository/design.md
interaction.grill          -> resources/protocols/interaction/grill.md
interaction.show-me        -> resources/protocols/interaction/show-me.md
workset.reentry-replan     -> resources/protocols/workset/reentry-replan.md
common.authoritative-work  -> resources/protocols/common/authoritative-work.md
```

Core exposes a closed `PROTOCOL_IDS` inventory. Unknown IDs are rejected; callers cannot supply arbitrary filesystem paths.

The SHA-256 hash covers the exact complete file bytes, including frontmatter. The body returned to an Agent excludes frontmatter.

### 7.1 Show-me interaction contract

`interaction.show-me` is selected only when the user explicitly asks for an explanation, comparison, visualization, “show me”, or indicates that the current explanation is not understandable. It changes presentation for the current response; it is not stored as a user preference and is not automatically added to unrelated protocol bundles.

The resource instructs the Host to:

- lead with the practical conclusion and plain-language meaning;
- define a specialized term or acronym briefly on first use, then retain the canonical term for precision and search;
- use short sentences, concrete nouns, observable outcomes, trade-offs, and user impact;
- calibrate depth from demonstrated familiarity in the current domain without inferring a persistent user profile;
- preserve exact constraints, evidence references, assumptions, exceptions, and unknowns instead of replacing them with vague analogies or guesses;
- choose the smallest representation that materially reduces understanding cost;
- keep a textual takeaway with every non-text representation.

Representation guidance is based on the information shape, while the Host still judges whether a representation materially improves understanding:

| Information shape | Default representation | Do not use |
| --- | --- | --- |
| One fact or short explanation | Prose or a short list | A diagram that repeats the prose |
| Exact alternatives, mappings, or repeated fields | Markdown table | Loose prose that hides differences |
| Flow, hierarchy, state transition, dependency, or multi-project relationship | Mermaid | Long linear text that obscures structure |
| Visual appearance or interaction not expressible precisely in Markdown | Available Host-native visual, when materially clearer and technically accurate | Decoration or generated imagery presented as technical evidence |

Show-me is read-only. Loading or applying it does not create a Workset or Project Change, initialize a repository, write a canonical artifact, prepare a run, append progress, advance readiness, or modify personal state. If answering requires missing facts, the Router selects the appropriate read-only research or investigation path. If verified facts conflict with active intent, normal Reconcile rules apply.

## 8. Core protocol module

A focused module owns protocol discovery, validation, hashing, and bundle rendering:

```ts
export const PROTOCOL_IDS = [/* closed canonical inventory */] as const;
export type ProtocolId = (typeof PROTOCOL_IDS)[number];

export interface ProtocolRef {
  id: ProtocolId;
  version: number;
  hash: string;
}

export interface ProtocolDocument extends ProtocolRef {
  kind: 'common' | 'repository-capability' | 'interaction' | 'workset-action';
  content: string;
  sourcePath: string;
}

export interface ProtocolBundle {
  schemaVersion: 1;
  protocols: ProtocolDocument[];
  rendered: string;
}

export async function loadProtocol(
  id: ProtocolId,
  protocolRoot?: string,
): Promise<ProtocolDocument>;

export async function loadProtocolBundle(
  ids: ProtocolId[],
  protocolRoot?: string,
): Promise<ProtocolBundle>;
```

`loadProtocolBundle()` automatically prepends `common.authoritative-work`, preserves requested order, and removes duplicates.

### 8.1 Common accessibility baseline

`common.authoritative-work` contains the product-level communication floor that applies to every rendered bundle:

1. state the practical result or meaning before implementation detail;
2. prefer ordinary wording whenever it is equally precise;
3. when a specialized term is necessary, define it briefly on first use and retain its canonical name for precision and search;
4. never weaken an exact contract, evidence claim, safety rule, edge case, or unknown merely to simplify wording.

Tone, response length, detailed explanation depth, and preferred visual frequency do not belong in this common protocol. `interaction.show-me` adds the richer on-demand presentation and representation method.

The production locator resolves the packaged `resources/protocols` directory from `import.meta.url`, with a repository-root candidate only for source development. Tests inject an isolated protocol root.

## 9. Public read-only protocol command

The Agent Host obtains internal guidance through Core, not by guessing an npm installation path.

```text
omnai protocol show <protocols...>
omnai protocol show <protocols...> --json
```

Examples:

```bash
omnai protocol show workset.candidate-research --json
omnai protocol show interaction.grill repository.model workset.reentry-plan --json
omnai protocol show interaction.show-me --json
omnai protocol show interaction.show-me repository.design --json
```

JSON output is exactly one object:

```json
{
  "schemaVersion": 1,
  "protocols": [
    {
      "id": "common.authoritative-work",
      "version": 1,
      "hash": "sha256:...",
      "kind": "common",
      "content": "..."
    },
    {
      "id": "interaction.grill",
      "version": 1,
      "hash": "sha256:...",
      "kind": "interaction",
      "content": "..."
    }
  ],
  "rendered": "..."
}
```

Human output prints the rendered Markdown bundle.

The command is read-only. It does not initialize a repository, create a Workset, create a Project Change, advance readiness, or write personal state.

## 10. Repository capability flow

Repository capabilities continue to use the existing bounded-run model.

```text
Entry Skill
    -> omnai context --json
    -> repository scope
    -> omnai next
    -> omnai <capability>
    -> prepareStage()
    -> loadProtocolBundle([repository.<capability>])
    -> compose bounded prompt
    -> write run prompt and run manifest
    -> Agent reads prompt and authors canonical outputs
```

`src/core/prompts.ts` no longer contains the `stagePrompts` record. It becomes a small composer that accepts loaded protocol content, the user instruction, and Core-generated output contract.

The existing `STAGES` table keeps deterministic fields:

- output files;
- readiness key;
- authoritative context file list;
- machine-verifiable output contract.

The Markdown protocol keeps judgment guidance:

- method and sequencing;
- questions and heuristics;
- stop conditions;
- common failure modes;
- when to route back to Grill, Brainstorm, Experiment, or Reconcile.

This boundary follows the rule: if Core can validate it mechanically, Core owns it; if it requires engineering judgment, the protocol explains it.

## 11. Repository run audit

Prepared run manifests move to schema version 2 and record the exact protocol inputs:

```ts
export interface StageRunManifest {
  schemaVersion: 2;
  id: string;
  changeId: string;
  revision: string;
  capability: Capability;
  status: 'PREPARED' | 'COMPLETED' | 'FAILED' | 'CANCELLED';
  instruction: string;
  promptPath: string;
  promptHash: string;
  protocols: ProtocolRef[];
  outputPaths: string[];
  createdAt: string;
  completedAt?: string;
}
```

`promptHash` covers the exact rendered prompt bytes. This makes later evidence and debugging able to answer which protocol and complete prompt produced a run.

The current unused `workflow.lock.yaml.promptVersions` field is removed before the first release instead of pretending to pin content it does not enforce. Artifact schema and workflow version metadata remain. A future published-version migration system may introduce a real protocol lock when its upgrade semantics are designed.

## 12. Workset routing flow

`omnai workset next --json` remains the authoritative action selector and adds an ordered `protocolIds` field.

The deterministic mapping is:

| Workset action | `protocolIds` |
| --- | --- |
| `inspect-project` | `workset.candidate-research` |
| `decide-project-impact` | `workset.project-impact-decision` |
| `reenter` + `grill` | `workset.reentry-interaction`, `interaction.grill`, `repository.<capability>`, `workset.reentry-plan` |
| `reenter` + `brainstorm` | `workset.reentry-interaction`, `interaction.brainstorm`, `repository.<capability>`, `workset.reentry-plan` |
| `reenter` + `none` | `workset.reentry-interaction`, `repository.<capability>`, `workset.reentry-plan` |
| `decide-reentry` | `workset.reentry-decision` |
| `apply-reentry` | `workset.reentry-apply` |
| `replan-reentry` | `workset.reentry-replan` |
| `finalize-reentry` | `workset.reentry-finalize` |
| `project-workflow` | `workset.project-workflow-handoff` |
| `none` | empty list |

The Host loads the returned bundle through:

```bash
omnai protocol show <protocolIds...> --json
```

`workset.project-impact-decision` directs the Host to load `workset.project-change-binding` only after the user chooses a writable outcome. This preserves the explicit decision boundary between read-only observation and Project Change/Worktree creation.

`omnai-reconcile` loads `workset.reentry-classification` before recording a new WRE. After the WRE exists, the Router-provided protocol list is authoritative.

No Host-side table independently maps WRE kinds or Workset actions to methods.

Show-me is not a `WorksetRouteAction`, WRE interaction value, repository capability, or lifecycle transition. For an explicit Show-me trigger, the default Router first runs `omnai context --json`, then loads `interaction.show-me` through the read-only protocol command. It combines the interaction with an active repository or Workset protocol only when Core has already selected that protocol and the user is asking to understand that current action. The Host does not invent a capability or protocol mapping merely to produce an explanation.

## 13. Entry Skill responsibilities

### 13.1 `omnai`

The default router remains thin. It:

1. runs `omnai context --json`;
2. follows repository `next` or Workset `workset next --json`;
3. loads the protocol IDs selected by Core;
4. executes only the current legal action;
5. returns to the deterministic Router;
6. requires fresh verification evidence before completion claims.

It does not restate all repository capability methods.

For an explicit explanation, comparison, visualization, “show me”, or “I do not understand” request, it runs `omnai context --json` and loads `interaction.show-me` with `omnai protocol show interaction.show-me --json`. The Entry Skill contains only this trigger, the Core loading command, and the read-only boundary; terminology and representation methods remain in the Protocol Resource.

### 13.2 `omnai-grill`

The entry contains only trigger conditions, context bootstrapping, and the instruction to load `interaction.grill` plus the active capability protocol. The full Decision Frontier and questioning method live in the internal interaction resource.

### 13.3 `omnai-brainstorm`

The entry contains only trigger conditions, context bootstrapping, and the instruction to load `interaction.brainstorm` plus the active capability protocol. Full option comparison and Experiment escalation live in the internal interaction resource.

### 13.4 `omnai-reconcile`

The entry contains change-detection triggers and non-bypassable safety rules. Detailed classification, proposal, decision, apply, replan, and finalize procedures live in Workset and repository Reconcile resources selected by context and Core routing.

Entry Skills never reference a physical `resources/` path. They access protocols only through `omnai protocol show`.


It never copies `resources/` into:

```text

~/.agents/skills
~/.config/opencode/skills
```

Host installation manifests and hashes continue to cover only installed Entry Skill files. Protocol integrity is validated from the installed npm package by the protocol loader and `omnai doctor`.

## 15. Error handling and mutation safety

Protocol resolution is preflighted before a workflow mutation.

For repository `prepareStage()`:

1. resolve and validate the complete protocol bundle;
2. build the full prompt in memory;
3. only then create the run directory, write files, append progress, and mark readiness `IN_PROGRESS`.

Failures use explicit categories:

```text
PROTOCOL_UNKNOWN
PROTOCOL_RESOURCE_MISSING
PROTOCOL_METADATA_INVALID
PROTOCOL_MAPPING_MISSING
PROTOCOL_PACKAGE_ROOT_NOT_FOUND
```

There is no silent fallback to embedded text, a similarly named file, conversation memory, or a generic capability prompt.

A Workset route without a valid protocol mapping is a Core defect and fails explicitly. It does not return an actionable route with an empty protocol list except for `action: none`.

## 16. Clean-break changes

Implementation removes or replaces:

- the `stagePrompts` object embedded in `src/core/prompts.ts`;
- embedded cross-cutting `COMMUNICATION_CONTRACT` prompt text;
- full Show-me method bodies embedded in `skills/omnai/SKILL.md`;
- standalone communication documents that duplicate this protocol authority;
- detailed method bodies from the four Entry Skills;
- any remaining fine-grained Host Skill installation or discovery logic;
- the unused `workflow.lock.yaml.promptVersions` field;
- documentation that tells an Agent to invoke fine-grained `omnai-*` Skills;
- assumptions that a Host can read the npm package directory directly.

It preserves:

- all current deterministic capabilities and Scenario routing;
- `STAGES` mechanical output/context contracts;
- repository run prompts and manifests;
- Workset lifecycle and B2a Reconcile state machines;
- Core-calculated Readiness and Task closures;
- explicit human approval before DECIDED Re-entry plans;
- user-level installation of exactly four Entry Skills.

## 17. Test contract

Implementation tests must prove:

1. `skills/` contains exactly four `SKILL.md` files;
2. the repository protocol inventory exactly covers every value in `CAPABILITIES`;
3. the Workset protocol inventory covers every actionable `WorksetRouteAction` variant;
4. `reenter` protocol ordering is deterministic for `none`, `grill`, and `brainstorm` interactions;
5. protocol IDs cannot escape the packaged root or inject arbitrary paths;
6. frontmatter ID, kind, capability/action metadata, and version are validated;
7. hashes cover exact file bytes and bundle order is stable;
8. `common.authoritative-work` is prepended exactly once;
9. `omnai protocol show ... --json` emits exactly one valid object and performs no writes;
10. invalid and missing protocols fail with explicit errors;
11. repository prompt generation contains the packaged protocol body and no embedded `stagePrompts` source;
12. protocol preflight failure creates no run directory, progress event, or readiness mutation;
13. schema-v2 run manifests record protocol refs and the exact prompt hash;
14. `workset next --json` emits the expected `protocolIds` for every route;
15. Entry Skills call `omnai context --json`, use deterministic routing, and load internal protocols through the CLI;
16. Entry Skills do not contain the full fine-grained capability methods or direct `resources/` paths;
17. `npm pack --dry-run` includes all canonical protocols and only four Host Skills;
18. user-level Host installation never copies protocol resources;
19. `omnai doctor` validates the protocol inventory and metadata;
20. `common.authoritative-work` contains the minimum accessibility floor and is prepended exactly once to Show-me and every other bundle;
21. `interaction.show-me` has the exact canonical path, metadata, version, and hash, and appears in the closed protocol inventory;
22. Show-me adds no Host Skill, `Capability`, Workset action, readiness key, or Workset `InteractionMode` value;
23. the `omnai` Entry Skill routes explicit Show-me triggers through `omnai protocol show interaction.show-me --json` without embedding the terminology or representation method;
24. loading or applying `interaction.show-me` creates no Workset, Project Change, run directory, progress event, readiness change, canonical artifact, or personal preference state;
25. Show-me protocol tests cover first-use term explanation with canonical-name retention, plain-language-first ordering, representation selection, textual takeaways, precision preservation, and unknown handling;
26. Node 20 and Node 22 pass typecheck, the full test suite, build, package dry-run, and whitespace checks.

Behavioral forward-evaluation remains separate from deterministic Core tests. It covers at least: a simple concept that needs no diagram; an unavoidable specialized term; two structured alternatives suited to a table; a multi-step state flow suited to Mermaid or a labeled text fallback; a missing-evidence case that must remain unknown; and an expert follow-up that gains detail without losing the plain-language entry point.

## 18. Invariants

1. `skills/` is the public Host surface; `resources/protocols/` is internal package content.
2. Four Entry Skills are shared across all supported Hosts.
3. Core chooses legal actions and protocol IDs; the Host does not recreate the routing table.
4. Core owns schemas, transitions, closures, gates, and persistence.
5. Protocols guide judgment but never replace Core state.
6. Every repository capability has one canonical protocol source.
7. The same repository protocol is used by generated run prompts and explicit interaction bundles.
8. Protocol loading is read-only and preflighted before mutation.
9. Missing or invalid guidance is a hard failure, never a generic fallback.
10. Project-specific rules remain project truth rather than global protocol forks.
11. Protocol Resources are packaged but never installed as Host Skills.
12. `omnai-run` remains unavailable until Milestone C implements real execution primitives.
13. The common accessibility floor is a product invariant, not a persisted personal communication preference.
14. Show-me is an interaction resource, never a fifth Entry Skill or workflow state.
15. Workset `InteractionMode` remains `none | grill | brainstorm`.
16. Necessary canonical terminology, evidence, exact constraints, edge cases, and unknowns are preserved even when presentation is simplified.
17. Visuals are selected only when they reduce understanding cost; decorative visuals are not protocol compliance.

## 19. Design self-review

- **Placeholder scan:** no TBD, TODO, deferred implementation placeholder, or unspecified error behavior remains.
- **Internal consistency:** the directory tree, protocol IDs, route mapping, CLI contract, package boundary, and audit fields use one naming model.
- **Scope:** the design is limited to Entry Skill/protocol separation and the Core plumbing required to load, route, package, audit, and validate protocols.
- **Ambiguity:** the Host never reads package paths directly; Workset routes return ordered protocol IDs; repository runs load the same canonical resources through Core; mechanical contracts remain code-defined.
