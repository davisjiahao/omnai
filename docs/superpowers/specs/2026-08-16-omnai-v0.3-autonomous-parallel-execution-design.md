# OmnAI v0.3 Autonomous Parallel Execution Design

**Date:** 2026-08-16
**Status:** Approved design
**Target:** OmnAI v0.3.0
**Scope:** Milestone C — autonomous contract coordination, bounded parallel Runs, recovery, and CommitSets

## 1. Decision and supersession

This design replaces the Milestone C execution model in
`docs/design/omnai-v0.2-personal-workspace.md` where that document defines:

- a Workset-level cross-project task dependency graph;
- downstream repository tasks waiting for upstream repository task completion;
- host-assisted worker creation without a standard coding-Agent protocol or a
  Core-owned authority boundary; and
- workers committing before Core has validated the resulting change.

The following v0.2 decisions remain authoritative:

- a Workset coordinates, but does not replace, repository-local Changes;
- each active project has a dedicated requirement-branch Git worktree;
- original repositories are not mutated to execute a Workset;
- project Changes, Revisions, Baselines, tasks, and evidence remain project-local truth;
- multiple repositories may be written in parallel;
- one repository has at most one active writer;
- Reconcile is the only legal way to advance invalidated intent; and
- CommitSet is a coordination record, not a cross-repository Git transaction.

The v0.3 correction is fundamental:

> Repositories do not depend on one another's implementation tasks. Participating
> projects share one immutable, AI-produced `ContractSnapshot`. Once that shared
> development baseline is valid, provider and consumer implementations may start
> in parallel.

Project-local task dependencies remain legal. Cross-project `dependsOn` references
are rejected and must be expressed as a shared `contractRef`, an integration gate,
or a rollout gate.

## 2. Problem

OmnAI v0.2 can create and reopen a safe multi-project requirement workspace, bind
project Changes, reconcile changed project membership, and route work through host
skills. It deliberately does not yet provide real execution primitives.

A naive Milestone C would make consumer repository tasks wait for a provider
repository task to finish. That serializes work unnecessarily. If an HTTP, RPC, or
message contract is sufficiently defined, all participating projects can implement
against the same baseline using generated clients, mocks, fixtures, and contract
tests.

A second naive approach would ask a human to author and approve every contract,
start each agent manually, integrate every result manually, and recover every
failed run manually. That also contradicts OmnAI's purpose. All relevant project
source, intent artifacts, design artifacts, project rules, and tests are already
available to the active AI host.

v0.3 therefore needs a local, durable execution coordinator that lets AI perform
the reasoning while deterministic Core rules preserve safety, idempotency,
recoverability, and auditability.

## 3. Goals

v0.3.0 must:

1. automatically derive or update a shared cross-project contract from active
   intent, design, existing contracts, source, tests, and project knowledge;
2. independently evaluate that contract from provider, consumer, and critic
   perspectives;
3. generate an immutable `ContractSnapshot` with scenarios, mocks, validation
   evidence, and source hashes;
4. reject cross-project task dependencies while retaining project-local task DAGs;
5. calculate deterministic, bounded Waves from currently eligible tasks;
6. automatically start isolated workers through Agent Client Protocol (ACP) v1,
   with a narrow Native Adapter fallback for hosts that cannot speak ACP;
7. enforce at most one active writer for each repository;
8. give every worker one immutable, bounded Run Packet;
9. let workers edit and test, but let Core reconstruct behavioral test-only RED,
   validate final-tree GREEN, prove metadata-only commit delta, and create the
   final commit;
10. preserve successful repository results when another repository fails;
11. recover safely after CLI, ACP session, Native Adapter, or worker interruption
    without duplicate workers or commits;
12. detect contract changes, revalidate compatible work, and replan only affected
    work;
13. ask a human only when available facts do not determine one defensible business
    choice, an external authority is missing, or safety cannot be proven;
14. use read-only Project Test Planner Runs plus Core validation to make tasks,
    acceptance criteria, and contract scenarios traceable through immutable,
    scoped/content-addressed `TestCaseRef` and `VerificationPlan` records;
15. run repository-local, provider/consumer contract, and—when policy requires
    it—real multi-service integration/E2E verification as distinct test layers;
16. bind every authoritative multi-service result to the exact ContractSnapshot
    for each contract key/scope, VerificationPlan, profile and definition bytes,
    executors, supporting/external artifact digests, CommitSet scope, and Git
    commit/commitTree/verifiedTree/metadata delta for every participating repository;
    and
17. produce a `CommitSet` that links project commits, exact contract snapshots, and
    fresh verification evidence and becomes `COMPLETE` only after every required
    integration environment gate passes and cleans up safely.

## 4. Non-goals

v0.3.0 does not add:

- automatic merge to project `main` branches;
- remote PR creation or merge;
- release, deployment, or CI/CD orchestration;
- a general-purpose container, Kubernetes, cloud, or shared-QA environment
  platform;
- a full API, event, or schema-management product;
- a database, server, or resident daemon;
- Temporal, Argo Workflows, or another external workflow engine;
- multi-machine scheduling;
- multi-user distributed locking;
- the Milestone D VS Code management extension;
- a separately maintained native Claude Code or OpenCode Adapter; or
- a claim that AI can infer business intent that is absent from every available
  source.

An ACP client, OmnAI's ACP compatibility profile, a Fake ACP Agent, and a narrow
Native Adapter fallback are in scope. Codex through its ACP adapter is the first
release-certified Agent. Other ACP-compatible Agents can be discovered and used
when they satisfy the same capability and conformance requirements; they are not
all release-certified by v0.3.

Local disposable test environments and narrow adapters to project-owned commands or
an enterprise-provided isolated test environment are in scope. They verify exact
development commits before CommitSet completion; they do not merge, release, deploy
to production, or replace a company's environment and delivery systems.

## 5. Architecture

OmnAI remains a local Node.js 20+ and TypeScript CLI. It uses XState v5 for legal
lifecycle transitions; Zod-validated YAML, JSON, JSONL, and Markdown for stable
domain persistence; atomic filesystem writes; and native Git commands. It gains no
server or database. Raw XState actor snapshots are not durable domain truth.

```text
Requirement + active Changes + all active project source
                         |
                         v
                 Contract Coordinator
          AI synthesis, independent review, validation
                         |
                         v
                Project Test Planner
       Read-only test-case synthesis and Core validation
                         |
                         v
                 Verification Planner
       Traceable cases and immutable verification plan
                         |
                         v
                    Ready Set Planner
            Deterministic bounded Wave snapshot
                         |
                         v
                 Execution Coordinator
              Writer Claim + Run Packet
                         |
                         v
                     ACP Client
          Codex / Claude / OpenCode / other Agents
             Native Adapter only as fallback
                         |
                         v
             Requirement-branch worktrees
                         |
                         v
          Core validation + Core-owned commit
                         |
                         v
                CommitSet VERIFYING
                         |
                         v
            Integration Environment Runner
       Exact commits -> real services -> E2E evidence
                         |
                         v
                 CommitSet COMPLETE
```

The main components are:

### 5.1 Contract Coordinator

Prepares shared development truth. It starts one read-only Contract Planner to
synthesize a candidate, parallel isolated Project Critics for every provider and
consumer perspective, and a Contract Resolver only when their structured findings
conflict. The roles produce business scenarios, executable validation assets, and
structured evidence. Core validates and freezes the result.

Core does not embed or call one specific model directly. Intelligent work is
requested through the ACP boundary or conforming Native fallback. Core owns
legality, schemas, hashing, state transitions, and acceptance of the result.

### 5.2 Ready Set Planner

Calculates which project-local tasks are currently executable. It does not build a
cross-project implementation DAG. It checks local task readiness, active project
membership, worktree state, ContractSnapshot readiness, writer availability,
signals, policy, and host capacity.

### 5.3 Execution Coordinator

Owns Wave, Claim, Run, retry, recovery, and CommitSet state. XState v5 defines each
legal transition and rejects illegal events; OmnAI's versioned Zod domain records
and append-only event log remain the persistence and audit boundary. The component
is responsible for exactly-once logical dispatch, bounded retries, deterministic
recovery, and the transition from worker-reported completion to Core-verified
integration.

### 5.4 Agent connectivity

OmnAI acts as an ACP v1 Client for compatible coding Agents. Local Agents run as
subprocesses over JSON-RPC on stdio. Core negotiates capabilities, creates or
restores sessions, sends one immutable Run Packet prompt, consumes typed progress
events, answers permission requests from deterministic policy, and cancels or
closes sessions when required.

ACP is the primary interoperability contract; OmnAI does not redefine its session,
prompt, cancellation, filesystem, terminal, permission, or progress protocols. A
narrow Native Adapter can wrap a host that cannot speak ACP, but must expose the
same Core-facing session semantics and pass the same conformance suite. Neither an
ACP Agent nor a Native Adapter can choose work or mutate workflow state directly.

### 5.5 Git integrator

Validates the worktree against the immutable Run Packet and starting Git HEAD,
reconstructs the Core-owned test-only and final verified trees, proves RED then
GREEN where required, updates only authorized project-local task/evidence metadata,
creates the final commit, proves the metadata-only tree delta, and records all tree
identities in a CommitSet.

### 5.6 Recovery coordinator

Uses current YAML state, append-only events, Git state, process information, ACP
session capabilities and events, Native Adapter inspection where applicable, and
stored patches to resume interrupted work without duplicating a worker or
discarding recoverable work.

### 5.7 Execution backend boundary

The orchestration domain depends on an internal `ExecutionBackend` boundary for
durable transition append, state materialization, bounded dispatch, retry timing,
and wake-up. v0.3 ships only `LocalExecutionBackend`, implemented with the existing
atomic files, foreground CLI process, and restart reconciliation. This is not a
public plugin API in v0.3.

Run Packet, Writer Claim, ACP session, verification, Git integration, and CommitSet
semantics remain above that boundary. A later server or team edition may implement
the boundary with Temporal, Restate, DBOS, or a queue without redefining those
domain contracts.

### 5.8 Verification Planner

Before compilation, one read-only `PROJECT_TEST_PLANNER` Run per affected project
reads that project's immutable Change/Revision/task/spec/design sources and proposes
project-local TestCases as a structured artifact. It has no Writer Claim and cannot
edit the project. Core validates source hashes, scoped-task coverage, executor
resolvability, ID/ref uniqueness, and policy, then persists the accepted cases as
project truth under the active Change. Replanning creates a new Run and immutable
case revision; it never overwrites accepted meaning.

The Verification Planner then compiles those Core-accepted project-local cases,
ContractSnapshot business scenarios, active task identity, risk policy, configured
commands, and integration profiles into one immutable `VerificationPlan`.
Core—not an Agent—checks coverage, source hashes, command/profile resolvability,
and policy. A plan must be `READY` before an affected task may join a Wave.
Changing a case, task Revision, contract, command, profile, or policy produces a
new content-addressed plan and never changes an active Run Packet.

### 5.9 Integration Environment Runner

After all required project members have official commits, Core materializes exact
read-only commit snapshots and drives one configured environment through setup,
build, start, health, seed, test, evidence collection, and teardown. The runner
owns lifecycle legality, input hashing, resource identity, redaction, bounded
recovery, and acceptance of structured results. Adapter `prepare` is side-effect
free parsing and validation; `setup` is the only allocation boundary. Teardown and
the adapter's fallback `release` are ownership-proven and idempotent. Every running
step accepts cancellation, enforces a timeout, and terminates its entire owned
process/container tree before final collection. Docker Compose, project-owned
commands, and enterprise environment adapters implement only this declared
boundary; none may mutate OmnAI workflow state or broaden the authority of Core.

## 6. Fact ownership and persistence

Project truth remains in each active worktree:

```text
<project-worktree>/.omnai/changes/CHG-*/
  change.yaml
  tasks.yaml
  test-cases.yaml
  progress.jsonl
  revisions/
  runs/
  evidence/
```

Workset execution truth is stored under the personal Workset:

```text
~/.omnai/worksets/WKS-0001/
  workset.yaml
  integration/
    profiles/
      authorization-local.yaml
    definitions/
    executors/
  workspace/
  reentries/
  execution/
    contracts/
      CTR-0001/
        manifest.yaml
        contract.yaml
        scenarios.yaml
        evidence/
    verification-plans/
      VPL-0001/
        plan.yaml
    waves/
      WAVE-0001.yaml
    runs/
      RUN-0001/
        packet.yaml
        state.yaml
        events.jsonl
        agent-session.yaml
        outputs/
        evidence/
    claims/
      user-center.yaml
    commitsets/
      CST-0001.yaml
    integration-environments/
      profiles/
        authorization-local-sha256-....yaml
      runs/
        IER-0001/
          input.yaml
          state.yaml
          events.jsonl
          evidence/
    progress.jsonl
```

`integration/` is the user-owned configuration surface. `omnai run` discovers
checked-in project commands and Compose definitions, asks the read-only planning
roles to propose a draft profile when deterministic discovery is sufficient, and
stores or updates only a user-reviewable profile in this path. A missing external
credential or an unresolvable environment choice produces one precise action; the
user is never expected to edit `execution/` records. Before plan readiness, Core
strictly resolves the selected profile, definition bytes, command definitions,
executor artifacts, supporting images/services, and external attestations, then
copies one content-addressed immutable snapshot into
`execution/integration-environments/profiles/`. Later source-path changes create a
new snapshot and cannot change an active VerificationPlan or environment Run.

The Workset never copies full child Change state. Wave, Run, VerificationPlan, and
CommitSet records reference a fully scoped child task:

```text
project/change/revision/task
```

Accepted project-local TestCases remain project truth. Their `scopedTasks` entries
are the only authoritative task-to-case coverage direction; `tasks.yaml` does not
contain bare TestCase IDs. Workset records use only scoped, content-addressed
TestCase references and immutable normalized snapshots needed for execution and
audit.

Every state file has an explicit schema version. Writes use existing atomic file
helpers. A short-lived Workset mutation lock serializes Core state-file changes.
That lock is separate from the long-lived repository Writer Claim and any
environment resource lease. It is never held while an AI worker or environment
command executes.

`outputs/` is an Agent-writable staging inbox, not authoritative Workset state. An
Agent or environment command cannot write `state.yaml`, `events.jsonl`, Claims,
Waves, ContractSnapshots, VerificationPlans, IntegrationEnvironmentRuns, or
CommitSets. Core validates, hashes, and records a staged artifact before any state
transition may reference it.

Every accepted lifecycle event has a stable event ID and monotonically increasing
sequence. Under the mutation lock, Core appends and flushes the event before it
atomically replaces materialized state containing `lastEventSequence` and
`lastEventHash`. On startup, a missing, stale, or ahead materialized state is
reconstructed or rejected from the append-only log before any side effect is
dispatched. The persisted record also pins the lifecycle-machine schema version so
an upgrade cannot silently reinterpret an in-flight Run. A version mismatch
requires a registered, tested state migration; otherwise the affected execution is
blocked before dispatch with a precise compatibility error.

## 7. ContractSnapshot

### 7.1 Meaning

A `ContractSnapshot` is the immutable shared baseline for one set of parallel
project implementations. It is not limited to an OpenAPI document. It may contain:

- HTTP paths, request and response schemas, errors, and examples;
- RPC IDL;
- message topics, keys, payload schemas, delivery semantics, ordering, retry, and
  idempotency rules;
- business scenarios and expected outcomes;
- generated mocks, fixtures, or client inputs;
- compatibility policy; and
- traceability from requirement to contract element to project use and test.

Existing OpenAPI, AsyncAPI, JSON Schema, Protobuf, Thrift, Markdown, source, tests,
or external schema references are inputs. If no sufficient contract exists, AI
generates the change-local contract artifacts. OmnAI does not become an interactive
enterprise API editor.

### 7.2 Minimum manifest

```yaml
schemaVersion: 1
id: CTR-0001
worksetId: WKS-0001
status: READY
contentHash: sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
previousSnapshot: null
participants:
  - project: user-center
    role: PROVIDER
  - project: quote-center
    role: CONSUMER
  - project: order-center
    role: CONSUMER
sources:
  - kind: intent
    ref: user-center/CHG-0002/REV-0003/intent.md
    contentHash: sha256:abcdef0123456789abcdef0123456789abcdef0123456789abcdef0123456789
businessScenarios:
  - SC-001
  - SC-002
validationEvidence:
  - EVD-001
  - EVD-002
createdByRun: RUN-0001
createdAt: 2026-08-16T00:00:00.000Z
```

### 7.3 Lifecycle

```text
GENERATING -> VALIDATING -> READY -> SUPERSEDED
                    |
                    +---------> INVALID
```

`READY` means technically usable, immutable, source-traceable, and validated. It
does not mean AI has discovered intent that does not exist. No manual approval is a
normal readiness condition.

An existing READY snapshot is never overwritten. Any change creates a new
snapshot. Core records and compares exact content hashes.

### 7.4 Business-correctness evidence

The Contract Coordinator must not accept one Agent's unsupported confidence. It
requires:

1. traceability from active intent and design to the contract;
2. a provider feasibility analysis;
3. a separate analysis for every consumer project;
4. an independent conflict and omission review;
5. normal, boundary, failure, retry, and compatibility scenarios where applicable;
6. parsable machine-readable artifacts where such formats exist;
7. generated mocks, fixtures, or executable contract-test inputs where practical;
8. successful configured validators; and
9. no unresolved contradiction that can affect implementation.

AI can normally decide from available sources. When two business choices remain
equally defensible and tests cannot distinguish them, the affected work enters
`NEEDS_DECISION`. The question must identify the exact missing decision and provide
evidence-backed options. Unaffected work continues.

Stable scenario IDs are mandatory. Snapshot validation must prove that every
applicable scenario has enough source identity and executable validation input to
compile provider, consumer, integration, or E2E TestCases. The subsequent
VerificationPlan gate—not ContractSnapshot readiness itself—proves complete case
coverage. This preserves the ordered flow `ContractSnapshot READY ->
VerificationPlan READY` and avoids a circular readiness dependency.

## 8. Test and verification model

### 8.1 Three test layers

Milestone C distinguishes tests by the development fact they prove:

| Layer | Exact input | Execution point | Acceptance meaning |
|---|---|---|---|
| Project-local | one scoped task, Run Packet, starting tree, Core-reconstructed test-only tree, final verified tree, then the official commit/commit tree | Writer TDD and Core RED/GREEN pre-commit verification | the new behavioral test fails for the intended reason before production changes and all mapped cases pass on the final verified tree |
| Contract | one exact ContractSnapshot plus one provider or consumer `verifiedTree` | snapshot validation, Writer work, and Core verification | the project implements the shared API/event/schema semantics without waiting for another repository |
| Multi-service integration/E2E | exact ContractSnapshot and VerificationPlan hashes, environment profile/artifact hashes, CommitSet scope, and official commit/commitTree for every service | after all required project commits exist | real services start, become healthy, communicate, and satisfy cross-project business scenarios |

Project-local and contract checks gate each official project commit. Multi-service
verification gates coordinated completion; it never gates the start of provider or
consumer implementation. A partial CommitSet may retain passing commits but cannot
claim full-flow success.

For each behavior-changing Writer result, Core reconstructs a detached
`testOnlyTree` from the exact starting tree plus only authorized new/changed test,
fixture, and test-harness paths. It runs the mapped new cases and requires a
behavioral `RED` attributable to the missing change, not a syntax, dependency,
environment, or unrelated failure. Core then constructs the exact final candidate
`verifiedTree` from all authorized Writer changes and requires `GREEN` for every
applicable project and contract case. If a policy-approved case cannot support a
meaningful test-first check, the VerificationPlan must contain a hashed exemption;
Writer prose cannot waive RED. Both tree identities, commands, case outcomes, and
bounded diagnostics become evidence.

The tests in this section are **user-project tests**. They are distinct from the
unit, schema, Git, Fake ACP, fault-injection, package, golden, and live Codex tests
that verify OmnAI itself in Section 19.

### 8.2 TestCase

A `TestCase` is a stable, machine-readable verification obligation. Project-local
cases remain project truth under the active Change. The read-only
`PROJECT_TEST_PLANNER` proposes them from acceptance criteria, design, tasks, and
existing tests; Core validates and persists them. `TestCase.scopedTasks` is the
single authoritative task-to-case coverage direction. Tasks never carry bare case
IDs. Cross-project cases remain Workset truth and derive from stable
ContractSnapshot scenario IDs. The record describes intent and traceability; the
implementation remains in the project's chosen test framework.

```yaml
schemaVersion: 1
id: TC-0042
contentHash: sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
title: Revoked authorization is rejected by quote and order
level: E2E
required: true
sourceRefs:
  - ref: quote-center/CHG-0002/REV-0003/spec.md#AC-07
    contentHash: sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
contractRefs:
  - id: CTR-0001
    contentHash: sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
scenarioRefs: [SC-007]
scopedTasks:
  - project: quote-center
    changeId: CHG-0002
    revision: REV-0003
    baseline: BL-0001
    taskId: TASK-001
ownerProjects: [quote-center, user-center]
expectedOutcome: Revoked credentials produce the contract denial and no quote
executorRef: e2e.authorization-revoked
evidenceRequired: [test, contract, service-logs]
```

A bare `TC-*` value is display-only and never authoritative outside its owning
case file. Every persisted packet, plan, evidence record, or recovery decision uses
one canonical `TestCaseRef`:

```yaml
scope: PROJECT
project: quote-center
changeId: CHG-0002
revision: REV-0003
id: TC-0010
contentHash: sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
```

For a cross-project case, `scope: CONTRACT` replaces project/change/revision with
`worksetId`, normalized `contractKey`, coordination `scopeHash`,
ContractSnapshot ID/hash, and scenario ID.
These scoped fields plus `id` and `contentHash` form the reference identity.
Different projects may use the same display ID without collision. Semantic changes
produce a new content hash and, when meaning changes, a new case revision/ID.

Allowed levels are `UNIT`, `COMPONENT`, `CONTRACT_PROVIDER`,
`CONTRACT_CONSUMER`, `INTEGRATION`, and `E2E`. Every required acceptance criterion
and applicable contract scenario has at least one required case, or a frozen,
policy-backed `NOT_APPLICABLE` decision. Every behavior-changing task is named by
at least one accepted case's `scopedTasks`; test-only or documentation tasks may
carry a reviewed exemption. A `PROJECT_TEST_PLANNER` result is a proposal, not
evidence: Core must prove its source hashes, complete scoped-task coverage, case
reference uniqueness, and executor mapping before persistence. Semantic changes
create a new case revision or identity and invalidate evidence.
`ownerProjects` routes failure analysis and recovery only; it is never a
cross-project implementation dependency.


`READY` requires complete source/contract/task traceability, risk-policy coverage,
resolvable command and environment profile references, and no duplicate or missing
required case. The plan freezes the full canonical `TestCaseRef` and environment
profile hash for every reference; ID-only references are invalid rather than merely
stale. A Wave and every project Run Packet freeze the plan ID/hash and the
project-relevant scoped case/command subset. Changing a case, command, profile,
task Revision, policy, or contract creates a new plan; active packets never change.

Existing repository verification commands remain supported, but each authoritative
command has a stable `commandRef` and maps to scoped TestCaseRefs. A generic `npm test` PASS
without that mapping is useful evidence but does not alone satisfy full
traceability.

### 8.4 VerificationEvidence

Every accepted evidence record binds:

- VerificationPlan ID/hash and sorted scoped, content-addressed TestCaseRefs with per-case
  `PASS | FAIL | INCONCLUSIVE | SKIPPED` outcomes;
- exact ContractSnapshot references;
- a discriminated subject: project
  commit/commitTree/verifiedTree/metadataDeltaHash, IntegrationEnvironmentRun, or
  compatibility revalidation;
- command reference/hash, exit code, bounded redacted output hash, artifact/report
  hashes, timestamps, and Core/adapter identity; and
- for environment evidence, the exact sorted project
  commit/commitTree/verifiedTree/metadataDeltaHash tuple, profile-definition,
  executor, supporting/external artifact digests, and environment input hashes.

`SKIPPED` cannot satisfy a required case unless the frozen plan contains a specific
policy-approved reason. Agent prose, a mutable branch name, a floating image tag,
or a generic successful command is never sufficient authority.

### 8.5 IntegrationEnvironmentProfile

A strict, secret-free `IntegrationEnvironmentProfile` declares how to execute one
real multi-service test environment. Its editable source lives under the user-owned
Workset `integration/` path; `execution/` contains only Core-resolved immutable
snapshots. `omnai run` may bootstrap a draft from safely discovered checked-in
Compose definitions and configured project commands, but Core must validate and
freeze it before plan readiness. Profiles are content-addressed over all non-secret
semantics and referenced definition bytes. The closed drivers are `compose`,
`commands`, and `external`.

```yaml
schemaVersion: 1
id: authorization-local
driver: compose
requiredProjects: [order-center, quote-center, user-center]
definitionRef: integration/compose.yaml
```

Command definitions use executable plus argv arrays and a bounded cwd, not an
implicit shell string. Each command declares network policy, timeout, output limit,
required artifacts, required sandbox capability, and cancellation/kill-tree
semantics. Profiles persist environment-variable names only. Secret
values are resolved at spawn time, excluded from hashes and durable records, and
recursively redacted from output before persistence. Missing secret authority is an
external blocker, never permission to copy or invent a credential.

`shell: false`, argv validation, cwd selection, or read-only mode bits are not a
sandbox. A `commands` profile is authoritative only when Core proves an OS,
container, or conforming host sandbox that confines filesystem roots, network,
process descendants, credentials, and resource limits for every phase. Otherwise
it may run only as explicitly labeled diagnostic evidence and cannot satisfy a
required gate.

Adapter boundaries are:

- **Docker Compose:** OmnAI may use a checked-in definition and generated run-local
  override. It owns unique project/network/volume names, dynamic ports, labels,
  exact build contexts, logs, and teardown. It never rewrites the source definition
  or accepts a floating build context as evidence. Before allocation it parses the
  normalized effective configuration and applies a closed deny policy. Privileged
  containers, host PID/IPC/network, devices, Docker/container sockets, unapproved
  capabilities, and host bind mounts outside exact read-only snapshots and the
  owned run root are non-authoritative and blocked unless a separate explicit host
  policy proves equivalent containment.
- **Project or Workset commands:** projects own their scripts and semantics. OmnAI
  validates argv/cwd/policy, sequences the fixed phases, supplies immutable inputs,
  and accepts structured results. A successful arbitrary script proves only the
  cases explicitly mapped to it.
- **Enterprise environment:** a narrow adapter may reserve an isolated
  namespace/tenant, publish exact artifacts through already-authorized company
  mechanisms, return endpoints, run tests, collect evidence, inspect the lease, and
  release it. OmnAI does not become a deployment, Kubernetes, cloud, CI/CD, or
  production-release orchestrator. A static shared QA URL with no verifiable
  artifact identity or exclusive lease is diagnostic only and cannot satisfy the
  authoritative gate.

Adapter `prepare` resolves and validates immutable inputs without side effects.
Only the runner's `setup` phase may allocate resources. `teardown` performs normal
owned cleanup; adapter `release` is an idempotent fallback over the same ownership
proof and may not broaden the deletion set. Each step accepts an `AbortSignal`, and
timeout/stop kills the complete owned process/container tree before collection and
cleanup continue.

### 8.7 IntegrationEnvironmentRun lifecycle

```text
PLANNED -> SETTING_UP -> BUILDING -> STARTING -> HEALTHCHECKING
        -> SEEDING -> TESTING -> COLLECTING -> TEARING_DOWN
        -> PASSED | TEST_FAILED | INFRA_FAILED | BLOCKED | CANCELLED

Any active phase -> COLLECTING -> TEARING_DOWN -> terminal outcome
TEARING_DOWN failure -> CLEANUP_REQUIRED
CLEANUP_REQUIRED -> TEARING_DOWN -> preserved primaryOutcome
SAFETY_UNPROVEN -> TEARING_DOWN -> preserved primaryOutcome
```

The durable record includes an `IER-*` ID, input hash, machine version, phase,
attempt, owned resource IDs, reserved ports, process/container/lease identities,
timestamps, per-case outcomes, evidence refs, `primaryOutcome`, primary failure,
cleanup attempts, and cleanup result. `SAFETY_UNPROVEN` is a closed status alongside
`CLEANUP_REQUIRED`; neither erases the primary test/infrastructure/cancel outcome.
Core owns every transition; environment commands only return structured outputs.

The phases have fixed meaning:

1. `setup` verifies immutable inputs and allocates the run root, snapshots,
   network/namespace/lease, dynamic ports, and ownership labels;
2. `build` builds pinned local sources and records image/artifact digests;
3. `start` starts only the exact built artifacts with run-scoped identities;
4. `health` proves every declared service and dependency is ready;
5. `seed` loads namespaced, idempotent fixtures tied to the contract and cases;
6. `test` executes the plan's integration/E2E cases and emits per-case results;
7. `collect` always captures redacted service logs, reports, health history,
   digests, and environment metadata, including after an earlier failure; and
8. `teardown` removes or releases only resources whose run ownership is proven.

Every Run has an isolated root and opaque run-derived resource names. Compose uses
a unique project, network, labels, and volumes. Service DNS is preferred; host
ports are selected under a short-held allocation lock, which is released
immediately after one durable reservation record is written. The reservation—not
the lock—remains active until start proves ownership or cleanup completes. Shared
environments without an exclusive
namespace/lease are serialized and remain non-authoritative if another actor can
mutate the same data. Seed operations use the environment Run ID as an idempotency
namespace. Teardown may never delete an unlabeled or otherwise unowned resource.

Setup, start, seed, inspect, and teardown use the Run ID as an idempotency key. On
restart Core reconciles event state with owned processes, labels, ports, filesystem
markers, or the external lease. It resumes a phase only when exact authority and
idempotency are proven; otherwise it collects available evidence, cleans up the old
owned instance, and starts a new Run. It never reruns a test against a possibly
mutated environment and calls that a retry.

`TEST_FAILED` routes failed cases and shared evidence to Recovery Writers for the
declared owner projects. `INFRA_FAILED` consumes a bounded environment retry budget
without blaming project code. Missing required evidence blocks acceptance even
when a test command returned zero. `CLEANUP_REQUIRED` blocks CommitSet completion
and is visible to doctor. Ambiguous ownership or unprovable cleanup becomes
`SAFETY_UNPROVEN`; existing commits, evidence, and `primaryOutcome` are retained.
After ownership is re-established, either cleanup status may retry only teardown
with the same Run ID/idempotency key; it never reruns tests. A successful retry
records cleanup proof and restores the preserved primary terminal outcome. If
ownership remains unprovable, Core takes no destructive action and continues to
block completion.

## 9. Cross-project coordination semantics

### 9.1 No cross-project task dependency

Repository A implementation completion is never a prerequisite for Repository B
implementation start merely because A is a provider and B is a consumer. Consumer
work uses the same ContractSnapshot, mocks, and fixtures while provider work is in
progress.

Project-local `Task.dependsOn` remains valid only for task IDs inside the same
Change. Workset validation rejects fully-qualified task dependencies that cross a
project boundary and explains that the caller must use:

- `contractRef` for a shared implementation baseline;
- an integration gate for multi-project verification; or
- a rollout gate for deployment order.

Integration and rollout gates do not serialize implementation start.

### 9.2 Wave meaning

A Wave is a deterministic, bounded snapshot of tasks that can start now. It exists
to:

- cap resource consumption;
- select at most one writer for each repository;
- freeze the task, Change Revision, Baseline, ContractSnapshot, VerificationPlan,
  TestCase subset, and Run inputs;
- explain why every selected task was eligible;
- provide an interruption and partial-success checkpoint; and
- support repeatable recovery.

It no longer represents cross-repository code dependencies.

### 9.3 Eligibility

A task can join the Ready Set only if:

- its Workset member is `ACTIVE`;
- the bound project Change and task are current and writable;
- project-local dependencies are satisfied;
- every required ContractSnapshot is `READY`;
- one current `VerificationPlan` is `READY`, covers the task's required TestCases,
  and binds those exact ContractSnapshot and task inputs;
- the project worktree and requirement branch are valid and clean for a new Run;
- the repository has no active Writer Claim;
- no invalidating signal affects the task;
- risk and allowed paths are bounded;
- policy permits the work; and
- a configured Agent profile reports sufficient ACP or Native capability and
  remaining capacity.

Planner output is stable for equal input. Stable project and task ordering breaks
ties. Host capacity can split independent projects across multiple Waves without
introducing an artificial dependency.

### 9.4 Wave lifecycle

```text
PLANNED -> RUNNING -> COMPLETE
                    |-> PARTIAL
                    |-> SUPERSEDED
```

## 10. Writer Claims

A Writer Claim is a repository-scoped lease bound to exactly one Run:

```yaml
schemaVersion: 1
project: quote-center
runId: RUN-0002
phase: WRITING
worktree: /Users/example/.omnai/worksets/WKS-0001/workspace/quote-center
branch: feat/auth-v2
ownerProcess: 21931
agentProtocol: acp
agentId: codex
agentSessionId: sess_codex_run_0002
acquiredAt: 2026-08-16T00:01:00.000Z
heartbeatAt: 2026-08-16T00:01:30.000Z
```

Claim acquisition is atomic. A second writer is rejected even if both tasks appear
in otherwise legal planner input. A Claim is released after integration, block,
safe cancellation, or proven worker termination.

Claim phase advances through `WRITING`, `REVIEWING`, `INTEGRATING`, and optionally
`RECOVERING`. The Claim remains held after a Writer exits while its disposable
Reviewer Run and Core integration operate, so the reviewed tree cannot change under
them. Only the `WRITING` and `RECOVERING` phases expect a live writer process.

Expired time alone is not proof that a writer has stopped. Core inspects the process
and ACP session, or the Native Adapter session when applicable, before reclaiming
the lease. If liveness is uncertain, Core preserves the Claim and surfaces
attention instead of risking two writers.

## 11. Run Packet and Run state

### 11.1 Run kinds and session cardinality

Every AI invocation is a distinct Run with exactly one Agent session. Supported Run
kinds are:

- `CONTRACT_PLANNER`;
- `PROJECT_CRITIC`;
- `CONTRACT_RESOLVER`;
- `PROJECT_TEST_PLANNER`;
- `PROJECT_WRITER`;
- `PROJECT_REVIEWER`; and
- `RECOVERY_WRITER`.

Coordination Runs can reference a parent coordination cycle. A Reviewer Run records
the Writer Run it evaluates. A Recovery Writer records the failed or invalidated
Run it repairs. Agent sessions are never shared between Runs, even when the same
Agent implementation is selected. Only `PROJECT_WRITER` and `RECOVERY_WRITER` Runs
may acquire Writer Claims.

### 11.2 Immutable packet

Each Run receives one immutable `packet.yaml`. Fields that do not apply to a
read-only coordination Run are explicitly absent rather than inferred. The packet
contains at least:

- Run kind, Run, parent Run or coordination-cycle, Wave, Workset, project, Change,
  Revision, Baseline, and task IDs as applicable;
- starting Git HEAD, worktree, and requirement branch for project Runs;
- exact ContractSnapshot IDs and content hashes;
- exact VerificationPlan ID/content hash, applicable scoped/content-addressed
  TestCaseRefs, and stable command references;
- the bounded objective and required protocol bundle;
- allowed paths;
- required verification commands, expected per-case obligations, and evidence
  requirements;
- stop conditions;
- Agent selection, protocol, ACP session policy, and execution limits;
- deterministic permission policy, including allowed filesystem roots, terminal
  actions, network policy, and operations that must be denied;
- a hash of the full packet.

The packet is never rewritten. Replanning creates a new Run.

### 11.3 Mutable state

```text
read-only: PREPARED -> STARTING -> RUNNING -> FINISHED -> ACCEPTED
writer:    PREPARED -> CLAIMED -> STARTING -> RUNNING -> FINISHED -> ACCEPTED
                                                                      |
                                                                      +-> INTEGRATED

RUNNING or FINISHED may also produce:
BLOCKED | SIGNALED | FAILED | STALE | CANCELLED | RECOVERING
```

The guarded `CLAIMED` branch is mandatory for Writer Run kinds and illegal for
read-only kinds. `FINISHED` means only that the Agent reported completion.
`ACCEPTED` requires schema, staleness, role, and evidence checks. `INTEGRATED` is
legal only for Writer Run kinds after review, Core verification, and Core commit.

### 11.4 Outcomes

- `finish` supplies a structured summary, changed paths, logs, and evidence refs.
- `block` supplies a concrete blocker and any recoverable work.
- `signal` identifies an invalidated assumption, contract, Revision, or safety
  boundary.

Workers cannot redefine the Workset, select another task, broaden allowed paths,
spawn another OmnAI Run, or create the final Git commit.

## 12. Agent orchestration and ACP boundary

### 12.1 Primary protocol

ACP v1 is the primary protocol between OmnAI and coding Agents. OmnAI uses the
official TypeScript SDK as an ACP Client instead of inventing a parallel wire
protocol. It relies on ACP for:

- initialization, authentication discovery, version and capability negotiation;
- `session/new`, `session/load`, `session/resume`, `session/close`, and session IDs;
- `session/prompt`, streamed `session/update` events, plans, messages, tool-call
  progress, and stop reasons;
- `session/cancel` and request cancellation;
- filesystem, terminal, and elicitation requests;
- permission requests; and
- MCP server injection at session creation or restoration.

OmnAI adds domain policy around ACP; it does not fork ACP schemas. OmnAI-specific
metadata uses the protocol's extension facilities and remains optional to a generic
ACP Agent.

### 12.2 Core session wrapper

Core exposes these internal operations to the rest of OmnAI:

```text
probe    discover process, authentication state, ACP version, and capabilities
start    spawn or connect, initialize, create a session, persist its ID, then prompt
inspect  combine process liveness, session events, and persisted Run state
signal   cancel or close a session without stealing its Writer Claim
collect  normalize the prompt result, updates, logs, and evidence references
resume   prefer session/resume, then session/load, else perform Git-aware recovery
```

For a new Run, Core persists the returned ACP session ID atomically before sending
`session/prompt`. A crash before the prompt can leave only an idle session, never an
untracked writer. After the prompt is sent, recovery reconnects to that exact
session and does not issue a second prompt while its outcome is uncertain.

An ACP session ID is not the OmnAI idempotency key. The immutable Run ID is the
logical dispatch key, and exactly one active Agent session may be bound to it.

### 12.3 Agent profile and capability policy

ACP capabilities are combined with local, non-secret scheduling policy:

```yaml
schemaVersion: 1
agentId: codex
protocol: acp
command: codex-acp
available: true
authenticated: true
protocolVersion: 1
maxParallelSessions: 3
isolation:
  mode: agent-sandbox
  enforcedWorkspaceRoots: true
capabilities:
  loadSession: true
  resumeSession: true
  closeSession: true
  mcpStdio: true
omnaiModes:
  - coordination-read-only
  - project-writer
  - project-reviewer
```

ACP capabilities are negotiated, while capacity, isolation, and authorized OmnAI
roles come from host policy and conformance evidence. Planner decisions never rely
on a model's prompt claim about its own authority.

Agent selection is deterministic. Core first filters by required role, protocol
version, isolation, session recovery, tools, configured policy, and remaining
capacity. It then sorts eligible profiles by explicit user or Workset priority,
health, current load, cost class, and stable Agent ID. `--agent` constrains this
selection but cannot waive a hard capability or safety requirement. An LLM may
explain or recommend an Agent, but it never makes the authoritative routing
decision.

### 12.4 Orchestration roles

Core mediates every role and all handoffs:

1. **Contract Planner** — reads all applicable sources and produces one structured
   contract candidate.
2. **Project Critics** — run in parallel and in isolated contexts, one for each
   provider or consumer project, and produce structured findings without editing.
3. **Contract Resolver** — runs only when the candidate and findings contain a
   resolvable conflict; it cannot bypass validators or invent absent intent.
4. **Project Test Planner** — one read-only Run per affected project proposes
   source-hash-bound project TestCases whose `scopedTasks` cover that project's
   active behavior-changing tasks. Core, not the Agent, validates and persists the
   proposal; the Run cannot edit project source or task state.
5. **Project Writer** — owns one Writer Claim and edits only one authorized
   requirement worktree.
6. **Project Reviewer** — receives the immutable packet, diff, evidence, and
   acceptance rules in a read-only session. When capacity allows, policy prefers a
   different Agent implementation or model from the Writer, but isolated context is
   the minimum requirement.
7. **Core Verifier and Git Integrator** — performs deterministic checks and creates
   the official commit; it is not an AI Agent role.

Non-conflicting critic omissions and corrections create a new Contract Planner Run
with the findings as bounded input. The Resolver is reserved for contradictory
findings that available evidence can settle. Each revision is a new Run; an Agent
session is never silently repurposed for a different candidate.

A coordination or review session has no Writer Claim and no project/source write
permission; it may write only its dedicated Run output directory. A Writer session
has exactly one project Claim. No Agent may directly spawn another OmnAI Run,
transfer a Claim, select the next project, or alter Workset state.

Each role invocation is its own Run and ACP session. In particular, a Writer Run
and its Reviewer Run never share one session or context, preserving the invariant
that one Run binds at most one worker.

### 12.5 Handoff and context model

OmnAI uses an orchestrator-worker plus evaluator pattern, not unconstrained Agent
group chat. Agents exchange no private reasoning transcript and do not hand control
directly to one another. Core passes only versioned, schema-validated artifacts:

- ContractCandidate;
- ProjectFinding;
- ContractResolution;
- ProjectTestCaseProposal;
- RunPacket;
- WorkerResult;
- ReviewFinding; and
- VerificationEvidence.

This preserves context isolation, bounds tokens, makes retries repeatable, and lets
Core reject malformed or stale handoffs. Agent prose can accompany an artifact for
humans, but prose alone cannot advance workflow state.

ACP transports prompts and session events; it does not define OmnAI's domain-result
schemas. A Run Packet instructs the Agent to write its result to a Run-owned output
path or return an equivalent structured payload. Core parses that payload with Zod,
checks its Run ID and packet hash, and records it as an artifact before accepting
the Agent's terminal response.

### 12.6 Permissions and containment

When an ACP Agent requests permission, Core evaluates the request against the
immutable Run Packet. Safe actions explicitly authorized by the packet are approved
automatically. Out-of-scope paths, unauthorized network access, final Git commits,
Claim changes, Workset mutations, and nested OmnAI execution are denied
automatically. An unclear request is denied and converted into a structured blocker;
it is not repeatedly shown to a human.

The working directory and any additional ACP workspace roots are explicit absolute
paths. ACP is an interoperability protocol, not a sandbox, so permission prompts
alone are insufficient containment.

Coordination and review Runs receive disposable materialized source snapshots, not
writable project worktrees. A Reviewer snapshot captures the exact post-Writer tree
and diff hash while the Writer Claim remains held. Their output directory is
separate from those inputs. Writer Runs receive only the claimed project worktree
plus explicitly materialized read-only contract artifacts and one separate writable
Run output directory. Their Agent profile must name an enforceable isolation mode,
supplied by the Agent host or an OmnAI process sandbox, that prevents filesystem and
terminal access outside the effective roots. A profile that cannot prove writer
isolation is ineligible for autonomous write Runs.

Core still validates source-snapshot hashes and the resulting Git diff because
runtime containment is defense in depth, not proof of business or policy
compliance.

### 12.7 Native fallback

A host without ACP support may use a Native Adapter. The Adapter must implement the
Core session wrapper from section 11.2, preserve one-session-per-Run semantics,
normalize events and results into the same schemas, obey the same permission model,
and pass the same conformance suite. Native Adapters are compatibility code, not a
second orchestration architecture.

### 12.8 v0.3 delivery

v0.3 delivers:

- `@agentclientprotocol/sdk` integration and one Core ACP Client;
- a deterministic Fake ACP Agent used in ordinary tests;
- ACP compatibility and OmnAI role-conformance tests;
- discovery of configured ACP Agents and optional ACP Registry metadata;
- production release validation through the Codex ACP adapter; and
- the Native Adapter extension point and conformance harness, without requiring a
  second production Native Adapter.

Existing host manifests under `~/.omnai/hosts/` gain non-secret Agent command,
protocol, capacity, role, and capability state. Authentication and credentials
remain owned by the Agent host and are never copied into OmnAI state. A normal Run
may select another already configured, compatible Agent automatically; installing
or authenticating a missing external Agent remains an explicit external action.

Run Packets and persisted ACP session records contain logical MCP server IDs and
secret references, never resolved credential values. Core resolves credentials
only in memory at process launch and redacts them from normalized ACP events, logs,
diagnostics, and evidence.

### 12.9 Protocol boundaries

- **ACP** connects OmnAI to local coding Agents and is required by the primary v0.3
  path.
- **MCP** supplies bounded tools and data to an Agent through its ACP session; it
  does not schedule Runs.
- **A2A** is reserved for future independently hosted remote Agent services; v0.3
  does not create a peer-to-peer Agent network.
- **AG-UI** may later expose Run events and human interaction in the management UI;
  it is not Core execution state.

## 13. End-to-end execution

The normal user action is:

```text
omnai run
```

The command resolves the current Workset and performs the following loop:

1. inspect Workset, project, worktree, Change, Git, host, Claim, and unfinished Run
   state;
2. recover an interrupted execution before creating new work;
3. run the Contract Planner and parallel Project Critics, invoke the Resolver only
   for resolvable conflicts, and generate or revalidate the ContractSnapshot;
4. run or recover one read-only Project Test Planner per affected project, then
   have Core validate and persist its scoped, content-addressed project TestCases;
5. derive cross-project cases and compile or revalidate the immutable
   VerificationPlan against a resolved immutable environment-profile snapshot;
6. calculate the Ready Set and persist one Wave;
7. acquire one Writer Claim per selected project;
8. record each starting Git HEAD and create immutable Run Packets;
9. start isolated ACP Agent sessions, or conforming Native fallback sessions, up to
   configured and proven capacity;
10. monitor process liveness, ACP events, structured outcomes, and signals;
11. create one read-only Reviewer child Run for each finished Writer Run, accept or
   recover its findings, reconstruct the test-only tree and prove RED, verify the
   full candidate tree GREEN, create the final project commit with a proven
   metadata-only delta, and update project evidence and task state;
12. release Claims and record commit, commitTree, verifiedTree, and
   metadataDeltaHash in the active CommitSet;
13. preserve successful work and recover or replan failed work;
14. after all required members integrate, move the CommitSet to `VERIFYING`, freeze
   the exact commit/commitTree/verifiedTree/metadataDelta tuple, and execute each
   required IntegrationEnvironmentRun;
15. accept per-case evidence, collect diagnostics, and prove safe teardown or lease
   release; and
16. complete the CommitSet only when all exact-tuple gates pass, otherwise recover
   affected work or surface one precise external decision.

No normal user-facing `prepare`, `claim`, `finish`, or `resume` command is required.
Running `omnai run` again resumes persisted state.

## 14. Core-owned commit model

The dedicated project requirement worktree is clean at Run start. Core records its
HEAD, then grants the Writer Claim. The worker edits and tests but does not create
the final commit.

After `finish`, Core checks:

- the requirement branch and starting HEAD are unchanged except for authorized
  work;
- changed paths are a subset of `allowedPaths`;
- no unexpected commit was created;
- every project-relevant scoped TestCaseRef in the frozen VerificationPlan is
  mapped to the exact test paths and commands used below;
- the required Reviewer Run is ACCEPTED with no unresolved blocking finding;
- ContractSnapshot and VerificationPlan IDs and hashes still match;
- the child Change, Revision, Baseline, and task are still current; and
- no invalidating signal arrived.

Core never accepts “tests were written first” from Agent prose. For every required
behavioral case it reconstructs a detached `testOnlyTree` from the starting tree
plus only the Writer's authorized test/fixture/test-harness delta and runs the
frozen case command. Acceptance requires the intended behavior assertion to be
`RED`; compilation, missing dependency, infrastructure, or unrelated failures do
not qualify. Core then reconstructs the exact full authorized candidate as
`verifiedTree` and independently requires `GREEN` build, project, contract, and
policy evidence bound to that tree.

Only after GREEN may Core update project-owned `.omnai` task, progress, and evidence
metadata. It creates the standardized official commit and records:

- `commit` — official commit SHA;
- `commitTree` — the official commit's Git tree;
- `verifiedTree` — the exact pre-metadata tree on which GREEN evidence ran; and
- `metadataDeltaHash` — canonical binary delta from `verifiedTree` to `commitTree`.

Core proves every path in that delta is an authorized Core-owned `.omnai` metadata
path, that no production/test/executor byte differs, and that the recorded
task/evidence updates refer to the same Run, plan, cases, and verified tree. A
non-metadata difference invalidates verification and blocks the commit. Commit
trailers include Change, Task, Run, ContractSnapshot, VerificationPlan, scoped
TestCaseRefs, evidence, `verifiedTree`, and `metadataDeltaHash`.

If a worker creates an unexpected commit, Core preserves it under a quarantine ref,
restores the dedicated requirement branch to the recorded starting HEAD, and
validates the preserved content before creating an official commit. No commit is
deleted.

CommitSet lifecycle is:

```text
OPEN -> PARTIAL -> VERIFYING -> COMPLETE
          ^          |           |
          +----------+           +-> NEEDS_REVALIDATION
                     +-> NEEDS_REVALIDATION

NEEDS_REVALIDATION -> PARTIAL | VERIFYING
```

Successful project commits are retained immediately. A failed project is diagnosed,
retried, or replanned without rerunning successful unrelated projects. Later commits
join the same CommitSet when they satisfy its current contract and evidence rules.

Recording the first integrated or failed member always persists `OPEN -> PARTIAL`.
When every required member is `INTEGRATED`, the set then enters `VERIFYING` from
`PARTIAL`; even a single-member or atomically recovered set may not skip that
durable intermediate state. A project or contract failure attributable to one or more members
returns those members to targeted recovery while retaining unrelated commits. An
infrastructure failure retries the environment within policy without blaming code.

Changing a contract, plan, profile, policy, or member identity after completion
moves `COMPLETE` to `NEEDS_REVALIDATION`. Fresh compatibility evidence may preserve
unchanged project commits, but the set must re-enter `VERIFYING` and obtain a new
authoritative environment Run for the current exact tuple before it can complete
again.

No invalidation path jumps from `COMPLETE` directly to `VERIFYING` or back to
`COMPLETE`: it is always durably `COMPLETE -> NEEDS_REVALIDATION -> VERIFYING ->
COMPLETE` when lower-layer work remains acceptable. If project repair is required,
`NEEDS_REVALIDATION -> PARTIAL` precedes a later `VERIFYING` transition.

`COMPLETE` is legal only when Core proves in one lock-protected transition that:

1. every required member has an official reachable commit whose exact SHA,
   `commitTree`, `verifiedTree`, `metadataDeltaHash`, and trailers match the
   CommitSet; project verification evidence binds `verifiedTree`, and Core has
   proven the only `verifiedTree -> commitTree` differences are authorized metadata;
2. the VerificationPlan, tasks/Revisions, and ContractSnapshot refs are current,
   or accepted fresh compatibility evidence covers every divergence;
3. all required project-local and provider/consumer contract TestCases pass
   against each current member `verifiedTree`, with required behavioral cases also
   carrying valid test-only-tree RED evidence;
4. every required integration gate has one `PASSED` IntegrationEnvironmentRun
   whose input tuple exactly matches the current CommitSet scope, all member
   commits/`commitTree`s, plan hash, contract hashes, profile/definition hash, and
   executor/supporting/external artifact digests;
5. every required integration/E2E case is `PASS`, with no unauthorized skip or
   missing artifact; and
6. required evidence collection and resource teardown or external lease release
   are proven complete.

Risk policy may record an immutable `NOT_REQUIRED` integration gate for a genuinely
single-project, local-only change. Multi-project, API-contract, MQ, or remote-service
scope requires the gate by default. If any member commit, contract, plan, or profile
changes, the prior environment evidence no longer matches. Unchanged lower-layer
evidence may be reused only when its input hash is identical; a new authoritative
multi-service Run is required for the new complete tuple.

CommitSet remains local coordination metadata. It does not imply atomic commit,
merge, release, or rollback across repositories.

## 16. Contract and intent changes during execution

Core checks contract sources before dispatch, during orchestration checkpoints, and
before integration. A changed source never mutates the packet of an active Run.

The recovery flow is:

1. preserve the old immutable snapshot;
2. generate and validate a new snapshot;
3. compare old and new content and business scenarios;
4. identify every referencing task and Run;
5. classify the change as compatible, incompatible, or unresolved;
6. automatically revalidate compatible work;
7. preserve existing diffs or commits and create targeted repair Runs for
   incompatible work; and
8. ask one human question only if available facts do not determine the intended
   behavior.

Unrelated workers continue. A successful commit built against an old snapshot is
not deleted; it becomes `NEEDS_REVALIDATION` until evidence proves compatibility
with the current snapshot. A changed contract, TestCase, task Revision,
VerificationPlan, environment profile, or member commit invalidates every
environment result whose exact input tuple no longer matches; it never mutates or
deletes the historical Run.

For each normalized `contractKey` and coordination `scopeHash`, all applicable
members of a COMPLETE CommitSet must use one exact current ContractSnapshot or have
explicit fresh compatibility evidence accepted by policy. One CommitSet may
legitimately contain multiple different contract keys and therefore multiple exact
snapshots; consistency is enforced within each key/scope, not by forcing the whole
Workset onto one snapshot.

## 17. Error handling and recovery

### 17.1 Invalid or incomplete contract

The Contract Coordinator retries synthesis with validation and critic evidence. No
write Wave starts until the required snapshot is READY. Repeated conflicting but
equally valid business choices become one `NEEDS_DECISION` item rather than a broad
manual review.

### 17.2 Agent start failure

Core probes installation, authentication, ACP version, and capability state,
retries with the same Run ID, attempts `session/resume` or `session/load`, and may
select another configured compatible Agent only after proving that no prior session
can still perform work. It asks the user only when installation, login, credentials,
or another external authority is required.

### 17.3 Lost worker or CLI interruption

Core inspects persisted ACP session IDs, negotiated capabilities, session events,
local processes, Git state, and stored results. A live session is reconnected. A
dead worker with a recoverable diff receives a recovery Run. A dead worker with no
work is restarted from the original packet. An uncertain writer retains its Claim.

### 17.4 Forbidden path change

Core saves the complete diff and a recovery patch, records `POLICY_VIOLATION`, and
does not create an official commit. AI may determine that the design legitimately
requires broader impact and propose a new Revision and Run Packet. Otherwise the
recovery Run removes the unrelated edit and revalidates the allowed work.

### 17.5 Verification failure

A Run that fails its own result or evidence checks before acceptance enters
`RECOVERING`. A blocking finding from an ACCEPTED Reviewer Run leaves the original
Writer Run accepted but unintegrated and creates a linked `RECOVERY_WRITER` Run.
The repair worker receives the original packet, current diff, fresh test output,
evidence, review findings, and failure analysis. It retries without human
intervention when a bounded fix exists. The repaired result receives a new Reviewer
Run before integration.

### 17.6 Integration environment failure

An environment test assertion or contract mismatch produces `TEST_FAILED` and
routes the failed TestCases plus shared logs/evidence to Recovery Writers for their
declared owner projects. A build runtime, container engine, port, health dependency,
missing secret, or external lease failure is classified separately as
`INFRA_FAILED` or `BLOCKED`; it does not make a passing project commit failed.

Core always attempts redacted evidence collection followed by teardown. It resumes
an interrupted phase only when the same input hash, owned resources, and idempotent
step authority are proven. Otherwise it cleans the provably owned instance and
starts a new environment Run. Teardown failure becomes `CLEANUP_REQUIRED`; unknown
resource ownership becomes `SAFETY_UNPROVEN`. Both block CommitSet completion and
retain `primaryOutcome`. After ownership becomes provable, Core may transition
either state back to `TEARING_DOWN` and retry cleanup only with the same Run ID; it
must not rebuild, reseed, or rerun tests. Successful cleanup restores the preserved
primary terminal outcome. Unproven ownership never authorizes deletion.

### 17.7 Retry budget

The default is one initial attempt and two recovery attempts for the same error
fingerprint. A genuinely revised design, contract, or recovery strategy creates a
new correlated Run, but correlation history prevents superficial rewording from
causing an infinite loop.

After the budget:

- Core automatically reconciles to another evidence-backed strategy when one
  exists;
- missing business intent becomes `NEEDS_DECISION`;
- missing permission or local capability produces one precise external action; and
- unsafe or unprovable cleanup remains blocked.

### 17.8 Recovery invariants

- Original repository working copies are never mutated.
- Existing commits are never deleted.
- Uncommitted work is patched or otherwise preserved before cleanup.
- One repository never has two writers.
- One failed project does not stop unrelated projects.
- Core never treats worker confidence as verification evidence.
- Core never treats an environment result as authoritative unless its exact tuple,
  required per-case evidence, and cleanup state match current truth.
- Teardown never deletes a resource whose Run ownership is not proven.
- Safe, derivable work does not ask for human approval.

## 18. CLI and machine contracts

The public execution surface is intentionally small:

```text
omnai run [workset] [--agent <id>] [--max-workers <n>] [--json]
omnai run status [workset] [--json]
omnai run stop <execution-id> [--json]
omnai run doctor [--json]
```

`omnai run` also resumes. `status` explains current VerificationPlan coverage,
Wave, Runs, Claims, recovery, CommitSet, integration-gate, environment phase,
service-health, failed TestCase, evidence, cleanup, and attention state, and returns
the exact active `execution-id`. `stop` requires that ID; it never guesses “the
current run” from cwd or Workset alone, and it rejects stale or cross-Workset IDs.
It records stop intent for that execution, requests cancellation and safe session
close for its active child Runs, or the equivalent Native Adapter action. Stopping
an environment Run sends cancellation through its AbortSignal, kills the owned
process/container tree, then still collects evidence and tears down owned
resources. Neither stop path silently steals a Claim or lease.

`doctor` checks Git, worktrees, state schemas, claims, ACP compatibility, Agent
availability, authentication, capabilities, configured capacity, stale TestCases
or VerificationPlans, user-owned profile bootstrap/current snapshot hashes,
definition/executor/supporting/external artifact digests, proven command sandbox,
normalized Compose deny-policy results, container/runtime availability, port
reservation conflicts, missing environment-reference names, external lease
ambiguity, cleanup-only retry state, and leaked provably owned resources. JSON and
human output contain no secret values or unsafe raw command output.

Human-facing host skills hide these details and normally invoke JSON output. OmnAI
does not add a chat UI.

verification, Git commit, immediately before CommitSet update, and after every
durable integration-environment phase fact. Re-running `omnai run` must not

evidence record, Claim, or destructive teardown. Recovery must converge to exact
resume or safe cleanup plus a new environment Run.

## 21. Compatibility and migration

Existing Worksets remain schema-valid without an `execution/` directory. v0.3 lazily
creates execution state only when execution is requested. It does not reinterpret
existing project task dependencies as cross-project relationships.

Existing project verification commands remain valid inputs. Core assigns stable
command references when it compiles a VerificationPlan, but required test coverage
cannot be inferred from a generic PASS. Existing Changes without `test-cases.yaml`
are not manually migrated: read-only Project Test Planner Runs propose cases and
Core persists them only after source/coverage validation. Existing tasks are not
rewritten with bare refs; coverage is expressed solely by each accepted case's
`scopedTasks`. Existing Worksets without an integration profile are bootstrapped
from safely discoverable user-owned configuration into a reviewable draft; only a
resolved, content-addressed execution snapshot can enter a READY plan. A genuinely
local-only existing Workset may
receive a policy-evidenced `NOT_REQUIRED` integration gate. A cross-service Workset
without a resolvable isolated environment profile remains valid to inspect but is
blocked from `CommitSet COMPLETE` with one precise configuration or external
authority action; OmnAI never silently treats a shared mutable endpoint as proof.

The existing v0.2 Milestone C prose is documentation history, but this approved
specification is authoritative for v0.3 implementation. Implementation work must
update user-facing architecture, README, scenario, and roadmap text that still
describes cross-project implementation dependency blocking or manual host-assisted
dispatch.

`omnai run` and the `omnai-run` host skill remain unavailable until all execution
legality primitives required by this design exist and their acceptance tests pass.

## 22. Final invariants

1. AI reasons; Core authorizes and records.
2. Shared contracts coordinate repositories; repositories do not depend on one
   another's implementation completion.
3. A Run consumes immutable project, contract, VerificationPlan, and scoped,
   content-addressed TestCase truth; `TestCase.scopedTasks` alone owns task coverage.
4. One repository has at most one writer.
5. One Run binds at most one Agent session and starts at most one worker.
6. Worker completion is a claim; Core evidence makes it accepted completion.
7. Core proves test-only RED and final verified-tree GREEN where required, creates
   official project commits, and proves their tree difference is metadata-only.
8. Successful unrelated work survives partial failure.
9. Contract, test, plan, profile-definition, executor/artifact, and commit/tree
   changes create new immutable inputs and targeted revalidation; an invalidated
   COMPLETE set passes through NEEDS_REVALIDATION before VERIFYING.
10. Unknown business intent is surfaced precisely; known work stays autonomous.
11. Original repositories and existing commits are preserved.
12. CommitSet coordinates commits but never pretends cross-repository Git is atomic.
13. A multi-project result is complete only when real services pass required cases
    against the exact current tuple and owned resources are safely released.
14. Environment commands never own lifecycle state, broaden credentials, escape a
    proven sandbox, or delete resources whose Run ownership is unproven; diagnostic
    execution can never satisfy an authoritative gate.
15. ACP standardizes coding-Agent sessions; OmnAI adds policy rather than a competing
    wire protocol.
16. Agents exchange structured artifacts through Core and never transfer authority
    directly to one another.

## 23. Industry references and reuse decisions

This section records which established systems OmnAI directly adopts, which ideas
it borrows, and which runtimes it deliberately does not embed in v0.3.

### 23.1 Local lifecycle and durable execution

- **XState v5 — direct dependency for transition logic.** XState provides
  TypeScript state machines, statecharts, and actors. OmnAI uses machine definitions
  to make legal Wave, Run, Claim, ContractSnapshot, IntegrationEnvironmentRun, and
  CommitSet transitions explicit. It does not persist raw actor snapshots as domain
  truth because OmnAI requires stable, independently versioned Zod schemas and
  auditable event records.
  References: [XState](https://stately.ai/docs/xstate) and
  [persistence](https://stately.ai/docs/persistence).
- **Temporal, Restate, and DBOS — semantic reference and future backend options.**
  OmnAI borrows durable execution boundaries, append-only history, idempotent
  side-effecting activities, targeted retry, and resume semantics. v0.3 does not
  embed these runtimes because Temporal and Restate add a service, while DBOS adds
  database-backed execution, conflicting with the approved zero-server,
  zero-database local CLI scope. References:
  [Temporal](https://docs.temporal.io/),
  [Temporal retry policy](https://github.com/temporalio/documentation/blob/main/docs/encyclopedia/retry-policies.mdx),
  [Restate](https://docs.restate.dev/), and
  [DBOS architecture](https://docs.dbos.dev/architecture).
- **BullMQ, Argo Workflows, and Airflow — not Core dependencies.** BullMQ supplies a
  Redis-backed queue; Argo schedules Kubernetes workflows; Airflow expects a
  persistent scheduling service and DAG-oriented deployment. They are useful future
  distributed backends or operational references, but they do not own OmnAI's Git,
  contract, Claim, or CommitSet rules. References:
  [BullMQ](https://docs.bullmq.io/),
  [Argo Workflows](https://argoproj.github.io/argo-workflows/), and
  [Airflow Scheduler](https://airflow.apache.org/docs/apache-airflow/stable/concepts/scheduler.html).

### 23.2 Coding-Agent interoperability and orchestration

- **ACP v1 — directly adopted.** ACP already standardizes local coding-Agent
  subprocesses, JSON-RPC communication, session lifecycle, prompts, progress,
  permissions, cancellation, filesystem and terminal requests, MCP injection, and
  capability negotiation. OmnAI is an ACP Client and uses the official TypeScript
  SDK. The ACP ecosystem already exposes Codex CLI, Claude Agent, OpenCode,
  OpenHands, Goose, Hermes, and other Agents, natively or through adapters.
  References: [ACP introduction](https://agentclientprotocol.com/get-started/introduction),
  [ACP v1](https://agentclientprotocol.com/protocol/v1/overview),
  [TypeScript SDK](https://agentclientprotocol.com/libraries/typescript), and
  [Agent registry](https://agentclientprotocol.com/get-started/agents).
- **LangGraph, Microsoft Agent Framework, CrewAI, and Mastra — pattern references,
  not Core runtimes.** OmnAI borrows supervisor/subagent, concurrent, router,
  evaluator, handoff, checkpoint, and structured workflow ideas. Embedding one of
  these would create a second lifecycle and persistence authority beside XState and
  OmnAI domain files. Microsoft Agent Framework also targets Python and .NET;
  AutoGen is now in maintenance mode. Mastra is the closest TypeScript alternative
  and may be evaluated for a future optional AI subflow, but v0.3 does not require
  its storage or Agent abstraction. References:
  [LangGraph multi-agent patterns](https://docs.langchain.com/oss/javascript/langchain/multi-agent),
  [Microsoft Agent Framework](https://learn.microsoft.com/en-us/agent-framework/overview/),
  [CrewAI](https://docs.crewai.com/),
  [Mastra workflows](https://mastra.ai/ai-workflows), and
  [AutoGen status](https://github.com/microsoft/autogen).
- **Planner, generator, and evaluator — adopted harness pattern.** Contract Planner,
  Project Writer, and Project Reviewer follow the evidence from long-running coding
  harnesses that use role separation and structured artifacts between sessions.
  OmnAI extends that pattern with per-project Critics, deterministic Core policy,
  real Git isolation, and contract evidence. Reference:
  [Anthropic long-running application harness](https://www.anthropic.com/engineering/harness-design-long-running-apps).

### 23.3 Protocol stack boundaries

- **MCP** equips one Agent with bounded tools and data; it is supplied through ACP
  session configuration and never becomes the scheduler.
- **A2A** is the future boundary for independent remote Agent services. It is not a
  subagent or tool-call protocol, so v0.3 does not use it for local workers.
- **AG-UI** is a future transport for management-UI events, shared UI state, and
  human interaction. It cannot become Core's execution source of truth.

References: [A2A protocol boundaries](https://a2a-protocol.org/dev/),
[A2A specification](https://a2a-protocol.org/dev/specification/), and
[AG-UI](https://docs.ag-ui.com/).

### 23.4 Contract verification ecosystem

- **Pact and Spring Cloud Contract — optional direct validators.** OmnAI's
  ContractSnapshot is broader than consumer-driven HTTP contracts, so neither tool
  owns the shared contract model. When detected in a project, their existing
  consumer/provider tests, brokers, generated stubs, and messaging verification can
  contribute executable `VerificationEvidence` through configured validation
  commands. References: [Pact Broker](https://docs.pact.io/pact_broker) and the
  [Spring Cloud Contract Stub Runner reference](https://docs.spring.io/spring-cloud-contract/reference/project-features-stubrunner.html).

### 23.5 Resulting reuse rule

OmnAI directly adopts standards or libraries only where they replace generic
infrastructure without taking ownership of OmnAI domain truth:

1. XState owns legal in-process transitions, not durable business records.
2. ACP owns coding-Agent communication, not task selection or authority.
3. Existing contract tools own their executable validators, not the cross-project
   ContractSnapshot.
4. Docker Compose, project commands, and enterprise adapters own only their declared
   environment operations, not test-case meaning or completion authority.
5. OmnAI Core alone owns Run legality, Writer Claims, VerificationPlans, evidence
   acceptance, environment lifecycle, Git commits, recovery decisions, and
   CommitSets.

## 24. Implementation slices

Milestone C is one coherent execution feature, but the implementation plan must use
four ordered, independently testable slices. Later slices may not bypass an earlier
slice's acceptance tests.

1. **C1 — lifecycle and Agent substrate:** XState machine definitions, versioned
   domain state and event persistence, LocalExecutionBackend, ACP Client, Fake ACP
   Agent, Agent profiles, session recovery, and conformance tests.
2. **C2 — contract coordination:** Run kinds and artifacts for Contract Planner,
   Project Critics, Resolver, ContractSnapshot generation, validator integration,
   TestCase traceability, VerificationPlan readiness, compatibility classification,
   and business-decision escalation.
3. **C3 — parallel project execution:** deterministic Ready Set and Waves, Writer
   Claims, Writer and Reviewer Runs, permission and isolation policy, Core-owned
   per-case verification and commit, partial/VERIFYING CommitSets, exact-tuple
   IntegrationEnvironmentRuns, Docker Compose/custom/external adapter boundaries,
   safe environment recovery, and targeted repair Runs.
4. **C4 — hardening and release certification:** fault injection, package tests,
   three-repository real-service golden scenario, environment-phase and cleanup
   recovery, contract/plan/profile change invalidation, documentation migration,
   and authenticated Codex ACP release validation.

The public `omnai run` command is not declared production-ready until all four
slices pass. The implementation plan may land internal commits per slice, but it
must preserve existing v0.2 behavior after every slice.

### 24.1 Test-flow policy implementation note (2026-08-20)

The pure policy portion of TestCase/VerificationPlan compilation, Wave/Writer
entry checking, and exact transitive invalidation is specified in
`docs/superpowers/specs/2026-08-20-omnai-test-flow-optimization-design.md`. Its
source and focused tests currently form an isolated implementation handoff under
`src/execution/verification/`; they do not advance C2 or C3 until committed,
reviewed, and called from the authoritative C1-C3 services.

This additive slice deliberately leaves persisted v1 schemas readable and does
not claim C2 or C3 completion. `PROJECT_TEST_PLANNER` remains read-only; Core is
still the only authority that may validate cases, mark a plan READY, dispatch a
Wave, acquire a Writer Claim, mark a Run stale, or move a CommitSet through
`NEEDS_REVALIDATION`. The F4/C2-C3 integration work must call these pure gates at
the corresponding event-store boundaries and must not reimplement their policy
inside an Agent prompt.

Adversarial coverage is specified separately in
`docs/superpowers/specs/2026-08-20-omnai-adversarial-test-coverage-design.md`.
It is an orthogonal TestCase purpose and a VerificationPlan readiness floor, not
a new test level, write-capable Agent, aggregate, ledger, or scheduler. The
canonical case/plan/gate/closure policy remains the sole implementation that
Tasks 5-22 and F4/F5 may call at their authority boundaries.
