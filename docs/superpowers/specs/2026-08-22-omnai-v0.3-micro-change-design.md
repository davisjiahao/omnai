# OmnAI v0.3 `micro-change` 轻量通道设计

- **状态：** 设计讨论已批准，待书面规格审阅
- **日期：** 2026-08-22
- **分支：** `feat/omnai-v0.3-full-pipeline-fusion`
- **基线：** `39f295bc858ae1bcc5f82a8a38025db9ff431a50`
- **前置依赖：** `2026-08-22-omnai-v0.3-change-authority-integrity-repair-design.md`

## 1. 结论

新增原生 v0.3 场景 `micro-change`，用于低风险、单项目、单模块、单任务的局部变更。固定路线为：

```text
plan -> work -> verify -> archive
```

Agent 先进行只读评估并推荐，用户确认一次后，Core 独立复核并创建 Change。正常路径由 Agent 连续推进，不要求用户逐阶段确认。轻量化只减少交互、阶段和人工产物，不降低写入权限、验证、对抗性测试和审计要求。

`micro-change` 复用现有 `plan`、`work`、`verify`、`archive` Capability 和 Host Skill，不新增 `micro` Capability，不保留 v0.2 别名或兼容路径。

## 2. 背景与目标

当前 `small-feature` 需要 `spec -> design -> plan -> work -> verify -> archive`。对于改一处局部行为、补一组测试或修正文档，这六个阶段和多份产物明显偏重。

本设计目标是：

1. 正常路径只需要一次用户确认。
2. 将必需阶段从六个降为四个。
3. 只保留 `intent.md`、`tasks.yaml` 两份主要人工可读产物。
4. 允许局部前端或后端行为、测试、文档及非生产配置变更。
5. 通过严格准入、路径写入门禁、完成差异复检和新鲜证据维持生产安全下限。
6. 发现范围扩大或风险上升时，自动升级到更完整场景，而不是继续放宽轻量通道。

非目标：

- 不处理 Bug、事故、发布、迁移、重构或删除操作。
- 不支持跨项目、跨模块、多任务或契约变更。
- 不新增一套独立工作流运行时。
- 不用固定文件数量代替影响范围判断。
- 不为 v0.2 或中间态 v0.3 增加迁移、别名、双读或回退逻辑。

## 3. 方案选择

采用独立场景，而不是动态裁剪 `small-feature`：

- 独立场景的路线、准入、安全下限和证据要求都能进入权限目录并参与哈希，结果确定且可审计。
- 动态裁剪会使同一个场景每次拥有不同必需阶段，增加恢复、审计和升级复杂度。
- 新增专用 Capability 虽然能缩短表面命令，但会扩大协议、权限、适配器和测试面，违背轻量目标。

## 4. 信任边界与组件职责

### 4.1 Agent 推荐层

Agent 只能读取需求、仓库基线和影响信息，输出结构化推荐、匹配理由、未满足规则及建议场景。Agent 不能直接将 `eligible` 布尔值作为 Core 权限依据，也不能声明豁免项。

### 4.2 Core 准入编译器

Core 使用已锁定的场景目录、基线和结构化评估重新计算准入结果。任何字段缺失、未知、冲突或计算异常都按不准入处理。准入编译器必须是纯函数，其规则和实现资源纳入 `authorityCatalogHash`。

Core 生成的推荐记录至少冻结：规范化需求、非目标与验收标准及其摘要、变更类型、项目与模块、允许路径与操作、风险与影响、不确定性、仓库基线、权限目录摘要、准入结论、失败规则和目标场景。Agent 可以提出候选事实，但这些字段的规范化、完整性检查和最终结论只能由 Core 产生。

### 4.3 用户确认边界

只有 Host 的交互确认接口或交互式 CLI 才能生成用户确认记录。非交互调用方不能通过传入普通布尔值伪造确认。确认绑定推荐摘要、需求摘要、仓库基线和权限目录摘要；任一绑定发生变化，确认即失效。

### 4.4 既有流程运行时

确认后继续使用现有 Scenario、Flow、Run、Writer Claim、Evidence、Revision、Reconcile 和 Archive 机制。`micro-change` 只是目录中的新场景，不创建第二个调度器或状态机。

### 4.5 漂移与升级守卫

Core 在创建、开始工作、完成工作、验证和归档前重新检查准入条件及实际差异。越界时立即停止写入、撤销 Writer Claim，并进入场景重分类。

## 5. 场景目录定义

`micro-change` 的目录语义如下：

| 字段 | 值 |
| --- | --- |
| `id` | `micro-change` |
| `workMode` | `FEATURE` |
| `routeOrder` / `stages` | `plan, work, verify, archive` |
| `optionalStages` | 空 |
| `requiredArtifacts` | `intent.md` |
| `requiredMachineState` | `TASKFILE` |
| `requiredEvidence` | `micro-scope-review`, `micro-adversarial-check` |
| `risk` | `P3` |
| 新增 Capability | 无 |
| 新增 Host Skill | 无 |

风险维度默认为 `LOW`，影响默认全部为 `false`；准入评估可以将 `frontend` 或 `backend` 设为 `true`，其余禁止影响必须保持 `false`。

### 5.1 `intent.md`

`intent.md` 记录精简需求、明确的非目标和可观察验收标准。为避免绕过 Artifact Authority，Agent 不得在 Change 发布后任意改写它。

创建事务从已冻结的推荐与用户确认内容生成完整 `intent.md`；`plan` 将其哈希作为任务来源并再次校验其完整性。这样仍由 `plan` 固化需求与验收标准，但不增加 `frame` 阶段。

实现时复用权限目录中已有的 `intent.md` Artifact Authority 条目和创建发布编译器，不增加第十七个静态 Artifact 条目。创建编译器增加受目录约束的 micro 渲染分支，从冻结的确认内容产生目标字节；`plan` 只能读取并绑定该哈希，不能获得任意改写 `intent.md` 的权限。

### 5.2 `tasks.yaml`

`plan` 只允许生成一个严格 Task：

- ID 必须为 `TASK-001`。
- `dependsOn` 必须为空。
- 风险只能为 `LOW` 或 `MEDIUM`。
- 只能声明新增、修改和测试路径。
- 必须包含目标、步骤、验证要求和允许路径。
- `generatedFrom` 必须包含当前 `intent.md` 的权威来源引用。

这里的 Task `MEDIUM` 只表示局部实施复杂度；如果它来自安全、兼容、数据、运行或业务影响，Change 已不满足全部风险维度为 `LOW`，必须拒绝或升级。

Run 仍通过绑定的任务草稿完成 CAS 导入，Agent 不得直接写机器拥有的 `tasks.yaml`。

不创建 `research.md`、`domain.md`、`spec.md` 或 `design.md`。运行记录、证据、Revision、Flow 和归档清单属于机器状态，不计入主要人工产物数量。

## 6. 准入规则

### 6.1 必须全部满足

1. 风险等级为 `P3`，所有风险维度均为 `LOW`。
2. 所有不确定性均为 `CLEAR`，不存在阻塞决策。
3. 需求、非目标和验收标准已经明确。
4. 只涉及一个项目、一个模块和一个独立目标。
5. 计划恰好包含一个任务且没有依赖。
6. 变更类型只能是局部行为、仅测试、仅文档或非生产配置。
7. 操作只能是新增或修改。
8. 允许路径必须规范化、位于仓库内并排除 `.git`、`.omnai` 及符号链接逃逸。
9. 基线可以稳定封存；已有差异必须拥有明确归属并完全落在允许路径中。
10. 项目必须存在可执行且可取证的匹配验证配置。

局部行为可以是前端或后端，但不能跨越模块、接口或运行边界。准入不设置固定的最大文件数，因为文件数量不能可靠表示风险；以单模块、单任务、允许路径和实际差异复检共同限制范围。

### 6.2 任一出现即不准入

- API、数据库、数据迁移、MQ、远程服务或跨模块契约变化。
- 安全、权限、隐私、可观测性、生产配置、部署、基础设施或运行操作变化。
- Bug 修复、事故处理、发布、迁移、重构、删除或重命名。
- 跨项目、跨模块、多目标、多任务或任务依赖。
- 需求、影响、所有权、测试方式或验收标准存在未知项。
- 需要研究、领域建模、规格、设计、评审决策、上线或 Canary 才能安全完成。

简单 Bug 也必须进入 `bug-fix`，不能因改动文件少而伪装为 `micro-change`。

## 7. 正常运行流程

### 7.1 推荐与创建

1. Agent 执行只读仓库与影响分析。
2. Core 编译推荐结果并返回准入结论、理由、绑定摘要和建议场景。
3. Agent 向用户展示 `micro-change` 推荐及排除项。
4. 用户确认一次。
5. Core 重新验证基线、目录摘要和准入规则，再创建 Change；推荐与确认摘要先冻结到 `ProjectCreationRecord`，并在发布时写入 Change `Genesis`。

用户确认不是风险豁免。即使用户确认，只要 Core 复核失败，也不得创建 `micro-change`。

### 7.2 `plan`

- 校验确认记录、`intent.md`、当前 Revision 和基线仍然一致。
- 生成并严格解析唯一任务草稿。
- 校验任务路径、操作、风险和验证配置满足 micro 规则。
- 原子导入 `tasks.yaml` 并封存本 Revision 的计划权威。

### 7.3 `work`

- 只为 `TASK-001` 和声明路径签发 Writer Claim。
- 每次开始或恢复前检查基线、权限头和 Run 绑定。
- 写入层拒绝未声明路径、删除、重命名、路径穿越和符号链接逃逸。
- 完成时以实际仓库差异为准重新检查模块、路径、操作和影响，不能只相信任务声明。

### 7.4 `verify`

- 根据冻结的变更类型选择目录中的验证配置。
- 运行独立代码审查、编译或构建、目标测试及对抗性测试。
- 所有证据必须绑定当前 Change、Revision、任务、基线、Run 和权限摘要。
- 验证后再次读取实际差异；代码发生变化时，旧证据立即失效。

### 7.5 `archive`

只有以下条件全部满足才能归档：

- 唯一任务已完成且实际差异仍满足准入规则。
- 所有必需证据均为当前 Revision 的新鲜 `PASS`。
- 不存在未解决 Decision、Issue、漂移或待处理 Writer Claim。
- 权限链、审计顺序和归档目标全部一致。

`--force` 不得绕过 `micro-change` 的写入、验证或归档门禁。

## 8. 验证配置与后台执行

| 变更类型 | Task 必需证据 | 最小验证配置 |
| --- | --- | --- |
| 局部代码行为 | `build`, `tests` | 模块编译或构建、目标测试、负向/边界测试、独立代码审查 |
| 仅测试 | `tests`, `test-effectiveness` | 测试编译、目标测试、证明测试有效性的对抗检查、差异审查 |
| 仅文档 | `docs-check` | 格式、链接或文档构建检查、差异审查 |
| 非生产配置 | `config-validation`, `tests` | 语法或 Schema 校验、相关配置/启动测试、非法配置负向测试 |

场景固定要求 `micro-scope-review` 和 `micro-adversarial-check`；Task 再按上表声明类型相关证据。`plan` 必须校验其集合精确相等，不能少报或自定义弱化。新增证据 ID、生产者、类型、作用域和满足状态都必须进入 Stage Authority Catalog。

`micro-scope-review` 是绑定 `verify` Run 的独立审查证据，不激活 `review` Capability 或 Readiness；因此逻辑路线仍严格保持四个阶段。

进入代码审查、编译和测试流程时，由后台子 Agent 分别执行；互相独立的流程并行，有依赖的流程按顺序执行。每个子 Agent 必须返回执行状态、关键命令与环境、退出码、输出摘要、失败原因和可复现证据。正常路径不因此增加用户确认次数。

相对远程主干新增或修改的测试文件必须位于对应模块的 `test` 目录。

证据不能通过通用写文件接口自报 `PASS`。Core 只接受受信验证适配器或受约束的结果导入产生的记录，并校验真实命令、退出码、输出内容哈希和 Run 绑定。

## 9. 自动升级与恢复

### 9.1 触发条件

以下任一情况触发自动升级：

- 实际差异超出任务路径或单模块边界。
- 出现删除、重命名、契约、数据、远程、安全、生产或运行影响。
- 单任务拆分为多个任务，或出现任务依赖。
- 需求、验收标准、风险等级或变更性质发生变化。
- 实现或验证发现本质上属于 Bug、重构、迁移、事故或发布工作。

### 9.2 升级行为

1. 立即停止当前写入并撤销 Writer Claim。
2. 保留原 `ChangeId`，创建新 Revision，并记录触发事实与目标场景。
3. 使受影响的计划、任务、Run 和验证证据变为失效状态。
4. 根据语义重分类到 `small-feature`、`bug-fix` 或其他匹配场景。
5. 从新路线第一个尚未完成的必需阶段继续。
6. 无法唯一确定目标场景时进入 `BLOCKED`，等待补充信息。

仍然有效的需求事实和历史记录可以保留，但不能把过期计划或证据当作新 Revision 的通过依据。升级后不得自动降回 `micro-change`。

### 9.3 错误语义

- 准入未知或失败：拒绝创建，返回不满足的规则及推荐场景。
- 推荐绑定过期：要求重新进行只读评估和一次确认。
- 工作差异越界：停止写入并启动重分类，不继续原 Run。
- 普通验证失败：停留在 `verify`；若失败暴露范围或需求变化，再升级场景。
- 命令异常、超时或证据缺失：不得记为通过。
- 恢复时状态与冻结意图不一致：无写入失败，不能自动修补。

## 10. 安全、审计与可观测性

`micro-change` 必须建立在最终原生 v0.3 权限完整性修复之上：

- 场景 Profile、准入规则、证据模板、验证配置和编译资源进入锁定权限目录。
- 推荐与确认在发布前冻结到 `ProjectCreationRecord`，发布后由 `Genesis` 绑定；创建、阶段完成、升级和归档进入同一 Change 权限链。
- 所有读取和写入使用同一 Change 锁与认证上下文。
- 实际路径必须经过仓库包含、节点类型和符号链接检查。
- 任何未知字段、目录漂移、权限摘要变化或恢复冲突均失败关闭。

至少记录以下结构化事件。推荐、确认和拒绝属于 Host 交互审计，不得在被拒绝的仓库中产生持久化写入；其余事件属于 Change 权限审计：

- `MICRO_RECOMMENDED`
- `MICRO_CONFIRMED`
- `MICRO_CREATED`
- `MICRO_ELIGIBILITY_REJECTED`
- `MICRO_SCOPE_DRIFT_DETECTED`
- `MICRO_SCENARIO_ESCALATED`
- `MICRO_VERIFICATION_COMPLETED`
- `MICRO_ARCHIVED`

阶段耗时、确认次数、准入率、升级率和失败原因从真实事件推导，不接受 Agent 自报指标。事件不得记录凭据、敏感正文或无必要的完整命令输出。

## 11. 测试策略

### 11.1 单元与真值表测试

- Profile、路由顺序、风险和影响默认值。
- 每条允许规则、禁止规则及所有未知值的失败关闭行为。
- 推荐摘要、基线和权限摘要绑定。
- 单任务、路径、操作和验证配置校验。

### 11.2 集成与恢复测试

- 一次确认后完成四阶段正常路径。
- 不生成 `research.md`、`domain.md`、`spec.md`、`design.md`。
- 中断后从正确 Run 和阶段幂等恢复。
- 越界后保留 `ChangeId`、增加 Revision、失效旧证据并进入正确场景。
- 已有其他场景的路由、创建、恢复和归档行为不回归。

### 11.3 对抗性测试

- Agent 伪造 `eligible` 或用户确认。
- 任务声明与实际差异不一致。
- 未声明路径、路径穿越、大小写/编码别名和符号链接逃逸。
- 删除、重命名、跨模块和手工绕过 Writer Claim。
- 伪造 `PASS`、验证后篡改文件、复用旧 Revision 证据。
- 使用 `--force` 归档或在升级后自动降级。
- 在推荐、确认、创建、工作、验证和升级的各持久化边界注入崩溃。

### 11.4 最终认证

最终必须在干净检出和打包安装环境中执行真实 CLI/SDK 流程，验证目录哈希、编译资源、四阶段正常路径、自动升级、恢复及全部对抗性用例。快照更新不能作为正确性依据。

## 12. 实施顺序与依赖

1. 先完成并认证 v0.3 Change 权限完整性修复；在此之前保持 `micro-change` 不可用。
2. 以测试驱动方式扩展场景 ID、严格 Profile、权限目录和准入编译资源。
3. 接入只读推荐与可信用户确认边界。
4. 接入创建时的完整 `intent.md` 和单任务 `plan`。
5. 接入 Writer Claim、实际差异复检和自动重分类。
6. 接入按类型选择的验证配置、新鲜证据及后台验证编排。
7. 完成 CLI/Agent 体验、恢复测试、对抗性测试和安装包认证。

本规格是权限完整性修复规格之上的增量设计；如果前置规格的最终目录或事务 ABI 发生变化，必须先 Reconcile 本规格，不能直接在旧 v0.2 结构上补丁实现。

## 13. 验收标准

1. Agent 可以只读推荐 `micro-change`，并展示理由和排除项。
2. 用户只确认一次；Core 仍独立执行失败关闭的准入校验。
3. 合法变更的必需路线严格为 `plan -> work -> verify -> archive`。
4. 主要人工产物只有 `intent.md` 和 `tasks.yaml`，且任务恰好一个。
5. 不新增 Capability、Host Skill、v0.2 别名或兼容逻辑。
6. 所有写入严格限制在任务允许路径，并以实际差异完成复检。
7. 任一禁止影响或未知项都不能留在轻量通道。
8. 越界时保留 `ChangeId`、增加 Revision、失效旧证据并自动升级。
9. 验证包含匹配变更类型的正常检查、独立审查和对抗性检查。
10. 没有当前 Revision 的真实新鲜证据时无法归档，`--force` 也不能绕过。
11. 中断后能够幂等恢复，不重复写入或错误复用旧状态。
12. 现有场景和完整 v0.3 权限认证全部通过。

## 14. 风险与缓解

| 风险 | 缓解措施 |
| --- | --- |
| Agent 误判低风险 | Core 独立编译准入、未知即拒绝、多个阶段重复复检 |
| 实现中范围逐渐扩大 | Writer Claim、实际差异复检、自动升级且禁止自动降级 |
| 表面轻量导致证据缩水 | 验证配置按类型选择，但新鲜证据与对抗性测试不可省略 |
| 新通道扩大权限面 | 复用四个现有 Capability，并将新增规则纳入同一权限目录 |
| 后台验证增加计算时间 | 独立流程并行；减少用户等待操作而不牺牲必要检查 |
| 与权限修复规格发生漂移 | 明确实施依赖，目录或 ABI 变化时先 Reconcile 再实施 |

## 15. 批准记录

设计讨论已确认：

- 范围：允许局部 P3 行为、测试、文档和非生产配置；排除 Bug、重构、删除及边界影响。
- 入口：Agent 推荐，用户确认一次，Core 独立复核。
- 路线：`plan -> work -> verify -> archive`。
- 越界：自动升级并停在新路线的安全检查点。
- 架构：独立 `micro-change` 场景，复用现有 Capability 和 Host Skill。

书面规格审阅完成前，不进入实施计划或生产代码修改。
