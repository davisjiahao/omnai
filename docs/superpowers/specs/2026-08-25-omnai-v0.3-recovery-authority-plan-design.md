# OmnAI v0.3 RecoveryAuthorityPlan 统一恢复权限设计

- **状态：** 书面规格已批准，待实施
- **日期：** 2026-08-25
- **分支：** `feat/omnai-v0.3-full-pipeline-fusion`
- **设计基线：** `89a268ef7cea5565a473c40440ed42aaa744d1c8`
- **上位规格：** `docs/superpowers/specs/2026-08-22-omnai-v0.3-change-authority-integrity-repair-design.md`
- **触发审查：** `.superpowers/sdd/2026-08-24-omnai-v0.3-ar-a-authority-contracts-flow-binding/task-5-overall-rereview-round-2.md`
- **版本边界：** package 与 CLI 继续保持 `0.2.0`

## 1. 结论

AR-A Task 5 的前两轮修复已经证明，单独收紧某一个恢复函数不能关闭完整权限风险。当前缺口不是哈希算法或某个错误 matcher，而是同一个恢复事务在不同 consumer、source/target phase 和 generic helper 中使用了不同的写前门禁。

本设计引入一个进程内、只读准备、不可变提交的 `RecoveryAuthorityPlan`：

1. 每个拥有 PENDING transaction 的恢复入口，在任何目标写入前，从冻结 transaction 和同一把 Change 锁下的一次当前快照推导完整、唯一、有序的持久操作序列。
2. 当前机器状态只能是该序列的精确前缀；任何错位、缺失前置、额外成员、错误 correlation、错误 owner、重排或正文漂移都在首次新写入前失败。
3. commit 只执行已经准备好的剩余操作，不再读取或重新解释权限状态。
4. ordinary Reconcile、Decision Reconcile 和 Flow assessment 的 source、target、completion retry 共同遵守该协议。
5. completed validator 和全局 lineage 使用同一 owner/candidate-set 规则，不能让 PENDING 阶段拒绝的审计在 COMPLETED 后被长期忽略。

它是 AR-A 对现有 v1 transaction/recovery 路径的内部收口，不是第二个工作流运行时，也不提前实现 AR-D 的最终 AuthorityRecord、AR-F 的整文件原子审计或 AR-G 的最终 TerminalStateCalculator。后续阶段应吸收本设计的不变量，而不是并行保留两套权限事务。

## 2. 背景与已确认问题

### 2.1 已经关闭的能力

截至设计基线，以下能力已通过实现验证和静态复审：

- Decision 正文、binding 集合摘要与 Flow v2 身份完整绑定。
- source/target metadata、Revision、signal、Decision 与 Flow 的冻结时间统一使用 transaction `createdAt`。
- ordinary target 主路径使用单 progress snapshot、Decision 成员级两遍式验证、精确 Flow 候选和 terminal Flow hash。
- reconcile terminal audit 已具有 expected-event 单一构造器、只读 prepare 与 immutable commit 原语。
- 未篡改 Flow-rebound retry 与 terminal-audit-before-completion retry 能收敛到一次成功执行的相同终态。

### 2.2 尚未关闭的根因

现有协议仍有四个结构性缺口：

1. **接入不完整。** ordinary target 使用早期 prepare，但 ordinary source、Decision Reconcile source/target 和 Flow assessment source/target 仍在 archive、Decision、Flow 或 finalize 写入后才首次检查 terminal audit。
2. **owner selector 不完整。** 部分逻辑先用待验证的 correlation、decisionId、from/to 判断事件是否“相关”；同时伪造这些字段的 target-Revision orphan audit 可以逃出候选集合。
3. **phase 不完整。** 已存在 terminal audit 时，没有同时证明 archive、tasks、signal、Revision、metadata、全部 Decision/audit 和 Flow 已经完整落盘；删除早期 archive 后仍可能被主动补写并完成。
4. **PENDING 与 COMPLETED 规则不一致。** 本地恢复可能忽略的额外事件，在 completed validator 或全局 lineage 中也可能继续被相同 selector 忽略。

这些缺口违反上位规格：

- I03：锁内一次读取并冻结上下文；
- I08：审计顺序属于事务；
- I09：新写入、恢复和重试使用一个精确终态；
- I11：PENDING 后的非精确恢复不得产生额外写入。

## 3. 目标

本设计必须做到：

1. 为三类 PENDING consumer 建立同一个 prepare-before-write 强制协议。
2. 从冻结 transaction 唯一推导 owner、目标 Revision/Baseline、目标文件和有序审计事件。
3. 用稳定 owner 范围界定完整候选集合，再验证 correlation、decisionId、from/to 等正文；不能反过来用待验证字段缩小候选集合。
4. 将所有可恢复机器状态限制为唯一持久操作序列的精确前缀。
5. 在同一 Change lock 内只读取一次每类业务快照；prepare 与 commit 之间无业务 callback、无二次权限读取、无 TOCTOU。
6. 让 source retry、target partial、Flow target、terminal-audit durable 和 completion-only retry 都收敛到一次成功执行的相同字节与顺序。
7. 对冲突、未知、额外、重排和缺失前置状态失败关闭，并证明失败后整个 Change 零新增、零改写。
8. 保持无 correlation 的内部 reconcile 兼容路径，不把本设计扩张成通用事件溯源平台。

## 4. 非目标

本设计不：

- 提前创建最终 `AuthorityRecordV1`、AuthorityEnvelope、MachineAuthoritySeal 或 WriterFence。
- 把 `progress.jsonl` 改造成最终整文件原子审计格式；该工作仍由 AR-F 拥有。
- 改变公开 CLI、root exports、package schema 或产品版本。
- 引入 Flow v1 兼容、旧持久结构迁移或 force/repair 后门。
- 允许恢复逻辑自动删除、重排或“修复”未知审计；未知状态必须失败关闭。
- 顺手迁移与本 finding 无关的 Writer、Stage、Execution、Workset 或 micro-change。
- 将 diagnostics channel 当作权限证据；它只制造测试 crash seam。

## 5. 考虑过的方案

### 5.1 已批准：共享 RecoveryAuthorityPlan + consumer adapter

共享层负责 owner、快照、候选集合、精确前缀和不可变 commit；ordinary、Decision 与 Flow adapter 只负责从各自冻结 transaction 生成业务目标和操作序列。

优点：

- 一个协议覆盖全部 PENDING consumer；
- 共享规则与业务目标解耦；
- 可以逐 consumer 接入并独立 TDD/复审；
- 后续可被最终 AuthorityTransaction/TerminalStateCalculator 吸收。

代价：

- 需要修改多个恢复入口和 generic reconcile 接口；
- 必须建立完整 consumer/phase 对抗矩阵。

### 5.2 拒绝：每个 consumer 单独增加 preflight

局部补丁改动表面较小，但前两轮修复已经证明它会造成 source/target、PENDING/COMPLETED 和 local/global validator 不对称。继续使用该方案会复制 expected audit、selector 和 phase 规则。

### 5.3 拒绝：立即重写为最终通用事务引擎

把现有 Reconcile、Decision 和 Flow 全部迁移到最终 AuthorityRecord 能获得最干净的长期模型，但会提前吞并 AR-B 至 AR-G 的所有权，扩大持久 Schema、迁移和发布风险。本设计只建立后续引擎必须吸收的内部协议。

## 6. 核心概念

### 6.1 RecoveryAuthorityOwner

每个计划具有冻结 owner：

```ts
interface RecoveryAuthorityOwner {
  transactionKind: 'ORDINARY_RECONCILE' | 'DECISION_RECONCILE' | 'FLOW_ASSESSMENT';
  changeId: string;
  correlationId: string;
  sourceRevision: string;
  sourceBaseline: string;
  targetRevision: string;
  targetBaseline: string;
  createdAt: string;
}
```

owner 的全部字段来自已认证 PENDING transaction。调用方输入、当前审计字段或当前 Flow 不得重新定义 owner。

### 6.2 RecoveryAuthoritySnapshot

snapshot 在同一 Change lock 内构造，至少冻结：

```ts
type RecoveryTransaction =
  | OrdinaryReconcileTransaction
  | DecisionReconcileTransaction
  | FlowAssessmentTransaction;

interface RecoveryAuthoritySnapshot {
  metadata: ChangeMetadata;
  tasks: TaskFile;
  signal: ReconcileSignal | null;
  revision: Revision | null;
  sourceArchive: FlowPlan | null;
  sourceArchiveExists: boolean;
  decisions: readonly DecisionRecord[];
  flow: FlowPlan | null;
  progressEvents: readonly RecoveryProgressEvent[];
  transaction: RecoveryTransaction;
  transactionOwners: readonly RecoveryAuthorityOwner[];
}
```

`RecoveryProgressEvent` 是现有 progress audit 类型经 owning Schema 解析后的只读联合，不创建新的持久事件格式。`transactionOwners` 来自当前 Change 已有 ordinary、Decision Reconcile 和 Flow assessment transaction inventory，用于证明每个权限事件恰好归属一个 owner。

实现可以按 consumer 细分类型，但必须满足：

- metadata、tasks、Decision inventory、Flow、archive presence/content 和完整 progress 只为本次 prepare 读取一次；
- 所有值进入普通不可变快照，后续不回读调用方对象或动态容器；
- progress 必须是完整有序数组，不能分别为不同 helper 多次读取；
- 同一个 snapshot 同时供目标正文、audit candidate、phase 和 prefix 验证使用。

### 6.3 RecoveryAuthorityOperation

adapter 从冻结 transaction 产生唯一有序操作：

```ts
type RecoveryAuthorityOperation =
  | { kind: 'ENSURE_ARCHIVE'; path: string; expected: FlowPlan }
  | { kind: 'WRITE_TASKS'; path: string; expected: TaskFile }
  | { kind: 'WRITE_SIGNAL'; path: string; expected: ReconcileSignal }
  | { kind: 'WRITE_REVISION'; path: string; expected: Revision }
  | { kind: 'WRITE_METADATA'; path: string; expected: ChangeMetadata }
  | { kind: 'WRITE_DECISION'; path: string; expected: DecisionRecord }
  | { kind: 'APPEND_AUDIT'; path: string; expected: RecoveryProgressEvent }
  | { kind: 'WRITE_FLOW'; path: string; expected: FlowPlan }
  | { kind: 'WRITE_TRANSACTION'; path: string; expected: RecoveryTransaction };
```

操作不是新的持久 Schema。它只描述现有 writer 的确定性目标，并携带 commit 所需的完整普通值。

### 6.4 RecoveryAuthorityPlan

```ts
interface RecoveryAuthorityPlan {
  owner: RecoveryAuthorityOwner;
  snapshot: RecoveryAuthoritySnapshot;
  operations: readonly RecoveryAuthorityOperation[];
  durablePrefixLength: number;
  pendingOperations: readonly RecoveryAuthorityOperation[];
  expectedTerminalDigests: Readonly<Record<string, AuthorityHash | null>>;
}
```

`durablePrefixLength` 是已经完整落盘的操作数。当前状态必须精确等于 `operations.slice(0, durablePrefixLength)` 的机器投影；不存在跳跃、补集、重排或两个不同前缀同时成立的情况。

## 7. 完整候选集合规则

### 7.1 先界定 owner 范围，再验证正文

审计候选集合必须先由不可伪造的机器位置界定：

- `changeId` 等于 owner Change；
- 顶层 `revision` 等于 owner target Revision；
- `event` 属于 adapter 声明的 transaction-owned event kind。

在候选集合形成后，才验证：

- correlationId；
- decisionId；
- fromRevision/toRevision；
- baseline；
- timestamp；
- detail；
- consumer-specific data。

因此，同 target Revision 但 wrong-correlation、wrong-decision、wrong-from/to、wrong-baseline 的 schema-shaped event 仍属于候选集合，并必须作为漂移拒绝，不能被过滤为“无关”。

### 7.2 transaction-owned event kinds

现有三类 adapter 至少拥有：

| Adapter | transaction-owned audit | 最终边界事件 |
| --- | --- | --- |
| ordinary Reconcile | 本事务产生的有序 `DECISION_REBOUND`，唯一 `RECONCILE_APPLIED` | `RECONCILE_APPLIED` |
| Decision Reconcile | 本事务产生的有序 `DECISION_REBOUND`，本事务 selected Decision transition，唯一 `RECONCILE_APPLIED` | `RECONCILE_APPLIED` |
| Flow assessment | 本事务产生的有序 `DECISION_REBOUND`，唯一 `RECONCILE_APPLIED`，本事务 `FLOW_REASSESSED` | `FLOW_REASSESSED` |

consumer-specific transition 的精确 owner 仍由其现有冻结 transaction 和语义 validator 定义；共享层不能只按事件名吞并 target Revision 后由其他独立 transaction 合法产生的事件。

### 7.3 completed 后的事件边界

adapter 声明的唯一最终边界事件把 transaction-owned 前缀与后续合法 mutation 分隔。ordinary/Decision 的边界是 `RECONCILE_APPLIED`；Flow assessment 的 `RECONCILE_APPLIED` 是前置操作，最终边界是 `FLOW_REASSESSED`：

- 最终边界之前必须与本 transaction 的冻结 audit sequence 完全相等；
- 最终边界自身必须唯一、全文精确；
- 最终边界之后的事件由后续 transaction 的 owner/lineage 独立认证；
- `DECISION_REBOUND` 与 `RECONCILE_APPLIED` 不允许在同一 target Revision 通过 wrong correlation 伪装成后续 transaction。

### 7.4 全局 owner 补集

本地 plan 负责 owner target Revision 的完整候选集合；同一次 progress snapshot 还必须完成全局补集检查：

1. 对每个 transaction-owned event，使用 Change、Revision、event kind 与 transaction inventory 查询可能 owner。
2. 恰好一个 owner 时，由该 owner 的冻结 expected sequence 验证事件全文和位置。
3. 没有 owner 时是 orphan，失败关闭。
4. 多个 owner 时是权限分叉，失败关闭。
5. 已完成 transaction 最终边界后的普通 Decision mutation 只由其自身 transaction/lineage 认领，不能被前一个 recovery plan 吞并。

该补集不新增全局权限头；它复用已有 transaction 文件与 lineage inventory，防止攻击者同时修改 revision、correlation 和成员字段后逃出所有本地 selector。

## 8. 精确前缀算法

prepare 必须执行以下顺序：

1. 从 PENDING transaction 推导 owner 和完整 `operations`。
2. 在锁内读取一次 `RecoveryAuthoritySnapshot`。
3. 用 owning Schema 和 canonical boundary 认证 snapshot 中每个机器对象。
4. 构造 target Revision 的完整候选 audit set，并和 operations 中的 audit 子序列比较。
5. 从第一个 operation 开始依次判断当前机器投影：
   - 已存在且全文精确：计入 durable prefix；
   - 尚未存在且所有后续 operation 也尚未落盘：确定 prefix 结束；
   - 已存在但正文不精确：失败；
   - 前置缺失而后置已存在：失败；
   - 出现不属于 operations 的 owner candidate：失败。
6. 验证最终边界 phase：adapter 的最终边界事件只有在 archive、tasks、signal、Revision、metadata、全部 Decision/audit、Flow 和 consumer-specific 前置事件均 durable 时才允许存在。
7. 生成不可变 `pendingOperations`；prepare 结束后不得再访问业务状态。

文件操作的“尚未存在”必须按 transaction 语义解释：

- source Flow 非 null 时，source archive 是序列首部；后续任一操作 durable 而 archive 缺失都属于漂移，不能补写。
- source Flow 为 null 时，该 transaction 不拥有 archive operation；出现其 source Revision archive 必须按现有 legacy/ownership 规则证明属于其他合法历史，否则失败关闭。
- source 状态允许 target signal、Revision、metadata、Decision、Flow 和 terminal 均尚未出现。
- target partial 只能是同一操作序列的一个前缀，不能按文件类型分别挑选“看起来合法”的状态。

## 9. Prepare/Commit 协议

### 9.1 Prepare

`prepareRecoveryAuthorityPlan` 必须：

- 由持有 Change lock 的 caller 调用；
- 完全只读；
- 不创建目录、不 ensure archive、不 append audit、不发布业务事件；
- 不执行可重入用户 callback；
- 返回普通、不可变、可一次消费的 plan；
- 把错误映射为现有稳定 AuthorityError 域，不在 detail 中包含正文或外部路径。

### 9.2 Commit

`commitRecoveryAuthorityPlan` 必须：

- 在同一 Change lock、同一调用栈中消费 plan；
- 只执行 `pendingOperations`，不能重新读取当前业务状态；
- 使用 plan 中冻结的完整对象/字节，不能重新调用业务 compiler 获取不同时间或输入；
- 严格按 operations 顺序写入；
- 对已在 durable prefix 中的操作 no-op，不重复 audit；
- diagnostics stage 只能在相应 awaited 写入成功后发布，不能参与权限判断。

### 9.3 Commit 后机器验证

commit 后允许重读本事务拥有的目标来验证实际 hash/全文，但该步骤：

- 不能重新读取 Decision/SourceRef 来解释业务目标；
- 不能因发现漂移而生成另一套目标或继续补写；
- 失败时 transaction 保持 PENDING，已落盘内容必须仍是冻结 operations 的精确前缀；
- 后续精确 retry 使用同一 transaction 重新 prepare。

这与上位规格未来的 MachineAuthoritySeal 方向一致，但本阶段不提前持久化最终 Seal。

## 10. Consumer 接入矩阵

### 10.1 ordinary Reconcile

| Phase | 要求 |
| --- | --- |
| fresh / intent durable | 创建 PENDING 后、archive/tasks/signal/Revision/metadata 首写前 prepare；已有 target audit 或 target 文件必须属于精确前缀，否则拒绝 |
| source retry | 使用冻结 transaction 推导完整 plan，不再让 generic reconcile 在写后首次 prepare terminal audit |
| target partial | 使用同一 snapshot 验证 archive、Decision audit prefix、Flow 与 terminal；archive 缺失且后续 durable 时拒绝 |
| terminal durable / PENDING | 只允许 transaction completion 为 pending operation，不重复或补写其他目标 |
| COMPLETED retry | 用同一 owner/candidate/prefix 规则验证完整终态后返回冻结结果 |

### 10.2 Decision Reconcile

| Phase | 要求 |
| --- | --- |
| fresh / source retry | PENDING owner 在 generic reconcile 首写前准备 plan；selected Decision finalize 也是有序 operation |
| target partial | live Decision rebound、Flow rebound、selected Decision transition、reconcile terminal 和 transaction completion 共同组成唯一前缀 |
| terminal durable / PENDING | 只补 transaction completion；selected Decision、Flow 和 audit 均不得重复 |
| COMPLETED retry | 复用同一 owner 与完整 candidate-set validator，并允许 terminal 后由其他 transaction 认证的合法 Decision mutation |

### 10.3 Flow assessment

| Phase | 要求 |
| --- | --- |
| fresh / source retry | 在 archive/Decision/reconcile target 写前 prepare，不由 generic helper 在 finalize 后首次读取 audit |
| target partial | live Decision rebound、accepted Flow、accepted transaction state、`RECONCILE_APPLIED`、`FLOW_REASSESSED` 和 completion 共同形成唯一前缀 |
| terminal durable / PENDING | 只完成尚未 durable 的冻结 operation，不重复 accepted Flow 或 audit |
| COMPLETED retry | terminal 前序列精确；terminal 后的晚期 Decision 由现有 lineage 独立认证 |

### 10.4 无 correlation 内部 reconcile

没有 PENDING owner 的内部 reconcile 保留现有接口与错误语义：

- 不伪造 RecoveryAuthorityOwner；
- 继续使用现有非 transaction audit conflict 规则；
- 不发布 transaction diagnostics stage；
- 不能被带 correlation 的 PENDING caller 当作绕过入口。

## 11. Generic reconcile 接口约束

`reconcileChangeWithinChangeLock` 的调用模式必须成为显式判别联合：

```ts
type ReconcileAuthorityMode =
  | { mode: 'UNOWNED_INTERNAL' }
  | { mode: 'OWNED_TRANSACTION'; plan: RecoveryAuthorityPlan };
```

规则：

- 只要提供 transaction correlation、transaction `createdAt`、expected Flow/Decision 或 finalize callback，就必须使用 `OWNED_TRANSACTION`。
- `OWNED_TRANSACTION` 的 plan 必须在 caller 的首次目标写入前完成。
- generic helper 只能验证实际 result 与 plan 中冻结 result 相等并 commit prepared operation；不能自行在流程尾部第一次读取 progress。
- 缺 plan、owner 不匹配、plan 已消费或 result 不等时失败关闭。
- `UNOWNED_INTERNAL` 不接受 transaction-only options。

该类型边界让遗漏 consumer 在编译期暴露，而不是依赖代码审查发现。

## 12. 错误与失败语义

所有 PENDING recovery 错误遵循：

- owner、候选集合、正文或 phase 漂移：`AUTHORITY_TARGET_DRIFT`；
- 持久对象不满足 owning Schema、重复 key 或 canonical boundary：`AUTHORITY_CORRUPT`；
- 相同 transaction owner 的不同请求：保留现有 request-conflict 错误；
- 不暴露 Decision 正文、SourceRef 内容、绝对路径或原始审计载荷；
- prepare 失败后，除既存 PENDING 意图外，整个 Change 文件清单与逐文件 bytes 完全不变。

不能为了通过 retry：

- 删除未知 audit；
- 把 wrong correlation event 改成 expected；
- 补写位于已 durable 后序 operation 之前的缺失前置；
- 重新排序已有 audit；
- 用当前墙钟重新编译目标。

## 13. 测试设计

### 13.1 TDD 原则

- 每个行为先在固定 BASE 上只改测试并取得真实 RED。
- 失败必须命中错误写入、错误完成或 selector 逃逸，不能以类型错误、fixture 缺失或 mock 自证。
- 预期值由冻结 transaction 和 literal event 构造独立推导；不能调用被测 prepare/commit 生成 expected。
- 每个拒绝用例比较整个 Change 的排序文件清单和逐文件原始 bytes。
- 所有测试保留 exact AuthorityError code/detail、audit cardinality/order 和 transaction status 断言。

### 13.2 consumer/phase 矩阵

| --- | --- | --- | --- | --- | --- | --- |
| ordinary | 必测 | 必测 | 必测 | 必测 | 必测 | 必测 |
| Decision Reconcile | 必测 | 必测 | 必测 | 按拥有操作验证 | 必测 | 必测 |
| Flow assessment | 必测 | 必测 | 必测 | 按拥有操作验证 | 必测 | 必测 |

### 13.3 selector 补集

表驱动覆盖至少包括：

- correlation、decisionId、fromRevision、toRevision 同时漂移；
- target Revision 上 wrong-correlation `RECONCILE_APPLIED`；
- duplicate、extra、orphan、正文漂移和顺序互换；
- terminal 位于 Decision rebound 之前；
- COMPLETED 后插入/reorder transaction-owned candidate；
- terminal 后合法独立 Decision mutation 不被误拒绝。

### 13.4 crash seam

独立子进程至少覆盖：

- PENDING intent durable；
- archive durable；
- metadata durable；
- 每个 Decision target 与对应 audit 之间；
- 全部 Decision audit durable；
- Flow/selected target durable；
- reconcile terminal audit durable；
- consumer-specific terminal audit durable；
- transaction completion durable。

每个 seam 都验证精确 retry、不同请求拒绝、audit 不重复、最终 bytes/hash/order 与 one-shot 相同。

### 13.5 回归门禁

round-3 实现完成后必须顺序通过：

1. typecheck；
2. build；
3. R01 focused；
4. ordinary、Decision、Flow assessment 全 consumer focused；
5. adversarial；
6. 独立整体代码复审；
7. Task 5 fresh build、full、source↔dist manifest、adversarial、pack/install/CLI 认证。

任一失败都停止后续阶段，先系统化定位；不得修改宽 matcher、删除旧测试或跳过 consumer。

## 14. 性能与复杂度

- 每次 prepare 对 progress 做一次线性读取和一次索引构建，时间复杂度 `O(events + decisions + operations)`。
- candidate-set 和 expected sequence 使用 Map/Set 辅助，但最终顺序比较以原 progress index 为准。
- 不为每个 Decision 重读 progress 或 Flow。
- commit 不执行额外扫描。
- 本地 Change 审计规模继续受现有配额约束；最终配额与整文件原子替换由 AR-F 冻结。

## 15. 实施边界与审查门槛

round-3 实施应拆成可独立拒绝的四个交付面：

1. 共享 owner、candidate-set、snapshot、prefix 与 prepared audit/operation 协议。
2. ordinary fresh/source/target/completed 全 phase 接入。
3. Decision Reconcile 与 Flow assessment 全 phase 接入。
4. completed/global validator、selector 补集、consumer 矩阵和最终认证。

每个交付面必须 RED→GREEN、聚焦 commit、独立 code review。不得让一个 Agent 在未复审前连续修改全部 consumer。

这是针对同一根因的第三次实现尝试。如果 round-3 独立复审仍发现 prepare-before-write 或 complete-set 的结构性绕过，停止进入第四轮补丁；回退到架构评审，决定是否提前实施最终 AuthorityTransaction/TerminalStateCalculator，而不是继续增加局部门禁。

## 16. 完成定义

本设计只有在以下条件全部满足时才算完成：

- 所有带 PENDING owner 的 reconcile 调用都在首次目标写入前持有 `RecoveryAuthorityPlan`；编译期不存在 late-prepare 调用方式。
- ordinary、Decision Reconcile、Flow assessment 的 source、target、terminal-only 和 completed retry 全部使用同一精确前缀规则。
- target Revision 的 transaction-owned audit 完整集合无法通过组合 selector 漂移逃逸。
- archive 和其他早期操作缺失时，后序 durable 状态不能被主动补写掩盖。
- prepare 失败后全 Change 文件清单和原始 bytes 不变。
- 精确 crash retry 与 one-shot 的机器目标、audit 顺序、hash 和 completed transaction 相等。
- completed validator 与 PENDING preflight 对 owner/candidate/order 的判定一致。
- Critical、Important 为 0，SPEC/QUALITY PASS。
- Task 5 fresh final certification 全绿，版本仍为 `0.2.0`，未 push、publish、启用 micro-change 或生成 WorkflowLock。

## 17. 已批准裁决

1. 采用共享 `RecoveryAuthorityPlan + consumer adapter`，拒绝继续按调用点独立打补丁。
2. owner 由冻结 transaction 定义；candidate-set 先按 Change、target Revision 和 owned event kind形成，再验证其他字段。
3. 当前机器状态必须是唯一持久操作序列的精确前缀。
4. PENDING consumer 必须 prepare-before-write；commit 不二读、不重新解释业务状态。
5. ordinary、Decision Reconcile、Flow assessment 的 source/target/completed 全部接入。
6. 保留无 correlation 内部 reconcile，不提前实现最终 AuthorityRecord/AR-F 审计格式。
7. round-3 是该根因最后一次补丁式实现；再出现结构性失败则回到最终事务架构评审。
