# OmnAI v0.3 Native Full-Pipeline Fusion Design

**Status:** Approved for phased implementation
**Date:** 2026-08-19
**Branch:** `feat/omnai-v0.3-full-pipeline-fusion`
**Baseline:** `776272c6e780bdc7fe01cec7faf9f3563ff13c79`

## 1. Purpose

OmnAI already contains selected Matt-inspired semantic-recovery mechanisms and
Superpowers-inspired delivery discipline, but they currently appear as separate
interaction protocols, repository capabilities, Scenario stage lists, Workset
coordination, and an in-progress autonomous execution subsystem. This design
turns those mechanisms into one OmnAI-native flow without importing either
upstream workflow as a second runtime.

The resulting model is:

- Matt-inspired capabilities recover intent, domain meaning, decision frontiers,
  codebase boundaries, implementation seams, and executable slices.
- Superpowers-inspired capabilities enforce alternative comparison, bounded
  planning, RED/GREEN evidence, independent review, verification, and branch
  completion discipline.
- OmnAI Core owns routing, durable state, Revision/Baseline lineage, evidence,
  multi-project coordination, execution, and selective re-entry.

The design deliberately distinguishes capability fusion from Skill copying. A
mechanism becomes a Host Skill only when a user needs a direct conversational
entry point. Repository reasoning remains a protocol, execution remains a Core
state machine, and human-readable summaries remain generated views.

## 2. Current-State Findings

The current repository establishes several useful foundations:

1. `ScenarioProfile.stages` and `resolveNextAction` provide deterministic but
   static repository routing.
2. `interaction.grill`, `interaction.brainstorm`, and `interaction.show-me` are
   thin conversational overlays that preserve Core authority.
3. `repository.map`, `repository.model`, and the module-boundary amendments to
   Research, Spec, Design, Plan, Work, Review, Verify, and Reconcile already
   express most of the upstream reasoning semantics.
4. `tasks.yaml` is a project-local dependency graph with stable task IDs,
   blockers, evidence needs, and selective invalidation.
5. Worksets provide aggregate execution workspaces backed by real Git
   worktrees. Cross-project coordination is contract-based rather than a shared
   cross-repository task graph.
6. v0.3 execution already defines ContractSnapshots, RunPackets, Waves, Writer
   Claims, Reviewer Runs, CommitSets, durable lifecycle events, and Attention
   items. Milestone C must finish these primitives; this fusion must not create a
   competing execution engine.
7. Review, learning, and revision history exist, but the structured records and
   generated user views do not yet express the complete unified flow.

The primary architectural gap is therefore not missing prompt text. It is the
lack of a structured, auditable, adaptive flow spine connecting decisions,
capability routing, tasks, execution packets, evidence, review, knowledge, and
re-entry.

## 3. Goals

The full pipeline MUST:

1. Select the smallest safe capability path for each Change instead of forcing
   every Change through every mechanism.
2. Route unresolved human-owned decisions to Grill, consequential solution
   choices to Brainstorm, recoverable facts to Research or Experiment, and
   executable work to the project-local Task graph.
3. Treat Wayfinder-style mapping and codebase-design analysis as conditional
   reasoning capabilities, not mandatory top-level stages.
4. Preserve exactly one authoritative representation for routing, decisions,
   tasks, execution, evidence, reviews, and revisions.
5. Generate Context, Task Brief, Lineage, Review, and Solution views from those
   authoritative records rather than creating parallel editable truth.
6. Preserve the existing rule that repositories never depend on tasks in other
   repositories. Cross-project dependencies are immutable contract references
   and coordinated verification requirements only.
7. Allow Reconcile to interrupt any active capability or Run, invalidate only
   affected state, and resume unaffected work.
8. Connect to Milestone C RunPacket, Wave, Reviewer, verification, and CommitSet
   models without weakening their release gates.
9. Keep simple Bugs and small Changes fast while providing stronger analysis
   for complex-domain, architecture, migration, and multi-project work.
10. Make every completion claim traceable to fresh evidence for the active
    Revision and exact source hashes.

## 4. Non-Goals

This change will not:

- vendor or execute Matt or Superpowers source code at runtime;
- add one Host Skill for every stage;
- replace an organization's issue tracker, deployment system, or release
  approval process;
- turn Decision records into implementation Tasks before they are executable;
- introduce cross-project `Task.dependsOn` references;
- publish `omnai run` or `omnai-run` before Milestone C C1-C4 acceptance gates
  pass;
- treat all code changes as conventional unit-test-first work when
  characterization, contract, migration, build, static, or runtime evidence is
  the correct proof;
- promote every completed Change into permanent knowledge;
- maintain editable `CONTEXT.md`, `lineage.md`, Ticket Plan, and Solution files
  as additional sources of truth.

## 5. Considered Approaches

### 5.1 Recommended: OmnAI-native adaptive flow

Add structured Decision records and a Core-compiled FlowPlan. Keep existing
repository capabilities, Task state, Workset state, and execution primitives as
the authorities for their respective concerns. Generate human-readable views
from those records.

Advantages:

- deterministic and auditable routing;
- no duplicate workflow engine;
- conditional complexity rather than a mandatory mega-pipeline;
- backward-compatible path for existing Changes;
- clean integration with Reconcile and Milestone C;
- upstream workflow names do not leak into persisted Core semantics.

Cost:

- requires schema evolution, compatibility loading, and end-to-end routing
  tests;
- AI-proposed assessments need strict Core validation before they influence
  routing.

### 5.2 Rejected: one fixed Matt-to-Superpowers pipeline

This approach would create a fixed sequence such as Grill, Model, Brainstorm,
Wayfinder, Tickets, Plan, SDD, Review, Finish, and Reconcile.

It was rejected because simple work would become unnecessarily expensive,
Reconcile would be incorrectly modeled as a final stage, Workset would be
misrepresented as an internal stage, and multiple editable artifacts would
drift. It would also duplicate the existing Scenario router and Milestone C
execution engine.

### 5.3 Rejected: upstream Skill facade

This approach would expose separate commands such as `/wayfinder`,
`/to-tickets`, `/writing-plans`, and `/finishing` while leaving Core mostly
unchanged.

It was rejected because the host conversation would become the effective state
machine, different hosts could advance work differently, and decisions or
completion claims could bypass Revision, readiness, evidence, and Workset
guards.

## 6. Architectural Model

The fusion has four layers.

### 6.1 Interaction layer

Direct user-facing entries remain deliberately small:

- `omnai` routes all non-trivial work through Core.
- `omnai-grill` resolves one blocking human-owned decision at a time.
- `omnai-brainstorm` compares genuinely distinct viable approaches for one
  open solution decision.
- `omnai-show-me` behavior remains part of the OmnAI entry and presentation
  protocols rather than a workflow transition.
- `omnai-reconcile` records and routes a changed premise or baseline.

No new Host Skill is added for Model, Wayfinder, codebase-design, ticket
decomposition, testing seams, review, or finishing. Core selects their
repository protocols and runtime services.

### 6.2 Reasoning layer

Repository protocols remain bounded reasoning methods:

- Frame and Grill clarify goal, scope, success, ownership, and acceptance.
- Research and Model recover facts, language, lifecycle, invariants, and
  boundaries.
- Brainstorm and Design compare solution alternatives.
- Map represents destination, decision frontier, blockers, fog, and excluded
  scope for program-scale work.
- Codebase-design remains a cross-cutting architecture lens inside Research,
  Spec, Design, Plan, Work, Review, Verify, and Reconcile.
- Plan converts settled work into a project-local Task DAG.
- Review, Verify, Ship, Learn, and Archive close the evidence and knowledge
  loop.

### 6.3 State and orchestration layer

OmnAI Core owns:

- Change, Scenario, risk, impact, Revision, and Baseline;
- DecisionRecords and the compiled FlowPlan;
- readiness and project-local Tasks;
- Workset membership and ContractSnapshots;
- RunPackets, Waves, Claims, Reviewer Runs, Evidence, and CommitSets;
- Reconcile closures and lineage;
- promotion of reviewed learning.

### 6.4 Projection layer

Generated views make the state easy to consume without becoming authorities:

- Change Context View;
- Task Brief View;
- Flow and Decision Map View;
- Review View;
- Lineage View;
- Solution/Learning View.

Every generated view MUST identify its Change, Revision, Baseline, generation
time, and source hashes, and MUST begin with a do-not-edit notice.

## 7. Authoritative Records

### 7.1 DecisionRecord

The existing per-Change `decisions/` directory gains validated YAML records.
Each record has a stable `DEC-####` ID and contains:

- `schemaVersion`, `id`, `changeId`, `openedRevision`, and optional
  `resolvedRevision`;
- `kind`: `PROBLEM`, `DOMAIN`, `SOLUTION`, `ARCHITECTURE`, `CONTRACT`,
  `DELIVERY`, or `EXTERNAL`;
- `owner`: `HUMAN`, `AGENT`, or `EXTERNAL`;
- `status`: `OPEN`, `BLOCKED`, `RESOLVED`, `REJECTED`, or `SUPERSEDED`;
- one precise question;
- zero or more normalized options with consequences and evidence references;
- selected option or free-form resolution when resolved;
- affected capability, artifact, Task, project, or contract references;
- source references and source hashes;
- created and updated timestamps.

Core routing applies the following rules:

- blocking `HUMAN` decisions select `interaction.grill` together with the
  current owning repository protocol;
- open `SOLUTION` or `ARCHITECTURE` decisions with at least two viable options
  select `interaction.brainstorm` only after upstream problem/domain blockers
  are resolved;
- `AGENT` decisions that require facts route to Research, Diagnose, or
  Experiment and MUST NOT be delegated to the user;
- `EXTERNAL` decisions or missing authority become a Workset Attention item
  when execution reaches them;
- resolved decisions are not reopened in the same Revision;
- contradictory new evidence enters Reconcile rather than silently mutating a
  settled decision.

Markdown sections in `domain.md`, `design.md`, and `contract.md` may explain
decisions, but the DecisionRecord is authoritative for status, ownership,
selection, and routing.

### 7.2 FlowAssessment and FlowPlan

Each active Change gains `.omnai/changes/<change>/flow.yaml`. It is written only
by Core and contains both the accepted assessment and the compiled capability
plan for the active Revision.

The assessment classifies:

- scale: `LOCAL`, `CHANGE`, or `PROGRAM`;
- uncertainty for problem, domain, solution, and delivery as `CLEAR`, `OPEN`,
  or `BLOCKED`;
- topology: `SINGLE_MODULE`, `CROSS_MODULE`, or `CROSS_PROJECT`;
- architecture applicability: `NOT_APPLICABLE`, `FOCUSED`, or `FULL`;
- delivery shape: `STANDARD`, `MIGRATION`, or `HIGH_RISK`;
- relevant DecisionRecord IDs and source hashes.

The compiled plan records each capability as:

- `REQUIRED` with a deterministic reason;
- `CONDITIONAL` with the condition and current disposition; or
- `NOT_APPLICABLE` with a validated reason.

It records the DecisionRecord IDs that influenced capability eligibility, but
does not persist the currently selected interaction overlay. The repository
router derives the current Grill or Brainstorm overlay from the earliest
pending capability, current DecisionRecord status, and readiness. This avoids
rewriting FlowPlan merely because readiness advanced. Decision mutations still
recompile the same-Revision FlowPlan so its decision references, capability
eligibility, input hash, and route hash remain current. The FlowPlan does not
contain requirements, design prose, task instructions, or test results.

Initial flow compilation uses Scenario, risk, impact, and Workset topology.
Later assessments may be proposed by an Agent but Core accepts them only when:

1. the proposal targets the exact active Revision and Baseline;
2. every classification has a source reference and current source hash;
3. a Scenario-required capability is not silently downgraded;
4. risk, compatibility, human approval, and evidence guards are not weakened;
5. already-completed downstream state is either still valid or routed through
   Reconcile with a computed invalidation closure.

The current `ScenarioProfile.stages` remains the compatibility floor. Existing
Changes without `flow.yaml` continue to use legacy static routing until an
explicit migration command compiles their first FlowPlan.

### 7.3 Decision Map

`map.yaml` remains the Wayfinder-style program view, but its decision sections
reference DecisionRecord IDs rather than copying decision bodies. It owns:

- destination;
- resolved, frontier, and blocked decision references;
- fog that cannot yet be made precise;
- out-of-scope work;
- program checkpoints and exit conditions.

Map is required for `PROGRAM` scale and conditional for high-uncertainty
`CHANGE` scale. It is not required for `LOCAL` scale work.

### 7.4 Tasks and Task Briefs

`tasks.yaml` remains the only implementation plan authority. Task schema v2
adds explicit:

- `sourceRefs` for acceptance criteria, decisions, interfaces, and contracts;
- `acceptanceCriteria` containing stable requirement IDs rather than copied
  prose;
- `stopConditions` for invalid assumptions, unsafe scope, or missing evidence.

The existing objective, slice, files, consumes, produces, steps,
evidenceRequired, dependency, and status fields remain.

Rules:

- a DecisionRecord is not a Task;
- only a settled, executable outcome may generate Tasks;
- each Task belongs to exactly one project Change and Revision;
- `dependsOn` may reference only Task IDs in the same `tasks.yaml`;
- cross-project coordination uses `contract:<key>` references and verification
  requirements, never cross-project task dependencies;
- Task schema v1 loads through a deterministic v1-to-v2 compatibility adapter.

The Task Brief is generated from the selected Task, active FlowPlan, referenced
acceptance criteria and decisions, module/interface references, relevant
ContractSnapshot references, required protocols, verification commands,
evidence requirements, and stop conditions. It is a read-only projection.

For autonomous execution, the immutable Milestone C RunPacket is the
authoritative executable brief. The Task Brief is the human/host presentation
of the same source set and cannot override the RunPacket.

### 7.5 ReviewRecord v2

Review remains one structured record, not three drifting reports. Version 2
contains independent gates:

- `specification`: observable requirements and non-goals;
- `standards`: implementation quality, architecture, contract, data, security,
  performance, UX, and engineering lenses selected by policy;
- `riskProduction`: migration, operability, rollback/forward-fix, runtime
  health, and delivery risks selected by policy.

Each gate records status, required lenses, evidence references, and findings.
Overall PASS requires all required gates to pass and no open CRITICAL or
IMPORTANT finding. The record binds the active Revision, reviewed Task or
CommitSet scope, source/diff hash, and Reviewer Run when available.

ReviewRecord v1 remains readable through a compatibility adapter. New writes
use v2 after the migration lands.

### 7.6 LearningRecord

Learning becomes a structured candidate before promotion. A LearningRecord
contains:

- stable ID, originating Change, Revision, and evidence references;
- problem and context;
- root cause or governing constraint;
- validated solution;
- applicability and limitations;
- invalidation conditions;
- promotion status and review evidence.

Archive may promote only a verified, reviewed, reusable LearningRecord. The
project glossary, decisions, policies, and learning index remain durable
project knowledge. A generated Solution View may be exported to an
organization-specific `docs/solutions/` convention, but that export is never
the OmnAI authority.

### 7.7 Lineage

No editable `lineage.md` is introduced. The Lineage View is generated from:

- Revision and Baseline records;
- Reconcile signals and computed closures;
- DecisionRecord status changes;
- FlowPlan changes;
- Task invalidation and supersession events;
- evidence and review bindings;
- Workset re-entry events and contract supersession.

The view shows what changed, why it changed, which work was invalidated, which
work remained valid, and which evidence belongs to each Revision.

## 8. Adaptive Routing

### 8.1 Repository route

`omnai next --json` will resolve in this order:

1. archived or terminal state;
2. pending Reconcile or stale FlowPlan;
3. blocking DecisionRecord interaction;
4. required or currently-triggered capability from FlowPlan and readiness;
5. project-local Task frontier;
6. Review, Verify, Ship, Learn, and Archive gates;
7. no pending action.

The result includes:

- selected capability or Task;
- ordered protocol IDs, including an interaction protocol only when selected;
- reason and blocking status;
- DecisionRecord IDs that caused the route;
- active Revision, Baseline, and FlowPlan hash.

Core remains the only component allowed to update readiness or claim a route
transition.

### 8.2 Fast, standard, and program paths

Typical paths are:

- local Bug: Triage -> Reproduce -> Debug -> Fix -> Plan -> Work -> Verify ->
  Review/Learn when policy requires;
- small clear feature: Spec -> Design applicability check -> Plan -> Work ->
  Verify -> Archive;
- complex domain feature: Grill/Research -> Model -> Spec -> Brainstorm/Design
  -> Plan -> Work -> Review -> Verify -> Learn -> Archive;
- architecture change: Research -> Model when needed -> Design with
  codebase-design lens -> Plan -> Work -> Review -> Verify -> Learn -> Archive;
- migration program: Frame -> Map -> Research/Model -> Spec/Design -> bounded
  project-local Task graphs -> coordinated execution and verification -> Learn
  -> Archive;
- multi-project change: a Workset wraps independent repository routes and
  coordinates only contracts, readiness, integration evidence, and CommitSet
  completion.

### 8.3 Codebase-design trigger

Architecture applicability becomes `FOCUSED` or `FULL` when evidence shows one
or more of:

- cross-module ownership or dependency-direction change;
- a new or changed API, event, adapter, persistence, or stable interface;
- more than one plausible code placement;
- circular dependency, boundary leakage, or mixed responsibilities;
- staged migration or legacy-path retirement;
- a need to find a characterization or controllable test seam;
- broad call-site leverage or a high deletion/simplification claim.

Localized configuration, isolated text, and unambiguous single-seam fixes may
remain `NOT_APPLICABLE` with a recorded reason.

### 8.4 Testing policy

The Evidence Matrix chooses proof by behavior and risk rather than applying one
test ritual universally:

- new observable behavior uses RED -> GREEN -> REFACTOR;
- legacy behavior first uses characterization evidence at the selected seam;
- contracts use provider/consumer or configured compatibility evidence;
- migrations use dry-run, reconciliation, rollback or forward-fix evidence;
- build/configuration changes use compile, static, packaging, smoke, or runtime
  evidence as appropriate;
- deletions require proof that observable behavior and contracts remain
  preserved.

Every required Evidence item remains scoped to the active Revision. Milestone C
VerificationPlans bind project and multi-project tests to exact Task,
ContractSnapshot, commit, and environment hashes.

## 9. Workset and Multi-Project Semantics

Workset is an optional outer orchestration scope, not a repository capability.

Each active Workset project owns:

- its own Change, Revision, FlowPlan, DecisionRecords, Task DAG, evidence, and
  review;
- its own branch and real Git worktree;
- its own Writer and Reviewer Runs.

The Workset owns:

- membership and project impact decisions;
- contract planning, criticism, resolution, and immutable snapshots;
- coordinated Waves and CommitSets;
- cross-project integration environment and evidence;
- Attention items and re-entry coordination.

Contract changes apply as follows:

1. a new source hash creates a new candidate ContractSnapshot;
2. Core calculates provider/consumer compatibility and affected projects;
3. compatible evolution allows unaffected project Tasks and Runs to continue;
4. incompatible or unproven evolution supersedes the old snapshot for new
   Runs, marks exact referencing Runs stale, and creates targeted project
   Reconcile signals;
5. project-local dependency graphs are never connected to each other;
6. integrated completion is decided only from the exact ContractSnapshot,
   CommitSet, VerificationPlan, commit-tree, and environment evidence tuple.

## 10. Reconcile as a Cross-Cutting Interrupt

Reconcile is not the last phase. A new fact may interrupt Frame, Model, Design,
Plan, Work, Review, Verify, Ship, or an autonomous Run.

The existing L0-L5 meanings remain. Full-flow additions are:

- decision ownership or option changes identify the earliest affected
  capability;
- FlowPlan is recompiled for the new Revision;
- completed capabilities remain valid unless their source hashes or decision
  dependencies are in the computed closure;
- Task v2 `sourceRefs` make task invalidation precise;
- RunPackets bound to an old Revision, FlowPlan, DecisionRecord, Task, contract,
  or verification hash become STALE and cannot be integrated;
- generated Context, Brief, Lineage, Review, and Solution views are regenerated
  and never used as invalidation sources;
- unaffected projects and Tasks continue.

## 11. CLI and Host Surface

The final surface adds Core commands, not new stage Skills:

- `omnai flow status [change] --json` shows the accepted assessment, compiled
  capabilities, selected interaction, and source hashes;
- `omnai flow assess <assessment-file> [--change ...]` validates an exact
  Revision/Baseline proposal and applies any required Reconcile transaction;
- `omnai decision list|show|open|resolve|supersede` mutates validated
  DecisionRecords under Core guards;
- `omnai view context|task-brief|flow|review|lineage|solution` renders generated
  projections without mutating workflow state;
- `omnai next --json` returns the full ordered protocol bundle and route causes;
- existing capability commands remain compatible;
- `omnai run` and `omnai-run` remain gated by the Milestone C release plan.

Host Skills always call Core for fresh context and route. They never infer a
FlowPlan from conversation history or directly edit `flow.yaml`.

## 12. Compatibility and Migration

The migration is additive and fail-closed:

1. old Changes without `flow.yaml` retain current Scenario routing;
2. `omnai flow migrate` compiles the first plan from current Scenario, risk,
   impact, readiness, and source hashes without marking any new capability
   READY;
3. Task v1 and ReviewRecord v1 remain readable through explicit adapters;
4. new Task and Review writes use v2 only after workflow-lock schema versions
   are updated atomically;
5. existing Markdown artifacts remain authoritative for their current prose
   concerns;
6. generated views are never migration inputs;
7. no existing Revision, evidence, progress event, or Workset re-entry history
   is rewritten;
8. any ambiguous legacy decision remains an open DecisionRecord or fog rather
   than being guessed.

## 13. Delivery Slices

The overall design is too broad for one implementation plan and is split into
five independently reviewable slices.

### F1: Adaptive flow spine

Deliver DecisionRecord v1, FlowAssessment/FlowPlan v1, legacy fallback,
decision-aware `next`, route audit output, flow/decision CLI commands, protocol
updates, and routing tests. This slice does not modify Milestone C execution
files.

Acceptance:

- simple work remains on the fast path;
- open human decisions select Grill;
- viable solution alternatives select Brainstorm only after upstream blockers
  clear;
- program work selects Map;
- cross-module evidence selects the codebase-design lens without creating a new
  Host Skill;
- Scenario-required capabilities cannot be downgraded;
- old Changes route exactly as before until migrated.

### F2: Task lineage and generated views

Deliver Task schema v2 and migration, decision/acceptance/source linkage,
Context View, Task Brief, Flow View, and Lineage View. Generated output is
deterministic and source-hash bound.

Acceptance:

- a Task Brief is reproducible from authoritative records;
- cross-project task dependencies are rejected;
- a Decision becomes a Task only through explicit Plan output;
- Reconcile invalidates the exact task closure through `sourceRefs`;
- editing a generated view never changes Core state.

### F3: Review and knowledge closure

Deliver ReviewRecord v2, independent gate validation, LearningRecord,
promotion guards, Review View, and Solution View.

Acceptance:

- specification, standards, and risk/production gates remain independently
  visible;
- no open blocking finding can pass;
- stale review or learning evidence cannot satisfy the active Revision;
- Archive promotes only verified, reviewed, reusable knowledge.

### F4: Milestone C execution bridge

After Milestone C C1-C3 are stable, bind FlowPlan, DecisionRecords, Task v2,
ContractSnapshots, and VerificationPlans into RunPackets, Reviewer Runs,
Attention items, CommitSets, and recovery.

Acceptance:

- autonomous execution consumes the same sources as Task Briefs;
- no stale packet or contract can integrate;
- unresolved human/external decisions become bounded Attention items;
- separate Writer and Reviewer Runs produce exact evidence;
- no competing SDD ledger or execution engine exists.

### F5: Full-flow certification

Extend C4 certification with repository and Workset golden scenarios covering
clarification, modeling, alternatives, mapping, module boundaries, task
decomposition, parallel implementation, testing, review, knowledge promotion,
and mid-flight Reconcile.

Acceptance:

- one small Bug proves the fast path;
- one complex-domain single-project Change proves adaptive routing;
- one three-project provider/consumer Change proves contract-based parallelism
  without cross-project task dependencies;
- one contract change during execution proves targeted Reconcile and selective
  continuation;
- packaged Host workflows and authenticated Codex certification pass before
  the execution command is released.

## 14. Test Strategy

Every implementation slice follows RED -> GREEN -> REFACTOR. Required test
groups are:

1. schema tests for strict parsing, compatibility adapters, IDs, hashes, and
   stale Revision/Baseline rejection;
2. pure route compiler table tests for scale, uncertainty, topology, risk,
   decisions, Scenario floors, and interaction selection;
3. invariant tests proving no route can weaken hard guards or cross-project
   dependency rules;
4. CLI tests for JSON stability, read-only views, and guarded mutations;
5. repository end-to-end tests from Change creation through generated views;
6. Reconcile tests for decision, flow, task, review, and evidence invalidation;
7. Workset tests for contract compatibility, independent project Task graphs,
   Attention, and continued unaffected work;
8. Milestone C integration and fault-injection tests only in F4/F5;
9. packaging tests proving resources, protocols, schemas, Skills, and commands
   ship together.

Tests involving Git use real temporary repositories. Tests involving Agents use
deterministic Fake ACP Agents in ordinary CI. Live credentials remain confined
to the explicit release certification command.

### 14.1 Test-flow policy bridge (2026-08-20)

`docs/superpowers/specs/2026-08-20-omnai-test-flow-optimization-design.md`
defines the concrete bridge policy for testing across Plan, Work, Review,
Verify, and Reconcile. Its pending implementation handoff is intentionally pure
and isolated under `src/execution/verification/`: after review and acceptance,
Core services will use it to compile source-bound TestCases and one immutable
plan, fail-close Wave and Writer entry against the exact plan subset, and compute
a content-addressed `ImpactClosure` for targeted revalidation.

F1 remains unchanged by this addition. Persisting the plan, launching the
read-only `PROJECT_TEST_PLANNER`, translating closure targets into legal Run,
Wave, and CommitSet events, and exposing status explanations remain F4 work.
No Writer or Test Planner may perform those Core-owned transitions.

`docs/superpowers/specs/2026-08-20-omnai-adversarial-test-coverage-design.md`
adds the mandatory adversarial-coverage floor. It reuses the same Test Planner,
Writer, Reviewer, Core gates, event store, and ImpactClosure; F4 must not create
an adversarial side ledger, second Writer, or alternate execution engine.

## 15. Baseline and Integration Constraint

The isolated branch was created from `776272c`. Its TypeScript build passes, but
the pre-change full suite exposed existing load-sensitive failures in
`execution-agent-profiles.test.ts`: one Host-lock interleaving and one ACP probe
exit classification failed in separate runs, while the focused probe case then
passed five consecutive isolated runs. No fusion code had been written.

F1 may be planned from this baseline because it avoids execution files, but
implementation MUST first integrate the latest Milestone C work and establish a
stable full-suite baseline. The fusion branch must not patch those unrelated
execution races speculatively or overwrite the active Milestone C worktree.

## 16. Success Criteria

The fusion is complete only when:

- the Core-selected route is adaptive, deterministic, source-traceable, and
  backward compatible;
- no upstream Skill or generated view acts as parallel workflow authority;
- Worksets coordinate repositories through contract and evidence records rather
  than task dependencies;
- Task execution, review, verification, and knowledge promotion bind the active
  Revision and exact source hashes;
- Reconcile can interrupt and selectively resume every supported path;
- the small, complex-domain, and three-project golden scenarios pass;
- Milestone C C4 and packaged/live certification gates pass before autonomous
  execution is announced as ready.
