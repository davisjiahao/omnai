# OmnAI v0.3 Module-Boundary Protocol Fusion Design

## Context

OmnAI already has a complete delivery loop: research, domain modeling, specification, design, planning, implementation, independent review, verification, and reconciliation. Its packaged Protocol Resources supply the method while Core owns routing, state, guards, evidence, and audit.

Matt's `codebase-design` material adds a useful architecture vocabulary and a set of concrete tests for internal code shape:

- a **module** is an interface plus an implementation at any scale;
- an **interface** is everything a caller must know, including operations, invariants, ordering, errors, configuration, and performance expectations;
- a **seam** is a place where behavior can change without editing callers;
- an **adapter** is a concrete implementation attached at a seam;
- **depth** is capability hidden behind a small, stable interface;
- **leverage** is the useful complexity removed from each caller;
- **locality** keeps behavior, data, and tests close to their owner;
- a **deletion test** asks whether removing an abstraction makes its complexity disappear or merely redistributes it across callers.

That material is a design reference, not an end-to-end delivery process. Superpowers supplies the complementary operating discipline: compare approaches, write a plan, test behavior first, review independently, verify with fresh evidence, and stop when facts invalidate an approved decision.

The goal is to combine both strengths without creating a second architecture workflow beside OmnAI.

## Decision

Add a risk-scaled **module-boundary assessment** to the existing repository phase protocols and the existing `architecture` review lens.

The assessment is guidance carried by canonical artifacts. It is not a new Host Skill, `Capability`, protocol ID, scenario, lifecycle stage, readiness key, persisted aggregate, task schema, review lens, or execution authority.

This document amends repository Protocol Resource methods. It does not replace or broaden the approved v0.3 autonomous execution design or plan.

The current public Host surface therefore remains exactly four Entry Skills. The approved v0.3 plan may later add the separate execution Entry Skill `omnai-run` after C4 certification; this change adds neither a fifth pre-v0.3 Skill nor a sixth post-v0.3 Skill.

## Why there is no standalone `codebase-design` Skill

A standalone reference is useful when a driver can invoke it only at the right moment. In OmnAI, Core already knows the scenario, risk, impact, active capability, artifacts, and legal next action. A second user-facing Skill would duplicate discovery, artifact ownership, stop rules, and Reconcile routing while having less context than the existing phase.

The responsibility split is:

| Concern | Owner |
| --- | --- |
| Current architecture facts and lineage | `repository.research` / `research.md` |
| Domain meaning, lifecycle, invariants, and ownership | `repository.model` / `domain.md` |
| Observable intent and compatibility expectations | `repository.spec` / `spec.md` |
| External HTTP, event, or public-library semantics | `contract.md` or another formal contract source |
| Target internal modules, interfaces, seams, adapters, and migration | `repository.design` / `design.md` |
| Frozen cross-project execution contract and traceability | v0.3 `ContractSnapshot` derived from approved contract sources |
| Executable slices and evidence | `repository.plan` / `tasks.yaml` |
| Bounded implementation | `repository.work` |
| Conformance and architecture challenge | `repository.review` with the existing `architecture` lens |
| Fresh proof | `repository.verify` |
| Invalidated assumptions and selective re-entry | `repository.reconcile` |

`interaction.brainstorm` remains the owner of collaborative alternative exploration. The module-boundary assessment supplies comparison criteria; it does not create another brainstorming procedure.

## Applicability and scaling

Every Design run is guided to state one of three applicability levels. The rest of the assessment scales to that result. This amendment enforces the guidance through the canonical prompt/scaffold, deterministic prompt tests, and Agent pressure tests; Core does not parse or validate the Markdown field.

| Level | Use when | Required treatment |
| --- | --- | --- |
| `not-applicable` | The change stays behind a stable interface and does not change callers, ownership, seams, adapters, the interface test boundary, or dependency direction. It may still add focused tests inside that boundary. | State the reason in one short paragraph and continue with the normal design. Do not invent a port, adapter, or module. |
| `focused` | An existing internal interface or module boundary changes, but ownership and the wider architecture stay stable. | Describe only the affected module, callers, interface semantics, dependency direction, test surface, and migration. |
| `full` | The work is architecture governance, a shared library or cross-service change, a migration, a new or materially changed boundary, an ownership/lifecycle change, or another P0/P1 boundary decision. | Compare genuinely distinct shapes, complete the module/interface/seam analysis, define enforcement and retirement, and require architecture review and proportionate evidence. |

Small fixes and narrow features keep their existing path. A null check, calculation correction, or local implementation change behind a stable interface does not earn architecture ceremony merely because this vocabulary exists.

## Artifact contracts

### Research

`research.md` records current truth, never the target design. When architecture is relevant it maps:

- current topology, ownership, callers, and dependency direction;
- current interfaces, seams, adapters, and dependency category;
- leaked knowledge, change fan-out, and locality problems;
- historical reasons for the shape and which constraints still apply;
- exact repository evidence for every load-bearing claim.

The dependency categories are `in-process`, `local-substitutable`, `remote-but-owned`, and `true-external`. Classification describes current facts; it does not automatically require a port or adapter.

### Domain model and specification

`domain.md` remains authoritative for domain boundaries, ownership, lifecycle, invariants, and ubiquitous language. A code seam is not automatically a bounded context.

`spec.md` records affected callers, observable behavior, preserved constraints, compatibility needs, and decision triggers. It must not prescribe an internal module shape unless that shape is itself an externally observable requirement.

### Design

`design.md` owns the target module-boundary assessment. Its template adds:

1. **Architecture applicability** — `not-applicable`, `focused`, or `full`, with the reason.
2. **Modules and responsibilities** — ownership, callers, owned data, hidden complexity, and locality.
3. **Interface semantics** — operations, invariants, ordering, error behavior, configuration, and performance expectations.
4. **Seams, adapters, and dependency direction** — seam location, dependency category, actual variation, concrete adapters, and retirement plan.
5. **Depth, leverage, and deletion test** — what callers no longer need to know; where complexity would move if the abstraction were removed; what observable behavior would break.
6. **Boundary enforcement and interface test surface** — dependency rules, package/export constraints, characterization/contract/integration evidence, and the smallest stable test surface.

Modules, interfaces, seams, and adapters use stable change-local IDs such as `MOD-001`, `IF-001`, `SEAM-001`, and `ADP-001`. An internal interface references an external contract by its authoritative ID; `design.md` must not duplicate HTTP/event/public-library semantics that could drift from `contract.md` or another formal contract source.

Depth is judged at the interface, not by implementation size. A shallow pass-through abstraction is not improved by adding another layer. One adapter is a hypothetical variation point; two real implementations make the seam concrete. Neither rule is absolute: the design must cite current evidence and expected change, not manufacture adapters to satisfy a checklist.

For consequential and difficult-to-reverse interface choices, compare two or three materially different module shapes. Use three when viable; if only two survive known constraints, record why. Each option is compared on depth, locality, dependency direction, migration risk, testability, operability, and deletion behavior.

### Plan

`tasks.yaml` uses its existing fields; no schema change is required:

- `files` contributes task-local scope; Core combines it with explicit policy when deriving `allowedPaths`;
- `consumes` and `produces` reference stable internal IDs such as `module:MOD-001` and `interface:IF-001`;
- `steps` encode the implementation/migration order;
- `evidenceRequired` names behavioral, characterization, contract, integration, operability, or deletion/simplification proof.

Planning must not bury an unresolved boundary choice inside an implementation task. A claimed deletion or simplification opportunity requires task-local evidence proving behavior and contract preservation. Internal references must not use the reserved `contract:` prefix. Cross-project boundaries use `contract:<key>` for discovery and the approved v0.3 `contractRefs` at execution time, never cross-project task dependencies.

### Work

Work implements only the selected task and the approved boundary. Tests prefer observable behavior through the stable interface; focused unit tests remain appropriate for algorithms and failure cases, but callers and tests must not reach through a module solely to couple themselves to its implementation.

If implementation proves that the approved interface cannot express required ordering, cancellation, retries, lifecycle, errors, ownership, or another load-bearing behavior, Host-assisted repository Work reports `BLOCKED`, preserves the patch and evidence, and routes Reconcile. A v0.3 `PROJECT_WRITER` instead emits a `WorkerResult` with `outcome: SIGNAL` and `signalKind: ASSUMPTION_INVALID`; it uses `outcome: BLOCK` only when execution is blocked without a new invalidating fact. Neither path may stack an adapter, weaken a test, or silently reinterpret the design.

### Review and verification

When Core selects the existing `architecture` lens, independent review applies the module-boundary assessment at its declared `not-applicable`, `focused`, or `full` depth and cites `design.md`, `contract.md`, task evidence, and the diff. Selecting the lens does not force a full assessment; P0/P1 hotfix, performance, and other risk-selected reviews still scale by applicability. Review checks for:

- shallow pass-through modules and needless indirection;
- caller knowledge that leaks implementation details;
- dependencies pointing against declared ownership;
- seams with no evidenced variation or adapters that conceal incompatible semantics;
- tests reaching through the declared interface;
- migration steps without retirement or rollback;
- a deletion claim without proof of preserved behavior.

The two approved review records remain separate and only share these criteria:

- repository-stage review writes `ReviewRecord.findings` with `CRITICAL | IMPORTANT | MINOR` severity;
- v0.3 execution review writes `ReviewFinding` with `INFO | NON_BLOCKING | BLOCKING` severity.

Neither schema is changed or merged. Static “unused” analysis alone is insufficient proof for deletion. Verification requires fresh behavioral, characterization, contract, integration, or operability evidence proportionate to risk and records `PASS`, `FAIL`, or `INCONCLUSIVE` honestly.

### Reconcile

Repository Reconcile preserves the existing L0–L5 levels and only clarifies where module-boundary signals belong:

| Level | Invalidated decision | Minimum re-entry |
| --- | --- | --- |
| L0 | Task-local implementation detail; approved task, behavior, and boundary still hold | Rework or revalidate the affected task and evidence. |
| L1 | Task decomposition, ordering, scope, or evidence plan | Rebuild the affected Plan/task subtree. |
| L2 | Technical interface, seam, adapter, dependency direction, migration, or test-surface assumption | Reopen Design and dependent Plan/Work/Review/Verify artifacts. |
| L3 | Domain ownership, lifecycle, invariant, bounded context, requirement, or acceptance intent | Reopen the earliest affected Model or Specification stage, then its downstream artifacts. |
| L4 | Product goal, product-level scope, or reality premise | Reframe the Change or create a new Change, then reopen affected downstream artifacts. |
| L5 | Existing delivery, validation, environment, or external-drift semantics | Use the existing L5 path; this amendment does not redefine it. |

`reopenFrom` is the earliest affected stage that actually exists in the selected scenario; Reconcile must not invent a stage or reopen both Model and Specification when only one is applicable. Reconcile preserves the previous Revision, Baseline, patch, tests, findings, and evidence as lineage. Content based on an invalidated decision becomes non-authoritative until revalidated; it is not silently deleted or certified. Unaffected tasks continue.

## v0.3 execution integration and non-authority

The handoff remains:

```text
research/spec/contract.md
  -> design.md: module-boundary assessment
  -> tasks.yaml: task-local scope + evidence
  -> (cross-project) ContractCandidate -> Critics/Resolver -> ContractSnapshot
  -> ReadySet -> Wave -> immutable RunPacket
  -> WorkerResult -> Reviewer ReviewFinding -> Core VerificationEvidence
  -> Core commit -> CommitSet
```

The assessment is never an execution aggregate and grants no authority:

- Core alone authorizes routing, packets, Claims, evidence acceptance, commits, recovery, and CommitSets.
- Agents stage typed outputs; they do not mutate active Run truth, event logs, Claims, Waves, ContractSnapshots, or CommitSets.
- A cross-project interface must retain `ContractSnapshot` traceability, scenarios, fixtures, validators, source hashes, and immutable `contractRefs`. Design prose is not a substitute.
- ReadySet and Wave freeze the approved scoped task, Revision, Baseline, contract refs, starting Git facts, allowed paths derived by Core, required evidence, and selected Agent as defined by the v0.3 plan. They do not implicitly freeze every byte of `design.md` or every repository protocol.
- A Writer receives one immutable `RunPacket`; it does not reinterpret the design. A change to contract, allowed paths, task objective, Revision, or Baseline requires Reconcile and a new packet/new Run.
- The lens cannot acquire a second Writer, release a Claim early, create an official worker commit, bypass Core verification, or change CommitSet progression.
- An internal module failure is revalidated within its owning project. A shared contract failure propagates through the `ContractSnapshot` reference closure to affected tasks, Runs, and participating projects. Unrelated projects and already integrated results are not rolled back.
- A deletion test is a safe counterfactual and verification method, never authority to delete outside `allowedPaths` or destroy recovery material.

No `ModuleAssessment` schema is added. Repository prepared-stage manifests continue to pin their exact protocol version/hash. v0.3 execution lineage continues to use only the fields approved for `ContractSnapshot`, `RunPacket`, Revision, task references, evidence, and Review findings; this amendment does not claim that execution packets pin repository protocol content.

## Protocol and compatibility changes

The semantic method changes bump the affected packaged resources from version 1 to version 2:

- `repository.research`
- `repository.spec`
- `repository.design`
- `repository.plan`
- `repository.work`
- `repository.review`
- `repository.verify`
- `repository.reconcile`

Historical repository run manifests remain valid and retain their original version/hash. New repository prepared runs record version 2 and its exact content hash. There is no amendment-specific product schema migration, task schema migration, evidence schema migration, new catalog entry, or Host installation change.

The `architecture-governance` scenario gains precise internal-architecture signals such as `architecture review`, `bounded context`, `dependency direction`, `dependency cycle`, and `layering violation`. It keeps the existing `architecture-review` evidence ID and existing `architecture` lens. Cross-service contract implementation continues to route to `cross-service-change`; public SDK/API work continues to route to `shared-library`.

When an input matches both `architecture-governance` and one of those specialized boundary profiles, the positive `cross-service-change` or `shared-library` match takes precedence. This is safer because the specialized profiles retain stricter contract and compatibility gates while still consuming the same module-boundary method; allowing the general architecture route to win could discard required cross-service or public-API evidence.

## Acceptance criteria

1. An internal layering/dependency/module-boundary prompt routes to `architecture-governance`, selects the existing `architecture` review lens, and prepares an audited version-2 repository-stage protocol bundle containing the risk-scaled module-boundary method.
2. A small P3 feature does not select the architecture lens, and the Design method permits an explicit `not-applicable` assessment without inventing abstractions.
3. Research, Specification, Design, Plan, Work, Review, Verify, and Reconcile prompts state their distinct artifact ownership and stop rules.
4. A Review record missing a Core-required `architecture` lens cannot complete; a complete non-blocking record can.
5. A contradicted approved seam stops Work and re-enters at L2 or L3 rather than stacking adapters or rewriting tests.
6. Repository prepared-stage manifests pin the exact version and hash; historical protocol versions need no rewrite.
7. Cross-service contract and public SDK/API prompts retain their more specific scenario routes, and the catalog remains at 19 scenarios.
8. This amendment adds no Host Skill, `Capability`, task/review/execution schema, or authority beyond changes already approved in the v0.3 execution plan.

## Evaluation scenarios

The same scenarios are run before and after the change:

- **Brownfield architecture:** extract provider-specific quote orchestration from a Spring service. The result should identify real callers and hidden complexity, compare module shapes, define truthful async/error semantics, and supply migration/retirement evidence.
- **Small local fix:** add a null guard behind a stable interface. The result should explicitly avoid new ports, adapters, or architecture ceremony.
- **Disproved seam during Work:** the only real provider requires streaming callbacks, cancellation, ordering, and provider-owned retries although the approved interface is synchronous. Host-assisted repository Work should report `BLOCKED`; a v0.3 `PROJECT_WRITER` should emit `WorkerResult` with `outcome: SIGNAL` and `signalKind: ASSUMPTION_INVALID` (or `BLOCK` only when it lacks a new invalidating fact). Both preserve evidence, classify at least L2, and selectively reopen Design and dependent work.

Deterministic tests cover routing, prompt composition, protocol version/hash audit, scaffolds/output contracts, review-lens enforcement, and the unchanged public Skill surface. Agent pressure tests assess the quality of the three scenarios without turning generated prose into a runtime gate.
