# OmnAI v0.3 Change 权限核心修复设计

- **分支：** feat/omnai-v0.3-full-pipeline-fusion
- **关联规格：** 2026-08-22-omnai-v0.3-micro-change-design.md

## 1. 结论

本轮只修复七项 Change 权限完整性风险，建立一条可恢复、可审计、失败关闭的统一权限事务。它不提前实现 F2、F3、F4，不把执行沙箱、Workset 或 Host 安装系统塞进权限修复，也不提前冻结 v0.3。

产品版本采用“一次成型”的裁决：

1. 开发期间 package 和 CLI 继续保持 0.2.0。
2. 在 F2、F3、Milestone C C1–C3、F4、micro-change 和 C4 发布表面完成前，不生成最终 WorkflowLock，不冻结最终场景目录。
3. micro-change 在最终冻结前始终不可用。
4. 所有功能完成后只进行一次最终 Writer 普查、场景目录冻结和 F5 候选认证。
5. 只有最终认证通过，Task 22 才将产品版本一次性提升为 0.3.0。
6. 最终 v0.3 不读取、迁移或兼容 v0.2 以及开发期间的中间态持久化结构。

本文件取代同一路径早期英文草案中的冲突内容。任何在本文件完成书面审阅前生成的实施计划均不具备执行权威，必须基于本规格重新生成。

## 2. 要解决的七项风险

| 编号 | 风险 | 修复后的不变量 |
| --- | --- | --- |
| R01 | Flow 只绑定 Decision 的部分身份，正文变化可能不改变路由身份 | Flow 绑定完整、规范化的 Decision 集合及其内容摘要 |
| R02 | SourceRef 可能语法合法但来源伪造、过期或由调用方指定路径 | Core 在 Change 锁内解析来源并冻结真实字节摘要 |
| R03 | 部分 Change Writer 绕过锁、事务上下文或 Writer 门禁 | 所有 Change 持久写入只能通过统一 WriterFence |
| R04 | 不同事务族之间缺少一条连续的全局权限链 | Genesis 后每次完成写入都绑定唯一前驱权限头 |
| R05 | 审计成员正确但顺序可能漂移，追加过程中可能出现撕裂 | 审计以旧文件完整前缀加下一事件进行整文件原子替换 |
| R06 | 普通场景与 Scenario 恢复使用不同或不完整的终态判断 | 创建、执行、恢复共同使用一个精确终态计算器 |
| R07 | “只读一次”依赖自报指标，恢复路径可能再次读取可变来源 | 上下文冻结观察结果，提交后由机器重读生成 Seal，业务逻辑零次回读来源 |

七项风险必须整体关闭。只修补某个调用点而允许其他 Writer、恢复入口或 CLI 继续绕过，不算完成。

## 3. 范围和所有权

### 3.1 本规格拥有的内容

本规格只拥有：

- Decision 完整内容与 Flow 身份绑定。
- 严格的 Core SourceRef 解析。
- Change 锁、不可变权限上下文和 WriterFence。
- Genesis 后的全局 AuthorityEnvelope 链。
- PENDING/COMPLETED 权限事务与精确恢复。
- 审计整文件原子更新。
- 普通场景与 Scenario 共用的终态计算。
- 真实观察计数和 MachineAuthoritySeal。
- 上述能力所需的规范哈希、锁所有者、路径安全、配额和稳定错误。

### 3.2 明确延期的内容

| 内容 | 所有者 | 本规格允许做什么 |
| --- | --- | --- |
| Task v2、Brief、任务派生视图 | F2 | 只预留 SourceRef 和 WriterFence 接口，不定义其业务 Schema |
| Review v2、Learning、知识闭环 | F3 | 只允许其未来成为受门禁 Writer，不定义评审业务状态 |
| 验证命令隔离、进程树、密钥与 Host 读取限制 | Milestone C | 权限核心只接收受信适配器返回的结果，不实现沙箱 |
| AgentSessionAdapter、执行 Run、并行 Worker、CommitSet | C1–C3/F4 | 不在 src/execution 中复制执行引擎 |
| Workset WOP、原生 Worktree、Host 安装事务 | 各自里程碑 | 只消费已认证的 Change 快照并遵守锁顺序 |
| micro-change 路由、准入、升级和证据 | micro-change 规格 | 依赖本规格，不在权限修复中提前加入目录 |
| 最终发布资源、WorkflowLock、0.3.0 升版 | C4/F5/Task 22 | 权限修复期间保持关闭 |

Stage 和 Execution 使用独立身份空间：

| 领域 | Run 身份 | Evidence 身份 |
| --- | --- | --- |
| Change 阶段 | StageRunId | ChangeEvidenceId |
| 生产执行 | ExecutionRunId | ExecutionEvidenceId |

两个领域可以通过显式引用关联，但不能共用同一个 RunId 或 EvidenceId 类型。

### 3.3 非目标

本规格不：

- 新建第二个工作流运行时或通用事件溯源平台。
- 实现远程共识、分布式事务或远程可信存储。
- 支持调用方传入 Change 目录、任意绝对路径或可构造的 ChangeRef。
- 提供 force、repair 或自动接管未知事务的后门。
- 提前冻结场景、Capability、证据模板或 Writer 总目录。
- 宣称能抵御已经控制操作系统或完整重写全部历史的攻击者。

## 4. 威胁模型

### 4.1 必须防护

- 多个合作式 Core 进程同时操作同一 Change。
- 进程在任一事务步骤崩溃、断电或只写入部分内容。
- 单个状态、来源、审计或事务文件被局部修改。
- 伪造、过期、跨 Change 或跨 Revision 的 SourceRef。
- 路径穿越、符号链接逃逸和仓库根识别错误。
- 请求重放、同一请求 ID 携带不同内容。
- 超过来源数、目标数、文件字节数或审计事件数等配额。

### 4.2 检测边界

本地哈希链提供完整性检测和因果连续性，不等于外部密码学认证。如果同一系统用户已经控制 OmnAI 程序、工作区全部文件并能一致重写整条历史，本地文件无法独立证明被篡改。

需要抵御该威胁时，必须增加工作区外签名密钥、远程时间戳或远程可信锚点。该能力属于后续安全里程碑，不得伪装成本轮已解决。

## 5. 核心不变量

### I01：只接受 ChangeId

所有公共读写入口只接受项目身份和 ChangeId。Core 从规范项目清单解析 Change，调用方不能提交目录、ChangeRef 或“已经解析”的元数据绕过权限判断。

### I02：一个规范锁

每次权限操作先解析规范仓库根，再按 repositoryIdentity、projectIdentity、ChangeId 的固定顺序获得同一把 Change 锁。获得锁后必须重新验证项目和 Change 身份，关闭解析到加锁之间的竞态。

### I03：一个不可变上下文

Core 在锁内只读取一次本次操作所需的 Decision、Revision、权限头、来源和目标基线，构造 ChangeAuthorityContext。后续校验、写入和恢复只能使用该上下文，不得为了“确认”再次读取原始来源。

### I04：严格来源解析

SourceRef 是逻辑身份，不是路径。SourceRefResolver 根据类型、逻辑 ID、Revision 和期望摘要定位权威内容，返回冻结字节、摘要和解析证明。期望摘要不一致时失败，不能自动替调用方改正。

### I05：所有 Writer 受门禁

任何能够修改已发布 Change 的 Core、CLI、恢复入口或小型辅助 Writer，都必须调用 WriterFence。模块不得直接使用通用写文件函数修改 Change 机器状态。

### I06：先意图，后目标

持久目标写入前必须先落盘 PENDING AuthorityRecord。该记录冻结请求摘要、来源捕获、目标摘要、审计事件和预期前驱。PENDING 落盘后，只允许精确相同请求恢复。

### I07：一条全局完成链

Genesis 是首个权限头。每个 COMPLETED AuthorityRecord 绑定当时唯一的 predecessorAuthorityHash，完成后成为新权限头。锁内不允许分叉、跳过前驱或改写历史记录。

### I08：审计顺序属于事务

审计事件和目标内容一起冻结在 PENDING 中。发布时必须验证旧审计完整字节摘要和长度，然后以“旧完整前缀 + 下一组完整事件”生成临时文件并原子替换。不能逐行 append，也不能重新排序。

### I09：一个精确终态

TerminalStateCalculator 是纯函数。新写入、PENDING 恢复、COMPLETED 重试和 Scenario 重分类都使用它计算同一个目标集合及摘要，不能只比较部分文件或部分字段。

### I10：机器 Seal

目标与审计发布后，Core 重新读取机器拥有的目标集合，生成 MachineAuthoritySeal。该重读只验证落盘结果，不重新读取 Decision 或 SourceRef 原始来源。Seal 不匹配时事务不能完成。

### I11：拒绝无副作用

在 PENDING 之前，Schema、路径、来源、配额、锁或权限校验失败不得产生 Change 持久写入。PENDING 之后，非精确恢复请求也不得产生额外写入。

## 6. 组件边界

### 6.1 AuthorityContracts

职责：

- 定义规范标量、稳定错误、锁所有者和权限事务 Schema。
- 规范化 JSON 和领域哈希。
- 定义状态转换，不访问文件系统。

依赖：无 I/O 依赖。

### 6.2 ChangeAuthorityContext

职责：

- 持有本次操作的 Change 锁租约。
- 冻结项目、Change、Revision、Decision、权限头、配额和目标基线。
- 记录真实读取观察，而不是接受调用方提供的计数。

依赖：规范项目解析器、受约束文件读取器。

### 6.3 SourceRefResolver

职责：

- 将逻辑 SourceRef 解析为当前权威内容。
- 校验 Change、Revision、来源类型、逻辑 ID 和期望摘要。
- 返回 SourceCapture，不暴露任意文件路径。

依赖：ChangeAuthorityContext、各领域只读投影。

### 6.4 AuthorityTransaction

职责：

- 创建 PENDING 记录。
- 发布目标与审计。
- 生成 MachineAuthoritySeal。
- 完成全局 AuthorityEnvelope 链。
- 处理精确重试和崩溃恢复。

依赖：原子文件接口、AuthorityContracts、TerminalStateCalculator。

### 6.5 WriterFence

职责：

- 成为所有 Change Writer 的唯一公共写入口。
- 将业务请求转换成确定性的 MutationIntent。
- 拒绝未登记 Writer、未声明目标和任意路径写入。

依赖：AuthorityTransaction。

### 6.6 TerminalStateCalculator

职责：

- 根据冻结请求和上下文计算完整目标文件集合、字节摘要及审计事件。
- 为新事务、恢复和重试提供同一结果。

依赖：纯业务编译器；不得直接执行 I/O。

## 7. 核心数据契约

以下是语义必需字段。实施计划可以拆分文件，但不得减少字段、改变所有权或把受保护字段交给调用方。

### 7.1 ChangeLockOwnerV1

- repositoryIdentity
- projectIdentity
- changeId
- nonce
- pid
- processStartMarker
- createdAt

锁所有者文件 Schema 非法、身份不符或进程状态无法证明时，不得自动删除。对 Schema 合法的本机锁，只有确认记录的 pid 与 processStartMarker 已不再标识同一个存活进程、宽限期已过、锁文件 nonce 仍未变化时，显式恢复协议才可用比较后删除的方式清理。

### 7.2 ChangeAuthorityContextV1

- repositoryIdentity
- projectIdentity
- changeId
- revisionId
- authoritySchemaVersion
- authorityHeadHash
- decisionSetHash
- baselineHash
- authorityLimitsHash
- sourceCaptures
- targetObservation
- observedReadSet
- lockNonce

上下文只存在于进程内，不作为可由外部恢复的授权令牌。持久恢复使用 PENDING 记录中的冻结数据重新认证当前环境。

### 7.3 SourceRefV1 与 SourceCaptureV1

公共 SourceRef 只包含：

- kind
- logicalId
- revisionId
- expectedContentHash

Core 生成的 SourceCapture 额外包含：

- resolvedAuthorityHash
- contentByteLength
- contentHash
- frozenBytes 或受内容寻址保护的内部引用

SourceRef 不包含绝对路径、仓库外 URI、回调或调用方提供的“已验证”标记。
如果使用内部引用，引用指向的冻结字节必须和 PENDING 记录一起受保护；每次恢复都重新校验长度和 contentHash，不能信任引用名称。

### 7.4 AuthorityRecordV1

共同字段：

- operationRequestId
- operationKind
- requestDigest
- status
- predecessorAuthorityHash
- contextDigest
- sourceCaptureDigest
- targetDigest
- auditBatchDigest
- createdAt

PENDING 还冻结：

- 目标文件及其完整字节或确定性内容引用
- 旧目标观察摘要
- 旧审计文件摘要和长度
- 下一批有序审计事件
- 规范响应字节及 responseDigest

COMPLETED 还包含：

- machineAuthoritySealHash
- completedAt
- responseDigest

同一个 operationRequestId 永远只能对应一个 requestDigest。

### 7.5 MachineAuthoritySealV1

- operationRequestId
- pendingRecordHash
- predecessorAuthorityHash
- targetSetHash
- auditFileHash
- observedMachineReadSet

Seal 只覆盖 Core 机器拥有的落盘结果。业务来源已经由 SourceCapture 冻结，不在此阶段回读。

### 7.6 AuthorityEnvelopeV1

- sequence
- operationRequestId
- operationKind
- predecessorAuthorityHash
- recordHash
- terminalStateHash
- auditBatchHash
- completedAt

Genesis 的 sequence 为 0，后续完成事务依次为 1、2、3。哈希链前驱和 sequence 任一不连续均视为 AUTHORITY_CHAIN_CORRUPT。

## 8. 规范化与哈希

所有权限哈希遵循同一规则：

1. 输入先通过 strict Schema，未知字段失败。
2. 允许的值仅为 UTF-8 字符串、布尔值、null、规范非负整数、数组和对象。
3. 禁止 undefined、浮点数、NaN、Infinity、稀疏数组和重复 JSON 键。
4. 对象键按 Unicode 码点升序排列；数组保持原顺序。
5. 字符串使用标准 JSON 转义；整数使用无前导零的十进制表示；输出不含空白。
6. 哈希前映像按以下字节顺序组成：ASCII 固定头 OMNAI-AUTHORITY 后跟一个 NUL；4 字节无符号大端领域标签长度及其 UTF-8 字节；4 字节无符号大端 Schema 版本长度及其 UTF-8 字节；8 字节无符号大端负载长度及规范 JSON UTF-8 字节。
7. 使用 SHA-256，输出小写十六进制。
8. 对象自身的 hash 字段不进入自己的前映像。

每种领域使用不同标签，例如 DECISION_SET、SOURCE_CAPTURE、AUTHORITY_RECORD、AUTHORITY_ENVELOPE、TERMINAL_STATE 和 MACHINE_SEAL。不同领域即使 JSON 相同，也不能得到可互换的权限摘要。

## 9. 路径、原子写入与配额

### 9.1 仓库根

OmnAI 是 Git 原生工作流。findRepositoryRoot 只信任成功执行的 git rev-parse。Git 不存在、起始目录不存在或不属于真实仓库时，必须返回带原始 cause 的稳定错误；不得扫描父目录中的 .git 作为弱回退。

### 9.2 路径规则

- 所有目标路径先转换为仓库根下的规范 POSIX 相对路径。
- 拒绝绝对路径、空路径、点段、反斜杠歧义、NUL 和仓库边界逃逸。
- 写入前逐级检查祖先组件，不允许符号链接组件。
- 最终文件使用不跟随符号链接的方式打开；临时文件必须位于同一受验目录。
- 原子替换前后重新验证目录身份和目标观察；无法证明安全时失败关闭。
- 不支持上述保证的平台不能静默降级为普通路径写入。

### 9.3 原子文件协议

目标文件和审计文件采用：

1. 在受验目标目录创建独占临时文件。
2. 写入完整字节。
3. fsync 临时文件。
4. 复核旧目标观察摘要。
5. 同文件系统原子 rename。
6. fsync 父目录。
7. 删除操作只允许由业务规格明确授权；权限核心本身不推断删除。

### 9.4 配额

AuthorityLimitsV1 集中定义并进入 contextDigest，至少限制：

- 单请求规范字节数。
- SourceCapture 数量和总字节数。
- 目标文件数量、单文件和总字节数。
- 单事务审计事件数。
- 单 Change 权限记录数和审计文件大小。

开发阶段使用版本化 Core 常量；最终数值在 E2 目录冻结时进入最终权限目录。任何加大配额的变化都必须产生新 Revision 和新权限摘要，不能由调用方临时覆盖。

## 10. 统一权限事务

### 10.1 新请求

1. 公共入口只接收 ChangeId、operationRequestId 和结构化业务请求。
2. Core 解析规范仓库、项目和 Change，获得 Change 锁。
3. 锁内重验身份并只读一次，构造 ChangeAuthorityContext。
4. SourceRefResolver 解析并冻结全部来源。
5. TerminalStateCalculator 计算完整目标、终态摘要和有序审计事件。
6. 校验权限头、Revision、请求身份、路径和配额。
7. 持久化 PENDING AuthorityRecord。
8. 按原子文件协议发布目标集合。
9. 以旧完整前缀加冻结事件原子替换审计文件。
10. 重读机器目标并生成 MachineAuthoritySeal。
11. 校验 Seal 与冻结目标完全相等。
12. 将记录完成为 COMPLETED，并把新的 AuthorityEnvelope 设为全局权限头。
13. 返回与 responseDigest 匹配的结果。

### 10.2 恢复与重试

| 当前状态 | 请求情况 | 结果 |
| --- | --- | --- |
| 无记录 | 合法新请求 | 创建 PENDING 并执行 |
| PENDING | requestDigest 完全相同 | 使用冻结目标、来源和审计继续，不重新解释业务请求 |
| PENDING | requestDigest 不同 | AUTHORITY_REQUEST_CONFLICT，无额外写入 |
| COMPLETED | requestDigest 相同且当前机器状态仍匹配 | 返回原结果，不重复写入 |
| COMPLETED | 当前目标、审计或权限头漂移 | AUTHORITY_TARGET_DRIFT 或 AUTHORITY_CHAIN_CORRUPT |
| 记录非法、状态未知或前驱分叉 | 任意请求 | AUTHORITY_CORRUPT，不自动修补 |

如果崩溃发生在 COMPLETED 记录落盘和全局头替换之间，精确重试先认证冻结记录、机器 Seal 和旧权限头，再完成唯一允许的头推进。其他请求不能接管。

## 11. 错误和失败策略

稳定错误 ID 至少包括：

- REPOSITORY_NOT_FOUND
- GIT_UNAVAILABLE
- AUTHORITY_INVALID_INPUT
- AUTHORITY_LOCK_CONFLICT
- AUTHORITY_LOCK_OWNER_INVALID
- AUTHORITY_REQUEST_CONFLICT
- AUTHORITY_SOURCE_MISSING
- AUTHORITY_SOURCE_STALE
- AUTHORITY_PATH_UNSAFE
- AUTHORITY_QUOTA_EXCEEDED
- AUTHORITY_HEAD_DRIFT
- AUTHORITY_AUDIT_DRIFT
- AUTHORITY_TARGET_DRIFT
- AUTHORITY_SEAL_MISMATCH
- AUTHORITY_CHAIN_CORRUPT
- AUTHORITY_CORRUPT

错误 ID 是机器契约，附加诊断文字可以包含 ChangeId、操作阶段和安全的 cause 摘要，但不能暴露来源正文、密钥或工作区外路径。

所有失败遵循：

- PENDING 前失败：除获取和释放规范锁所需的协调记录外，无 Change 持久副作用；锁记录不能推进权限头或改变业务状态。
- PENDING 后失败：只保留恢复所需的冻结意图和已经原子发布的可认证状态。
- 未知或冲突：失败关闭。
- 不允许 force 绕过。

## 12. 实施顺序

### 12.1 Preflight：基线可靠性修复

- 移除 findRepositoryRoot 的弱 .git 回退。
- 保留递归测试发现，按稳定排序顺序扫描各模块 test 目录；目录遍历使用顺序或有界并发，不能创建无界 Promise.all。
- 补齐 Git 缺失、非仓库、起始目录缺失、非 ENOENT 启动失败和 cause 保留测试。
- Git 缺失测试通过可注入命令网关或隔离子进程构造，不能修改测试进程的全局 process.env.PATH。
- 完成独立代码复审后单独提交，不与权限实现混合。

### 12.2 权限核心

| 阶段 | 内容 | 退出条件 |
| --- | --- | --- |
| AR-A | AuthorityContracts、规范哈希、Decision/Flow 完整绑定 | R01 聚焦测试通过 |
| AR-B | Change 锁、ChangeAuthorityContext、观察读取、Seal | R07 聚焦测试通过 |
| AR-C | Strict SourceRef 和 SourceRefResolver | R02 聚焦测试通过 |
| AR-D | PENDING/COMPLETED、AuthorityEnvelope、Genesis 后全局链 | R04 与崩溃测试通过 |
| AR-E1 | 迁移当前已存在的 Change Writer，建立临时普查 | R03 对现有 Writer 关闭；不冻结最终目录 |
| AR-F | 审计整文件原子更新和恢复 | R05 测试通过 |
| AR-G | TerminalStateCalculator、普通场景与 Scenario 收口 | R06 测试通过 |

AR-E1 只能声明“当前 Writer 已迁移”，不能声明 v0.3 Writer 总目录已经冻结。

### 12.3 后续功能与最终冻结

固定顺序为：

~~~text
权限核心
  -> F2 Task/Brief
  -> F3 Review/Learning + Milestone C C1-C3
  -> F4 生产执行编排
  -> micro-change
  -> C4 发布表面
  -> AR-E2 最终 Writer 普查与场景目录一次性冻结
  -> F5 候选认证
  -> Task 22 发布 0.3.0
~~~

F3 与 C1–C3 只有在共享契约稳定、文件所有权不重叠时才可并行。任何阶段新增 Change Writer，都必须立即接入 WriterFence，并在 AR-E2 重新普查。

## 13. 测试策略

### 13.1 TDD 和测试位置

- 每个行为先编写失败测试并观察 RED，再实现最小代码得到 GREEN。
- 相对远程主干新增或修改的测试必须位于对应模块的 test 目录。
- 测试不能只断言错误字符串；应断言稳定错误 ID、持久状态和副作用集合。
- 新增或修改代码使用中文注释说明修改背景、目的和权限或恢复上下文；提交信息使用中文。

### 13.2 七项风险追踪

| 风险 | 必须覆盖的测试 |
| --- | --- |
| R01 | Decision 正文、顺序、增删、重复 ID、未知字段改变时 Flow 身份变化或失败 |
| R02 | 伪造摘要、过期 Revision、跨 Change 引用、路径注入、来源在锁前后漂移 |
| R03 | Core、CLI、恢复和辅助 Writer 的绕过扫描；未登记 Writer 编译或测试失败 |
| R04 | 并发请求、前驱分叉、重放、完成记录与权限头之间崩溃 |
| R05 | 审计前缀漂移、顺序互换、临时文件撕裂、原子替换前后崩溃 |
| R06 | 普通场景、Scenario、重分类、恢复对同一终态的精确比较 |
| R07 | 真实 I/O 计数、来源零回读、机器目标一次 Seal 重读、回调诱导回读 |

### 13.3 崩溃矩阵

独立子进程至少在以下边界强制退出：

- PENDING 写入前后。
- 每个目标原子替换前后。
- 审计替换前后。
- MachineAuthoritySeal 生成前后。
- COMPLETED 记录落盘前后。
- 全局权限头推进前后。
- 返回响应前。

每个点都验证：精确重试可恢复、不同请求不可接管、不重复审计、不重复推进权限头、最终状态与一次成功执行完全相同。

### 13.4 对抗性测试

必须覆盖：

- 符号链接、路径穿越和仓库根伪造。
- 非法锁所有者、PID 复用和进程启动标记变化。
- 重放相同 ID 的不同请求。
- 局部篡改来源、目标、审计、PENDING、COMPLETED 和权限头。
- 所有配额的边界值和越界值。
- micro-change 的准入、单次确认、Core 复核、越界升级、证据失效和禁止自动降级。

micro-change 测试在其独立实施阶段加入；权限核心阶段只提供可测试接口，不提前启用场景。

### 13.5 后台验证

进入代码审查、编译、测试、打包或日志核验流程时，由独立后台子 Agent 实际执行。每个 Agent 返回：

- 执行状态与退出码。
- 关键命令、工作目录、运行时和缓存环境。
- 通过数量、失败数量及关键输出摘要。
- 可复现证据路径。
- 失败原因和未覆盖风险。

互相独立的流程并行；有前后依赖的流程按顺序执行。主 Agent 负责汇总，不用自报结果替代真实执行。

## 14. 阶段验收与最终发布门

每个权限阶段至少通过：

- 聚焦单元与集成测试。
- 本阶段新增对抗测试。
- typecheck 和 build。
- 独立代码复审。
- git diff --check。

最终候选必须同时满足：

1. 现有 783 项测试、173 项对抗测试及全部新增测试通过。
2. 递归测试发现没有漏掉模块 test。
3. npm pack、从打包产物安装和编译后 CLI 端到端验证通过。
4. 不存在 skip、only、已知失败或未关闭的 Critical/Important 评审问题。
5. R01–R07 均有实现、正向测试、负向测试、崩溃测试和追踪证据。
6. AR-E2 证明所有最终 Change Writer 已接入 WriterFence。
7. 最终场景目录包含 micro-change，并且只冻结一次。
8. 冻结摘要、WorkflowLock、包内资源和安装后资源完全一致。
9. F5 候选认证通过。
10. 满足以上条件后，Task 22 才发布 0.3.0。

当前 783 和 173 是基线数量，不是允许删除测试的固定目标。最终数量只能增加或由有证据的测试合并说明调整，不能为了达到数字而漏跑新测试。

## 15. 完成定义

本规格只有在以下条件全部满足时才算完成：

- 七项风险全部关闭且没有 accepted/open 权限风险。
- 所有 Change Writer 经过统一事务，绕过扫描为零。
- 崩溃恢复和重试保持确定、幂等、无分叉。
- 来源只由 Core 解析，业务逻辑不回读冻结来源。
- 审计顺序、机器 Seal 和权限链能够相互认证。
- 延期功能仍由其各自规格拥有，没有被权限核心抢先实现。
- 最终冻结与 0.3.0 发布尚未发生，除非整个 v0.3 流程已经达到第 14 节最终门槛。

完成本规格意味着权限核心达到后续 F2–F4 和 micro-change 的生产级基础，不等于整个 OmnAI v0.3 已经可发布。

## 16. 已批准裁决

1. 采用一个最终 v0.3、一次冻结、一次升版。
2. 权限修复只关闭 R01–R07，不扩张成完整运行时。
3. 公共入口只接受 ChangeId，Core 在锁内构建只读一次的不可变上下文。
4. 采用 PENDING 意图、原子目标、整文件审计、机器 Seal、COMPLETED 全局链的统一事务。
5. 锁、路径、哈希、配额和错误全部失败关闭，不提供 force。
6. Stage 与 Execution 的 Run/Evidence 身份空间分离。
7. Writer 普查拆成 AR-E1 和 AR-E2，最终目录在 micro-change 与 C4 完成后才冻结。
8. 基线仓库识别只信任 Git，不保留弱 .git 回退。
9. 所有代码评审、构建、测试和证据核验由后台子 Agent 实际执行并汇总。
