# OmnAI v0.1 Native Workflow Design

## 1. Purpose

OmnAI v0.1 is a lightweight, repository-local, native AI engineering workflow. It does not run HumanLayer, Matt Pocock Skills, OpenSpec, Superpowers, GSD, BMAD, gstack, Compound Engineering, Trellis, ECC, or OMC at runtime. It independently implements selected mechanisms from those systems behind one coherent command and artifact model.

The first release must support the full set of common software-engineering scenarios without a backend service, database, web console, or always-on daemon. All durable state lives in the target repository under `.omnai/` and all orchestration logic is shipped as a TypeScript CLI plus thin host skills.

## 2. Design principles

1. **Reality before redesign.** Existing-code research describes what the system does before proposing what it should do.
2. **Meaning is distinct from implementation.** Domain terminology, ownership, lifecycle, and invariants are not mixed with file-level plans.
3. **Every change has a local source of truth.** Intent, research, domain decisions, spec, design, tasks, progress, evidence, and revisions live under one change directory.
4. **Workflow is adaptive, not a fixed waterfall.** Scenario profiles choose which stages are required, optional, or not applicable.
5. **Fresh context for bounded work.** Each agent task receives a compact context packet instead of accumulated conversation history.
6. **Evidence before completion.** No task or change becomes complete solely because an agent reports success.
7. **New facts trigger reconciliation, not a full reset.** Upstream changes selectively invalidate downstream artifacts and tasks.
8. **Plain files are the durable substrate.** Markdown is the human view; JSON and JSONL are the machine state.
9. **No runtime dependency on upstream workflows.** Compatibility import/export may be added later without controlling the native workflow.
10. **Lightweight by default.** No runtime npm dependencies, no server, no database, and no mandatory issue tracker.

## 3. Influences and native reinterpretation

### 3.1 HumanLayer-inspired reality recovery

OmnAI adopts read-only current-state research, question decomposition, parallel locator/analyzer/pattern-finder work, evidence references, and surgical re-research after changes. It does not copy the `thoughts/` directory, HumanLayer CLI, or project-specific scripts.

### 3.2 Matt-inspired semantic recovery

OmnAI adopts design trees, dependency-aware question frontiers, user-owned decisions, agent-owned fact finding, overloaded-term detection, edge-case pressure tests, change-local glossaries, sparse ADR candidates, Wayfinder-style fog/frontier maps, tracer-bullet vertical slices, and expand-migrate-contract for wide refactors.

### 3.3 OpenSpec-inspired change management

OmnAI adopts a change-first directory, delta-oriented specification, editable living artifacts, update-versus-new-change decisions, verification before archive, and brownfield friendliness. OmnAI adds explicit artifact versions, dependency metadata, revisions, selective invalidation, and richer task statuses.

### 3.4 Superpowers-inspired delivery discipline

OmnAI adopts design gates scaled by risk, detailed implementation planning, testable task boundaries, fresh executor context, independent spec and quality review, bounded fix loops, durable progress ledgers, systematic debugging, isolated branches/worktrees when supported, and fresh verification evidence before completion claims.

### 3.5 Additional influences

- **GSD:** thin orchestrator, fresh-context workers, file-backed durable state, quick and full paths.
- **BMAD:** scenario-specific workflow depth, readiness gates, minor/moderate/major course correction.
- **gstack:** product framing, real browser QA tiers, production-oriented verification.
- **Compound Engineering:** simplify before review, one-learning-per-run, knowledge promotion and refresh.
- **Spec Kit:** project governance, strict task schemas, extension points, independently testable stories.
- **Addy Agent Skills:** vertical/contract/risk-first slicing, rollback-friendly increments, adversarial doubt review.
- **Trellis:** scoped context injection from project rules, change artifacts, and learnings.
- **OMC/ECC:** runtime adapters and model/agent orchestration remain replaceable infrastructure.

## 4. Product shape

OmnAI v0.1 consists of:

- `omnai` TypeScript CLI, compiled to ESM JavaScript.
- Repository-local `.omnai/` state and artifacts.
- Built-in scenario profile registry.
- Built-in stage and scenario documentation.
- Thin host skills installable for Claude Code, Codex, and OpenCode-compatible layouts.
- Deterministic readiness router.
- Basic revision and reconciliation engine.
- Schema and repository validator.

No process remains running after a command exits.

## 5. Canonical tracks and stages

### 5.1 Reality track

`research` answers how the current system actually works. Its primary artifact is `research.md`, with confirmed facts, assumptions, unknowns, and evidence references.

### 5.2 Meaning track

`model` answers what domain concepts mean, who owns them, how they change over time, and which invariants apply. Its primary artifact is `domain.md`; hard-to-reverse decisions are recorded under `decisions/`.

### 5.3 Change track

- `frame`: product/user/problem framing.
- `spec`: delta requirements, constraints, acceptance criteria, and non-goals.
- `design`: technical approaches, selected solution, data flow, failure handling, migration, testing, and operations.
- `plan`: structured task DAG with verification requirements.
- `map`: decision map for work too uncertain or too large to plan linearly.

### 5.4 Delivery track

- `work`: execute one ready task at a time from a bounded context packet.
- `debug`: reproduce, localize, hypothesize, test, fix, guard, and verify.
- `verify`: collect fresh evidence and compare implementation to intent.
- `qa`: browser or experience verification when relevant.
- `ship`: record handoff or delivery readiness; it does not replace company deployment systems.
- `learn`: promote reusable, validated knowledge.

### 5.5 Reconcile loop

Any stage may emit a change signal. Reconciliation classifies the change level, snapshots the current revision, marks affected artifacts and tasks, records the reason, and recommends the stage that must be revisited.

Levels:

- `L0_IMPLEMENTATION`
- `L1_PLAN`
- `L2_DESIGN`
- `L3_DOMAIN_OR_REQUIREMENT`
- `L4_PRODUCT`
- `L5_DELIVERY`

Task impact states:

- `UNAFFECTED`
- `STALE`
- `NEEDS_REVALIDATION`
- `INVALIDATED`
- `SUPERSEDED`

## 6. Scenario profiles

v0.1 ships all of the following profiles:

1. `code-query`
2. `bug-fix`
3. `small-feature`
4. `complex-domain-feature`
5. `cross-service-change`
6. `migration-program`
7. `product-discovery`
8. `ui-ux-feature`
9. `performance-investigation`
10. `architecture-governance`
11. `data-migration`
12. `shared-library`
13. `emergency-hotfix`
14. `incident-response`
15. `release-failure`

Each profile declares:

- purpose and selection signals;
- required, optional, and skipped stages;
- default risk level;
- human approval gates;
- required evidence categories;
- stage ordering and allowed loop-backs;
- recommended next command.

Profiles are data, not hard-coded command branches. The CLI loads them from the built-in registry so future releases can add profiles without redesigning core state.

        ├── change.json
        ├── intent.md

        ├── spec.md
        ├── design.md
        ├── tasks.json
        ├── progress.jsonl
        ├── decisions/
        ├── evidence/

`change.json`, `tasks.json`, and `progress.jsonl` are machine-authoritative. Markdown artifacts are human-editable and receive readiness metadata through `change.json`.

## 8. Change model

A change contains:

```ts
interface ChangeRecord {
  schemaVersion: 1;
  id: string;
  slug: string;
  title: string;
  goal: string;
  scenario: ScenarioId;
  status: ChangeStatus;
  createdAt: string;
  updatedAt: string;
  activeRevision: string;
  readiness: Record<StageId, ReadinessState>;
  artifactVersions: Record<ArtifactId, number>;
  baseline?: string;
}
```

Readiness states:

- `NOT_APPLICABLE`
- `MISSING`
- `DRAFT`
- `READY`
- `CONCERNS`
- `STALE`
- `INVALIDATED`
- `BLOCKED`

Change statuses:

- `DRAFT`
- `READY`
- `IN_PROGRESS`
- `BLOCKED`
- `NEEDS_RECONCILE`
- `VERIFYING`
- `READY_TO_ARCHIVE`
- `ARCHIVED`
- `CANCELLED`

## 9. Task model

Tasks form a DAG and include stable IDs, objectives, acceptance criteria, dependency edges, input artifact versions, files, interfaces, execution steps, required evidence, state, impact state, and commit/run references.

## 10. CLI commands

```text
omnai init
omnai new <slug> --scenario <id> --goal <text>
omnai list
omnai use <change-id>
omnai status [change-id]
omnai next [change-id]
omnai scenario list
omnai scenario show <id>
omnai event <type> [options]
omnai reconcile [change-id] --level <level> --reason <text>
omnai validate [change-id]
omnai install-skills --host <claude|codex|opencode> [--scope project|user]
```

The CLI does not itself call an LLM in v0.1. Host skills guide the AI agent and use CLI commands to persist state.

## 11. Host skills

v0.1 provides native OmnAI skills for start, frame, research, model, map, spec, design, plan, work, debug, verify, QA, ship, learn, and reconcile.

Each skill names its purpose and applicable scenarios, defines permitted side effects, reads only relevant artifacts, writes canonical artifacts, appends progress events, stops on conflicts that require reconciliation, and avoids claiming completion without fresh evidence.

## 12. Router and readiness

`omnai next` is deterministic. It resolves the active change, loads the scenario profile, checks required stage readiness in profile order, checks blocking task or reconcile states, and returns the next command, reason, required inputs, and exit criteria.

## 13. Reconciliation rules

The first release uses a static dependency graph:

```text
frame ─┬─> spec ─> design ─> plan ─> work ─> verify ─> ship ─> learn
       │
research ─> model ─┘
map ─> research/model/spec
```

A signal invalidates stage readiness and task state according to level. Every reconcile operation creates a revision snapshot and appends an event.

## 14. Validation

`omnai validate` checks required files, schema versions, scenario/stage IDs, readiness consistency, revisions, task dependency cycles, missing evidence, archive readiness, and unresolved placeholders in artifacts marked ready.

## 15. Safety and boundaries

No command deletes application source code. Reconcile modifies only `.omnai/`. Skill installation refuses paths outside known roots and never overwrites foreign files. Writes are atomic where supported, and user-derived paths are constrained to the repository root.

## 16. Testing strategy

Tests cover path safety, scaffolding, all profiles, readiness routing, task DAG validation, L0-L5 reconciliation, host installation, CLI flows, and representative golden scenarios.

## 17. Non-goals for v0.1

No web UI, backend control plane, database, automatic LLM API calls, deployment control, issue/PR automation, distributed swarm, vector database, or complete upstream-format compatibility.

## 18. Release criteria

The CLI must build and pass all tests; all fifteen profiles and all native skills must be present; core commands must work in temporary repositories; reconcile must selectively invalidate and snapshot revisions; documentation and a Java authorization-migration example must be complete.
